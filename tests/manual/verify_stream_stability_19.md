## 1a 根因（前端缺陷，与后端方案 19 机制无关）

**现象**：健康推流（state=streaming、帧持续、WS 持续收帧、后端持续发帧）
连接约 17s 后无条件触发 H264 回退 `reason=timeout`；回切后前端会重置
`h264StartedAt`，17s 后再次回退——形成「推流 17s → 回退截图 → 探针恢复 →
再推流」的 ~35s 呼吸循环（.25 与 .18 均复现）。

**根因**：`frontend/src/services/videoFallback.ts` 硬兜底分支
`if (now - startedAt >= thresholds.HARD_TIMEOUT_MS)` 缺少 `state !==
'streaming'` 守卫。该分支注释明示原意只针对「无论如何未出画面」场景
（旧实现「进入 streaming 即取消」）；方案 19 实施项 2 联动抬高
HARD_TIMEOUT 至 17s 后，健康流从 h264StartedAt 起 17s 必被误判。
现有单测（videoFallback.test.ts）仅锁定「streaming 但 lastFrameTime=0」
异常场景走 timeout，未覆盖「健康 streaming + 帧持续 + 超时」的正常场景，
故缺陷未被拦截。

**证据链**：600s 观察回退日志 30 条 reason 全部为 timeout（无 stalled）；
截图差分仅状态栏时钟变化（35s 间隔 59 像素 / 0.01%）；后端同期 0 保活、
0 stall、持续 au_size 发帧；WS 包计数 H/S 两段均持续收帧；第二轮 H 段 26s
恰为 restarting 宽限（t+29 码率降档 → 宽限至 t+44）罩住、宽限结束 0.6s 即
回退，第三/四轮 H=17s 精确吻合硬兜底公式。

**修复建议**（另行立项，验证阶段不改代码）：给硬兜底分支补
`state !== 'streaming'` 守卫（与 no-stream 分支同款守卫），并补
「健康 streaming + 帧持续 + now>HARD_TIMEOUT 不触发回退」单测锁定。

## 其他观察项

- **保活 RESET 在 .25/.18 从未触发**（`idle_reset_video_sent`=0）：两台设备
  静态画面仍持续产出真实帧（.25 状态栏时钟、.18 近空帧），空闲未达 5s。
  保活触发链本身已由验证 3 卡死注入实测（注入后 6.0s 发出 RESET）
  + 早期真机探针脚本（STOP 编码线程后 8.0s 发 RESET → 8.2s 新 SESSION/CONFIG
  → 9.0s 恢复）证实正常。
- **.18「0.4fps 故障型」判定已作废**：本次抓包 10.16fps 持续出帧，故障链
  未复现；此前「间歇冻结」观察可能被 1a 缺陷主导的呼吸回退干扰。1a
  修复后需复检 .18 真实断流行为。
  **复检（2026-09-23，方案 20 修复后）**：600s 观察 3.87fps 持续出帧、
  0 error/0 stalled、最大帧间隔 6.21s（保活 RESET 补齐）——真实出帧形态
  为「突发 + ~6s 静默」节律（与 .25 的 ~3s 突发同族），**「0.4fps 故障型」
  定性不成立**，原判定源于 1a 呼吸回退的观察干扰。
- **6c 竞争窗实测**：gap=1 瞬断下必现旧流 teardown 未完成（保活帧等待
  ≤5s > 3s 收尾窗），新流 adb forward 被拒一次；前端指数退避 1s 后重试
  即恢复，行为与终审预期完全一致。
- **观测口径**：带宽 33.8kbps 为静止画面（含状态栏时钟变化）下自发产帧
  流量；保活设计理论 37kbps（23KB IDR@5s）在本设备上因子发 4fps 而未达
  到其触发条件。
