# 方案 57：视频流黑边检测裁剪充满渲染方案（设计留档，暂缓实施）

> 状态：**设计记录，暂不实施**（2026-11-02 用户拍板：此种设备情况少见，先记录；v0.7.17 按现有包发布）。
> 触发：v0.7.17 验证期 .16（RK3576 餐饮 POS）反馈「旋转后没有全屏」——方案 56 的 CSS 旋转对这类设备无效，根因在源流侧。

## 1. 根因结论（四路采样实证，2026-11-02）

.16 面板**物理倒装**：`dumpsys display` 内置屏 displayId 0 逻辑 1280×800 rotation 0，但 `installOrientation=ROTATION_270`。`screencap`（SurfaceFlinger 最终合成输出）**正立满幅正常**；但 scrcpy 编码器的虚拟显示镜像**不继承面板 installOrientation 补偿**，对已旋转补偿的内容再做一次 90° 变换 + contain 缩放——**旋转与黑边被烧进码流本身**。

四路 `capture_orientation` 采样（throwaway 探针 `logs/probe_16_co.py` 各采 40 帧 + 无头 Chrome WebCodecs 解首帧，截图留档 `logs/probe_frame_{off,90,180,270}.png`）：

| capture_orientation | 编码帧 | 首帧实况 |
|---|---|---|
| 不传（生产现状） | 1280×800 横 | 内容横躺 90°、中央竖条 ~466×749、左右黑边 |
| 90 | 800×1280 竖 | 内容正立、满宽、高仅 ~500，上下黑边 ~61% |
| 180 | 1280×800 横 | 内容横躺（反向）、竖条、左右黑边 |
| 270 | 800×1280 竖 | 内容倒立、上下黑边 |

**结论**：`capture_orientation` 任一值都只改变"坏框"的摆放角度，无法去掉已烧进流的黑边；前端 CSS 旋转（方案 56）同样无能为力。**后端参数层面无解**，须渲染侧裁剪。

## 2. 设计方案（前端解码侧"黑边裁剪充满"）

**核心思路**：黑边烧进源流 → 在 WebCodecs 解码渲染时把内容区裁出来放大铺满播放器区域。设备无关，对所有非常规装机屏（倒装/异形/多屏镜像异常）通用。后端、协议、起流参数零改动。

### 2.1 内容区检测

- 解码帧先画到离屏 canvas（现有渲染路径即如此），对帧做**低频黑边扫描**：非播放每一帧都扫，仅在新流会话开始 + 每 N 秒（建议 2s）或检测到黑边比例突变时，取当前帧降采样（如 64×40）扫描，找上下左右连续暗行/暗列边界（亮度阈值建议 ≤8/255，允许水印/状态条场景用"最大连续暗带"而非硬阈值）。
- 检测结果 `cropRect{x,y,w,h}` 缓存复用；会话结束（restart/切换设备）清空。
- 静止画面黑边检测零成本；运动画面暗带误判风险由"比例变化需连续 2 次一致才更新"抑制。

### 2.2 渲染与交互打通

- canvas 绘制改 `drawImage(src, cropRect → 铺满目标)`，与方案 56 旋转角合成：先按 rotation 交换盒，再 contain/cover 适配容器——**裁剪开启后旋转语义变为"内容旋转"，.16 类设备预期选 90 即正立满屏**（检测器裁掉上下黑边后内容 800×500 横条，用户旋转 90° 变竖屏容器 cover 充满）。
- 触摸/键盘坐标反变换（`inputController.setDisplayRotation` 链）须叠加 cropRect 映射：`设备坐标 = cropRect.origin + 归一化坐标 × cropRect.size`，再走既有旋转反变换。
- UI：工具栏加「裁剪黑边」开关（默认开 or 默认关待拍板——建议默认开但检测仅对"黑边占比 >10%"的流生效，正常设备零影响）；徽标显示当前裁剪比例。

### 2.3 边界与风险

- **真黑内容误裁**（全屏黑视频/暗场景）：阈值 + "内容带恰好等于整帧则视为无黑边"；黑边须四边之一为连续暗带才裁。
- **状态栏/水印贴边**：暗带扫描按"连续"判定，非全暗不裁。
- RK 平台多屏虚屏（displayId 2/23）行为随 scrcpy server 版本可能漂移——升级 scrcpy 时回归 .16。
- 性能：降采样扫描单帧 <1ms，无感。
