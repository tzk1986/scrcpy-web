# 方案 16：设备连接可达性预检优化

- 日期：2026-09-18
- 状态：设计中（待评审），评审通过后实施
- 关联：[02-设备管理服务](./02-设备管理服务.md)、[10-集成测试与部署](./10-集成测试与部署.md)

## 一、问题分析

### 1.1 现象

在「添加设备」对话框输入一个**不可达**的 IP（设备已关机、IP 写错、不在同一网段、
防火墙静默丢包）后点击「连接」，前端要等待约 **21~30 秒**才失败；点「断开」同理。
用户在整个等待期间得不到任何反馈，只能看到按钮转圈。

### 1.2 现状链路走查

连接链路（自上而下）：

| 层 | 位置 | 行为 |
|----|------|------|
| 前端视图 | `frontend/src/views/Dashboard.vue:209-226` | `handleConnect` → store → 错误时只取 `(e as Error).message` |
| 前端 store | `frontend/src/stores/device.ts:75-89` | 成功后固定等 1s 再刷新列表 |
| 前端服务 | `frontend/src/services/api.ts:22,65-70` | axios 全局 `timeout: 30000` |
| 接口层 | `backend/app/interfaces/http/devices.py:121-140` | `POST /api/devices/connect?ip&port` → `service.connect_tcp` |
| 应用层 | `backend/app/application/device_service.py:150-168` | `adb.connect_tcp` → `get_device_info` → `repo.save` |
| 基础设施 | `backend/app/infrastructure/adb/cli.py:274-302` | `adb connect ip:port`，判 `"connected" in output` |
| 基础设施 | `backend/app/infrastructure/adb/cli.py:50-95` | `_run` 用 `settings().adb.timeout`（默认 **30s**，`config/base.yaml:19`）做 `wait_for` 兜底 |

断开链路同理：`devices.py:143-163` → `device_service.py:170-181` →
`cli.py:304-320`（`adb disconnect`，`AdbError` 被捕获后仅告警，最终仍返回成功）。

错误映射：`AdbError`（`backend/app/core/exceptions.py:61-65`）经
`openscrcpy_exception_handler`（同文件 72-77 行）统一转为
HTTP 400 `{"error": {"code": "ADB_ERROR", "message": ...}}`。

### 1.3 根因

1. **主因（耗时）**：`adb connect` 对「静默不可达」主机的 TCP 握手要等 Windows
   SYN 重传阶梯（约 21s 起步，视协议栈参数可更长），整个调用被
   `adb.timeout = 30s` 兜底。即：不可达场景的连接耗时 ≈ 21~30s。
   `adb connect` 自身没有可用的短超时参数，超时只发生在「命令级」而非「连接级」。
2. **次因（体验）**：后端其实返回了结构化的 400 错误体（含 `message`），但
   `Dashboard.vue:221,235` 只取 `(e as Error).message`——axios 抛出的
   `Error.message` 是 `"Request failed with status code 400"`，真正的原因被丢弃。
3. **断开阻塞**：对失效 transport 执行 `adb disconnect` 会触发 adb server 侧清理等待，
   同样被 30s 兜底；虽然最终吞掉错误返回成功（`cli.py:318-320`），但用户已白等。

### 1.4 影响面

- 仅涉及「TCP/IP 连接与断开」两条路径；USB 设备、其余 ADB 命令（install/shell/
  截图等）不受影响。
- 附带修复一处既有缺陷：`list_devices` 在一台掉线设备（表项仍为 `device` 状态）存在时
  整个列表接口 400（见 2.3 残留窗口）。
- 现有测试 `tests/infrastructure/test_adb_cli.py::TestTcpConnection`（3 例）会受实现
  变更影响，需同步调整（见 4.2）。

## 二、方案设计

### 2.1 总体思路

在调用 `adb connect` / `adb disconnect` **之前**，先做一次纯 TCP 可达性预检
（`asyncio.open_connection`，超时默认 1.5s，可配置）：

- **连接**：预检不过 → 立即抛 `DeviceUnreachableError`（HTTP 400，
  code=`DEVICE_UNREACHABLE`，附中文原因），前端直接弹出提示；预检通过 → 走原
  `adb connect` 流程。
- **断开**：预检不过 → **跳过** `adb disconnect`（该调用在目标不可达时纯属无谓等待），
  直接返回，由应用层继续 `repo.delete` 并返回成功；预检通过 → 走原流程。

预检只验证「host:port 能否建立 TCP 连接」，不验证对端是否为 adb——这是快速排除
「不可达」这一最大耗时来源的最低成本检查；端口开放但非 adb 的误连场景仍由原
`adb connect` 快速失败兜底，行为与现状一致。

### 2.2 连接（connect）时序

```
POST /api/devices/connect
  └─ DeviceService.connect_tcp
       └─ AdbCliDriver.connect_tcp
            ├─ probe_tcp(ip, port, 1.5s)          # 新增预检
            │    ├─ 不可达 → DeviceUnreachableError → 400 DEVICE_UNREACHABLE（总耗时 ≤ ~1.6s）
            │    └─ 可达   ↓
            ├─ adb connect ip:port                # 原逻辑
            ├─ get_device_info / repo.save
            └─ 200 {"success": true, "device_id": ...}
```

### 2.3 断开（disconnect）时序

```
POST /api/devices/{device_id}/disconnect
  └─ DeviceService.disconnect_tcp
       └─ AdbCliDriver.disconnect_tcp
            ├─ probe_tcp(ip, port, 1.5s)          # 新增预检
            │    ├─ 不可达 → log + 直接 return     # 跳过 adb disconnect（避免 30s 等待）
            │    └─ 可达   → adb disconnect       # 原逻辑
       └─ repo.delete(device_id)                   # 继续执行，接口仍返回 200
```

「断开」的语义是「从本平台移除该设备」，目标不可达时清理 adb 侧 transport 没有实际
收益，跳过是安全的；`adb server` 后续会自行清理失效表项，且离线表项不会污染设备
列表（`list_devices` 只保留含 `"device"` 状态的行，`cli.py:126`）。

**残留窗口（走查补充）**：adb 察觉设备掉线前，表项可能仍处于 `device` 状态（此时过滤
不住），而 `DeviceService.list_devices` 对该表项执行 `get_device_info` 会抛 `AdbError`
并让**整个列表接口 400**——这是既有缺陷（任何「设备掉线未察觉」时刻都会触发），但跳过
`adb disconnect` 会让该窗口更常被走到。为此本方案附带两处小加固：

- 后端：`list_devices` 对单个设备信息获取失败改为跳过 + 告警（与 `_refresh_loop`
  既有的逐设备 `try/except` 模式一致），不再让一台掉线设备拖垮整个列表接口。
- 前端：断开成功后先把该行从本地列表移除再做 `fetchDevices` 重同步（乐观更新），
  保证「直接中断」在 UI 上立即可见，即使列表请求瞬时失败也不会让行残留。

### 2.4 预检实现（新建 `backend/app/infrastructure/adb/reachability.py`）

```python
"""
设备可达性预检
===============

层：基础设施 → ADB。

在调用 adb connect / adb disconnect 之前，以纯 TCP 探测判断 host:port
能否建立连接，避免 adb 在「静默不可达」主机上等待 SYN 重传阶梯 + 命令级超时。
"""

import asyncio
import socket

from app.core.exceptions import DeviceUnreachableError
from app.core.logging import get_logger

logger = get_logger(__name__)


async def probe_tcp(host: str, port: int, timeout: float) -> None:
    """
    探测 host:port 能否建立 TCP 连接。

    成功返回 None；失败抛出 DeviceUnreachableError（message 含中文原因）。
    仅做 TCP 层探测，不验证对端协议。
    """
    try:
        _, writer = await asyncio.wait_for(
            asyncio.open_connection(host, port), timeout=timeout
        )
    except asyncio.TimeoutError:
        logger.warning("probe_timeout", host=host, port=port, timeout=timeout)
        raise DeviceUnreachableError(
            host, port, f"{timeout} 秒内无响应（连接超时），请检查设备是否在线、IP 与端口是否正确"
        )
    except ConnectionRefusedError:
        logger.warning("probe_refused", host=host, port=port)
        raise DeviceUnreachableError(
            host, port, f"连接被拒绝，端口 {port} 未开放（设备可能未开启无线调试或端口不同）"
        )
    except socket.gaierror:
        logger.warning("probe_dns_failed", host=host)
        raise DeviceUnreachableError(host, port, f"无法解析主机名：{host}")
    except OSError as e:
        logger.warning("probe_os_error", host=host, port=port, error=str(e))
        raise DeviceUnreachableError(host, port, f"网络不可达：{e}")

    writer.close()
    try:
        await writer.wait_closed()
    except OSError:
        # 对端 RST 竞态：连接已建立即判定可达，关闭阶段的异常不影响结论
        pass
```

### 2.5 配置项与错误码

`config/base.yaml`（adb 节点）：

```yaml
adb:
  path: adb
  timeout: 30
  probe_timeout: 1.5   # TCP 可达性预检超时（秒），仅用于 connect/disconnect 前置探测
  reconnect_interval: 5
```

`config/settings.py` `AdbConfig`（36-48 行）新增字段（yaml 值经
`Settings(**config)` 自动注入，与 `timeout` 同机制）：

```python
probe_timeout: float = 1.5
```

超时取值依据：局域网 TCP 建连典型 < 10ms；1.5s 覆盖弱 Wi-Fi 的多次重试，
同时把「静默不可达」的失败耗时从 21~30s 压到 ≤ 1.6s。`ConnectionRefused` 是
即时返回的，不耗满超时。

新增异常 `backend/app/core/exceptions.py`：

```python
class DeviceUnreachableError(OpenScrcpyException):
    """TCP 可达性预检失败：目标 host:port 无法建立连接。"""

    def __init__(self, host: str, port: int, reason: str):
        super().__init__(f"设备 {host}:{port} 不可达：{reason}", code="DEVICE_UNREACHABLE")
```

经既有 `openscrcpy_exception_handler` 转 HTTP 400
`{"error": {"code": "DEVICE_UNREACHABLE", "message": "设备 ... 不可达：..."}}`。

> 设计决策：
> 1. 该异常的 message 直接采用中文。项目其他领域异常消息为英文（面向日志），
>    但本错误的首要用例就是「展示给最终用户」（前端 ElMessage 直显 message），
>    故按 UX 载体处理。如评审不认可，可改为英文 message + 前端按 code 映射中文文案。
> 2. `DeviceUnreachableError` 直接继承 `OpenScrcpyException`，**不**作为 `AdbError` 子类：
>    `AdbError` 的语义是「ADB 子进程非零退出码退出」（见其 docstring），预检失败发生在
>    子进程启动之前，不属于该类；且后端现有 `except AdbError` 仅 cli.py 三处（270/300/318
>    行）且与预检路径不相交，无继承兼容性诉求。

### 2.6 驱动层改动（`backend/app/infrastructure/adb/cli.py`）

`connect_tcp`（274-302 行）在 `adb connect` 前插入预检：

```python
device_id = f"{ip}:{port}"
logger.info("connecting_tcp", ip=ip, port=port)

# 预检：不可达直接快速失败，避免 adb connect 等待 SYN 重传 + 30s 命令超时
await probe_tcp(ip, port, settings().adb.probe_timeout)
```

`disconnect_tcp`（304-320 行）在 `adb disconnect` 前插入预检，失败则跳过：

```python
device_id = f"{ip}:{port}"
logger.info("disconnecting_tcp", ip=ip, port=port)

# 预检：目标不可达时 adb disconnect 会阻塞在失效 transport 清理上且无实际收益，跳过
try:
    await probe_tcp(ip, port, settings().adb.probe_timeout)
except DeviceUnreachableError as e:
    logger.info("tcp_disconnect_skipped_unreachable", device=device_id, reason=e.message)
    return
```

    .response?.data?.error
  return body?.message || (e as Error).message || fallback
}

### 2.8 与四层架构的相容性

- 预检放在**基础设施层**（驱动内部）：`domain/ports.py` 的 `AdbDriver` 协议签名
  不变，接口层零改动；应用层仅 `list_devices` 附带加固（2.3 节），不引入跨层调用与
  新依赖（`asyncio`/`socket` 标准库）。
- 语义上「与设备通信的细节」本就属于驱动职责，与既有 `check_connection`、
  `connect_tcp` 同层内聚；USB 设备路径不经过 `*_tcp` 方法，天然不受影响。

### 2.9 备选方案与取舍（已否决）

| 方案 | 否决理由 |
|------|----------|
| 调小全局 `adb.timeout` | 会波及 install/shell/截图等全部命令；且 adb connect 不可达时仍要耗满新超时，只把 30s 变几秒，远差于 1.5s 预检 |
| 前端用 axios 超时「抢答」 | 掩盖而非解决问题：后端仍白等 21~30s 并占用子进程；且前端拿不到失败原因 |
| 预检放应用层 `DeviceService` | `asyncio.open_connection` 虽属标准库不违层次，但「TCP 探测」是对设备通信方式的实现细节，放驱动层才能让 USB/TCP 差异收敛在基础设施层 |
| 用 ping / ICMP 探测 | Windows 上 ICMP 常需管理员权限且易被防火墙误伤；TCP 探测与真实用途（连 5555 端口）一致性更高 |
| 参数化关闭预检（0=禁用） | YAGNI，出现真实误报需求再加 |
| 断开时后台清理 adb 失效 transport | 收益接近零：offline 表项已被 `list_devices` 过滤、残留窗口已有列表加固 + 乐观移除兜底，adb server 自身也会清理 |

## 五、风险与边界

- **假阴性（误报不可达）**：弱网下建连 > 1.5s 的极端情况会被拦截。此时
  `adb connect` 本身也大概率失败；确需放宽可调 `adb.probe_timeout`。
- **假阳性（端口开放但非 adb）**：预检通过后 `adb connect` 快速失败，行为与现状一致。
- **跳过 `adb disconnect` 的残留**：adb 察觉掉线前可能仍把表项标为 `device`（见 2.3
  残留窗口），以 `list_devices` 跳过加固 + 前端乐观移除兜底；offline 表项不进设备列表
  （`cli.py:126` 过滤），后续对同 ip:port 重连会复用/恢复表项。
- **仅覆盖 TCP 路径**：USB 设备、emulator 等不经过 `*_tcp` 方法，行为不变。
- **未含项**：不做参数化关闭、不做后台 transport 清理、不做 ICMP 探测；连接成功后的
  `get_device_info` 步骤仍受 `adb.timeout` 约束（设备刚连上即掉线的边缘场景），命令面板
  断开失败无提示为既有行为、本次不改。
