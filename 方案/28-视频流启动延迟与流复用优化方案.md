## 1. 现状走查（2026-09-30 核实）

**启动链**（`backend/app/infrastructure/stream/scrcpy.py:142-392`，每次 WS 连接无条件重放）：

1. `push_server()`（scrcpy.py:142-144）——每次 `ScrcpyEncoder.start()` **无条件重推 JAR**（`backend/app/scrcpy/scrcpy-server.jar` → `/data/local/tmp/scrcpy-server.jar`，server_manager.py:67/123-126，注释明言原因：server 退出时自删 JAR，见 E002）。push 常态 0.06~1s、负载时段实测 **10.1s**（E022）
2. adb forward（端口按 device hash 复用，scrcpy.py:136-137）+ `app_process / CLASSPATH=… tunnel_forward=true` 冷启动 + 轮询 stderr 等 `"Device:"`（30×0.1s）
3. 视频 socket（5s 超时）+ 控制 socket（3s）连接与握手 → config 消息 → 首帧

**生命周期**：WS 断开 → `stop_stream()` → `encoder.stop()`（scrcpy.py:771-835：关双 socket → terminate/kill app_process → 清 forward → 清队列）。单客户端设计（stream_service.py:117-125）；码率切换 = 整链路重启（stream_service.py:156-224），**同样重推 JAR**。`ServerManager.ensure_server`（先查后推，server_manager.py:69-101）与 `delete_server`（:212-251）已实现但流链路从不调用。

## 3. 设计决策

| # | 决策 | 说明 |
|---|------|------|
| D1 | **JAR 备份常驻（主案）**：`push_server` 统一入口改造——启动前若设备端 `/data/local/tmp/scrcpy-server.jar.bak` 存在且**大小校验**通过 → `mv` 恢复主 JAR（~0.1s，恒定）；无 bak（或校验失败）才 `adb push`，push 成功后 `cp` 刷新 bak | server 退出自删只删主 JAR，bak 留存——push 只在「首次部署 / JAR 升级 / bak 损坏 / 设备重启清 tmp」时发生。校验失败自动回退 push（E002 教训以显式校验落实）。收益：常态 −0.3~0.8s、**10.1s 级尖峰结构性摘除**（bak 路径与设备负载解耦） |
| ~~D2~~ | ~~server 进程宽限复用~~ **已判死（spike A 组）**：tunnel socket accept-once，客户端断开 → server 退进程 + JAR 自删。不实施，降级只落 D1 | 事实钉死，不猜测不绕行 |
| D3 | **bak 恢复失败自动回退 push**：mv 失败 / 校验不符 / adb 异常 → 走完整 push 路径，不新增错误态 | 复用是优化不是脆弱化 |
| D4 | **码率重启路径自动受益 D1**：仍走整链路重启（ruling 维持），但其 push 入口同样 bak 化 | 不改 restart 事件循环（stream_service.py:156-224） |
| ~~D5~~ | ~~前端 no-stream 宽限 8s→15s~~ **校准降级为不实施（spike C 组）**：常态首帧 p95 3.9s、D1 后最坏 ~4s，8s 阈值安全余量大；误回退闪变窗口由 D1 结构性闭合。前端零改动、blast radius 最小化 | 若 Phase 3 真机见「bak 失效 + 负载」罕见组合触发闪变，再立窄补丁 |
| D6 | **测量锚**：spike 用 WS 客户端计时（connect→config→首帧）+ 裸协议探测，生产零埋点 | 已由 Phase 0 履行 |

### Phase 1 — TDD 后端（单任务）

**任务 1：`backend/app/infrastructure/stream/server_manager.py` `push_server` bak 化（D1+D3）**

- push 前：执行 `ls -l {REMOTE_JAR}.bak`，输出含本地 JAR 字节数 → `mv .bak → 主路径` 成功即返回 True（restored）；无 bak / 大小不符 / mv 失败 → `adb push`，成功后 `cp → .bak`（cp 失败不阻塞——下次仍 push 而已）；push 失败仍抛原路径异常
- 测试（`tests/scrcpy/test_server_manager.py` 扩展，TDD RED→GREEN）：
  1. bak 存在且大小吻合 → 仅 mv，无 push 子进程调用
  2. bak 缺失 → push + cp 刷新 bak
  3. bak 大小不符 → push + cp（覆盖损坏 bak）
  4. mv 失败 → 回退 push（D3）
  5. push 失败仍抛异常（既有回归语义保持）

## 6. 风险

- **bak 与 JAR 版本一致性**：JAR 升级需刷新 bak——push 成功后无条件 `cp` 覆盖 + 大小校验（内容一致而大小相同的概率极低，首版不计 md5；升级流程 push 必然触发 cp）
- **设备重启 / tmp 清理**：bak 丢失 → 自动回退 push（D3 天然覆盖）
- **E022 慢 push 根因未查明**：D1 绕开而非治愈——按方案文本如实记录；负载态触发路径（推送大文件/连续实验）由 bak 路径与负载解耦
- **前端闪变残留**：唯一残余触发 = bak 失效 + push 慢 + 冷启动 > 8s 的三重罕见联合；Phase 2 若实测触发再立窄补丁（文档 D5 降级注记）
- **单客户端语义不受影响**：本方案不改 stream_service 结构、不引进程残留（D2 已死），交互面仅 push_server 内部
