## 1. 现状走查（2026-09-30 核实）

**启动链**（`backend/app/infrastructure/stream/scrcpy.py:142-392`，每次 WS 连接无条件重放）：

1. `push_server()`（scrcpy.py:142-144）——每次 `ScrcpyEncoder.start()` **无条件重推 JAR**（`backend/app/scrcpy/scrcpy-server.jar` → `/data/local/tmp/scrcpy-server.jar`，server_manager.py:67/123-126，注释明言原因：server 退出时自删 JAR，见 E002）。push 耗时常态 ~1s、负载时段实测 **10.1s**（E022）
2. adb forward（端口按 device hash 复用，scrcpy.py:136-137）+ `app_process / CLASSPATH=… com.genymobile.scrcpy.Server 4.1 … tunnel_forward=true` 冷启动（~1-2s + 轮询 stderr 等 `"Device:"`，30×0.1s）
3. 视频 socket（5s 超时）+ 控制 socket（3s）连接与握手 → config 消息 → 首帧

**生命周期**：WS 连接（video.py:60-76）→ `stream_service.start_stream`（video.py:143）→ encoder.start；断开 → `stop_stream()` 置 `active_streams=False` → 帧循环退出 → `encoder.stop()`（scrcpy.py:771-835：关双 socket → **terminate/kill app_process（2s 宽限）** → 清 forward → 清队列）。**全链零复用**：adb 新子进程、socket 随 encoder 销毁、server 进程随 stop 被杀。单客户端设计：`start_stream` 检测活跃流等待 3×1s 收尾窗口后拒绝（stream_service.py:117-125）。码率切换 = 「停旧 encoder → 起新 encoder」整链路重启（stream_service.py:156-224），**同样重推 JAR**。

**复用现成结构**：`ServerManager.ensure_server`（先 ls 检查再推，server_manager.py:69-101）与 `delete_server`（:212-251）已实现但流链路**从不调用**；`StreamService` 本身是跨连接单例（已按 device 维护 6 类字典，stream_service.py:68-82）；后端日志已有启动锚点 `pushing_scrcpy_server → scrcpy_server_pushed → starting_scrcpy_server → connecting_to_scrcpy_server → connected_to_scrcpy_server → config_sent`（video.py:137）。

**前端 watchdog**（frontend/src/services/videoFallback.ts）：

- `evaluateH264Fallback` 四类信号：error 立即回退；stalled（出帧后冻结 3s）；timeout（硬兜底 15s，仅未出帧时——方案 20 修复后健康流不受 hard 时钟约束）；no-stream（state ≠ streaming 且 15s… 实际 `NO_STREAM_MS=8000`，:39-43）。`computeFallbackThresholds`（:57-65）与后端 keepalive 联动
- 慢启动时序交叉：首帧 14.1s（push 慢）> no-stream 8s → 先回退截图 → 恢复探测（suspend 期间帧计数）回切 → **闪变**（E022）

## 2. 延迟构成（连接 → 首帧）

| 段 | 当前值 | 说明 | 可消除性 |
|----|----|------|---------|
| Tpush JAR 推送 | 1s~**10.1s** 抖动 | 734KB adb push，设备负载敏感；server 退出自删 JAR 导致每次重推（E002/E022） | **主因**，D1 摘除 |
| Tcold app_process 冷启动 | ~1-2s | RK 设备 Java 进程启动 + 等 `"Device:"` 就绪（30×0.1s 轮询） | D2 可消除（复用窗口内） |
| Thandshake 双 socket 握手 | ~0.5-1s | 视频 5s / 控制 3s 超时，常态快 | 复用窗口内仍有 |
| Tconfig+首帧渲染 | ~0.3-0.5s | config → 解码 → draw | 固定 |
| 前端误回退闪变 | 8s 阈值 vs 慢启动首帧 | no-stream 先于首帧触发 → 截图 → resume 闪变 | D5 消除 |

- 基线：常态首帧 4.3s、慢 push 14.1s（E022 实测）
- D1+D2 后复连场景理论：`0 push + 0 冷启动 + Thandshake + Tconfig` ≈ **1-2s**；冷启动场景（窗口外/首次）：`0 push + Tcold + …` ≈ 2.5-3.5s

## 3. 设计决策

| # | 决策 | 说明 |
|---|------|------|
| D1 | **JAR 备份常驻（主案，不依赖 accept 语义）**：`push_server` 统一入口改造——启动前若设备端 `/data/local/tmp/scrcpy-server.jar.bak` 存在且大小校验通过 → `mv` 恢复主 JAR（设备端内操作，~10ms 级）；无 bak（或校验失败）才 `adb push`，push 成功后 `cp` 刷新 bak | server 退出自删只删主 JAR，bak 留存——adb push 只在「首次部署 / JAR 升级 / bak 损坏 / 设备重启清 tmp」时发生，1-10.1s 抖动从启动链摘除。校验失败自动回退 push（E002 教训「不能假设存在」以显式校验落实） |
| D2 | **server 进程宽限复用（spike 定可行性）**：`encoder.stop()` 拆出 `suspend()` 语义——关双 socket、**保留 app_process 进程**、登记宽限截止；宽限窗口 W=30s（可配置）内重连 start 跳过 push+冷启动直达 socket 连接；到期由 asyncio 回收任务 kill | **可行性前提 = Phase 0 spike 实测**：scrcpy-server v4.1 tunnel_forward 模式下，客户端 socket 断开后 server 是否仍 accept 新连接。若 accept-once（server 随断连退出）→ D2 降级不启用、D1 单独落地，文档如实记录；若可重连 → 首帧复连 ~1-2s |
| D3 | **复用路径失败自动回退完整重启链**：socket 连接/握手任何一步失败（含 E009 编码器已崩导致 server 自退）→ 回退完整 `push→start`，不新增错误态；现有 EncoderStalledError 卡死自愈路径不动 | 复用是优化不是脆弱化：任何不确定都走老路 |
| D4 | **码率重启不纳入复用**（ruling）：adaptive 码率切换仍走 stop+完整 start 老路径 | 码率重启是主动重建且低频；其 push 开销自动受益 D1（每次 push 前 bak 校验/mv）。复用语义与 restart 事件循环（stream_service.py:156-224）解耦，首版不混用 |
| D5 | **前端启动宽限**：`NO_STREAM_MS` 首帧阶段 8s → 15s（= HARD 同值，E022 建议 12-15s 区间上沿）；出帧后判定逻辑不变（stalled 3s 主导；方案 20 修复后的 hard 条件不动，不造呼吸循环） | no-stream 仅在「从未出帧」时触发，8s→15s 的代价是「服务端死透」场景回退迟 7s——可接受（D1/D2 后慢启动 p95 会压进 15s；spike 用实测首帧分布校准终值） |
| D6 | **测量锚**：spike 解析后端既有日志锚分段计时（pushing→pushed→starting→connecting→connected→config_sent），不在生产代码加埋点 | 与方案 27 D6 同原则：先测后改、零生产波及 |

## 4. 实施项

### Phase 0 — spike 可行性钉事实（`tests/manual/spike_stream_reuse.py`，真机 .18）

四组，全部不改生产代码：

- **A. accept 语义探测（D2 生死）**：起 server → 连接视频/控制 socket → 模拟客户端断开（关 socket）→ 观察 server 进程存活与监听 → 再连观察是否成功。分「正常断开」与「异常断开（RST）」两亚组。判定：可重连 → D2 启用；accept-once → D2 降级
- **B. JAR bak 链路**：`adb shell cp/mv/ls` 在 `/data/local/tmp` 的耗时实测（cp 734KB、mv 同盘）；`ls -l` 大小校验；无 bak / 大小不符 / 设备重启（模拟：`rm` 后走 push 路径）各一遍
- **C. 启动段基线**：N=10 完整连接（WS 连接→首帧）分段直方图（日志锚差），另尝试复现负载时段慢 push（并发 adb 操作加压）钉 Tpush 分布
- **D. 首帧 p95**：C 组数据推前端宽限终值（若 p95 ≤ 13s 则 15s 宽限稳；若 > 13s 再议）

### Phase 1 — TDD 后端（每任务 RED→GREEN→提交）

**任务 1：`backend/app/infrastructure/stream/server_manager.py` `push_server` bak 化（D1）**

- push 前：`ls -l /data/local/tmp/scrcpy-server.jar.bak` 存在且大小 == 本地 JAR 大小 → `mv .bak 主路径` 并返回「restored」；否则 `adb push` 后 `cp 主路径 .bak`
- 测试（`tests/scrcpy/test_server_manager.py` 扩展）：bak 存在且大小对 → mv 无 push；bak 缺失/大小不符 → push + cp 刷新；push 失败仍抛原异常（回归既有 `test_start_raises_when_push_server_fails` 语义）

**任务 2：`backend/app/infrastructure/stream/scrcpy.py` suspend/复用快路径（D2，spike A 组通过才做）**

- `stop()` 拆 `_release_sockets()` 与进程终止；新增 `suspend()`（`_release_sockets()` + 保留进程 + 记录 suspend 时刻）；新增 `resume_tunnel()` 快路径（跳过 push/app_process，直接 forward + 双 socket 连接 + 握手）；启动前检测「同 device 存活宽限进程」→ 走快路径；快路径任一步失败 → 完整 `start()` 重建（D3）
- 测试（`tests/scrcpy/test_scrcpy_encoder.py` 扩展）：suspend 不杀进程不断 forward 语义断言；快路径跳过 push/start 的 mock 调用断言；快路径 socket 失败 → 回退完整链；窗口到期回收 kill

**任务 3：`backend/app/application/stream_service.py` 接线（D2，同任务 2 门槛）**

- `stop_stream` 参数区分「宽限 suspend」与「硬停」（码率重启走硬停，D4）；宽限窗口 W 与到期回收任务；重连 `start_stream` 检测宽限进程可用 → 复用
- 测试（`tests/application/` 扩展）：宽限窗口内重连不发第二次 push（沿用 mock encoder 断言）；窗口外重连走完整链；码率重启路径仍硬停（无回归）

### Phase 2 — TDD 前端（D5）

**任务 4：`frontend/src/services/videoFallback.ts` 启动宽限**

- `FALLBACK_THRESHOLDS.NO_STREAM_MS` 8000 → 15000；`computeFallbackThresholds` keepalive 联动同步（NO_STREAM ≥ STALL+2000 单调不变）
- 测试（`videoFallback.test.ts` 扩展）：未出帧 10s 不触发 no-stream（旧版 8s 触发）；15s 触发；出帧后 stalled 3s 语义不动；keepalive 联动回归全绿

### Phase 3 — 真机复测收口

- 用 Phase 0 同脚本连/断/重连循环（N=10），对比基线：常态首帧、复连首帧（D2 通过时）、窗口外冷启动首帧（D1 单飞收益）
- 慢 push 场景隔离验证：负载加压下连接首帧分布（D1 后 push 不再入链）
- 无闪变验证：慢启动场景 no-stream 误回退 0 次
- 回归：码率切换（D4 路径）、卡死自愈（E009 模拟）、e2e `video-stream.spec.ts` + `stream-stability-19` + `screenshot-fallback` 跑通

## 6. 风险

- **宽限窗口内进程残留**（D2）：RK 设备 app_process 挂 30s 的资源占用 + 编码器持有——spike A 组顺带观测 CPU；W 值以实测校准（过长残留、过短失复用）
- **E009 编码器崩溃**：server 自退 → 复用窗口内重连必失败 → D3 回退完整链兜底（回退本身含 push，延迟退回基线，但不会坏）
- **bak 与 JAR 版本一致性**：JAR 升级需刷新 bak——大小校验 + push 成功后无条件 cp 覆盖；大小碰巧一致而内容不同的概率极低（可加 md5 校验，spike B 组评估成本后定）
- **设备重启 / tmp 清理**：bak 丢失 → 自动回退 push（D1 校验天然覆盖）
- **单客户端语义与复用交互**：215 行的 3×1s 收尾等待窗口与宽限窗口并存，需防「宽限进程被误判为活跃流」——stream_service 接线时用 suspend 时刻与 active_streams 分离管理
- **前端宽限与方案 20 修复冲突**：hard 条件（仅未出帧触发）不动，只调 no-stream 首帧阶段阈值——呼吸循环不可能复现（出帧后 stalled 主导，no-stream 不参与）
