- 关联：方案 16（设备可达性预检）、方案 23（停机清理）、
  `backend/app/application/device_service.py`（list_devices / _refresh_loop）、

## 一、问题（现象与证据）

用户报告：**「我只是关闭（断开）其中一个设备的连接，不应该需要这么长时间」**
——在 Dashboard 点某台设备「断开」后按钮长时间转圈；进入/返回连接页面
（设备列表）同样要等很久。

实测证据链（2026-10-08，0.7.2 打包版 + .18/.25/.33 现场）：

| 测量 | 结果 | 说明 |
|------|------|------|
| `adb -s .18 shell getprop ro.product.model` | 0.148s | 正常设备 |
| `adb -s .25 shell getprop ro.product.model` | 0.171s | 正常设备 |
| `adb -s .33 shell getprop ro.product.model` | **3m45.5s** | .33 当前 adb 管道拥塞（开发占用 + push 循环争抢） |
| `GET /api/devices`（不动它，只读列表） | **32.197s** | 与「串行模型」完全吻合：adb devices 快 + .18/.25 各 ~0.7s + .33 卡 30s 超时 |
| 后端日志 | `adb_command_timeout` (30s) → `device_info_failed` | .33 的 getprop 在后端 30s 超时被 kill |

**注意**：根因与 .33 无关——.33 只是把「单台设备 adb 拥塞」这一病态场景
带到了现场。任何设备（USB 慢、网络抖、设备忙）都会触发同样后果。用户要求
在 .18/.25 上验证修复，验收口径 = 「.33 卡在场时，对 .18/.25 的断开/列表
操作不再被拖」。

### 1.1 设备为什么会慢（用户提问调研）

「单条 getprop 卡到分钟级」的真实来源在设备侧与 adb 管道竞争，观测与
归因候选（诚实标注，均为现场证据支持或明确推测）：

| 候选 | 支持证据 | 判定 |
|------|----------|------|
| 设备端 adbd/系统负载高 | .33 为 kiosk 且正被开发者占用；历史上该设备曾 offline 三连、SIGABRT 互踩 | 主因候选 |
| adb 管道争抢（同设备并发操作排队） | 现场：旧浏览器 tab 的 push_server_timeout 循环（每 30-40s 一轮 push+重连）+ 开发者自有工具同时用 adb；adb 单管道内命令排队 | 放大器 |
| push 超时 → 重连 → 再 push 的恶性循环 | 日志 `push_server_timeout` 周期复现；失败后前端自动重连立即再 push | 放大器 |
| WiFi/网络层抖动 | .18/.25 同网段毫秒级响应，仅 .33 卡 | 可排除为主因 |

结论：设备侧的慢（adbd 负载、CPU 竞争）本仓库不可控；本仓库能做两件事
——**(1) 不被它拖死**（D1-D6：并发、短超时、冷却、前端解阻塞）；
**(2) 把「慢」明确告诉用户**（D7：列表红灯标识），让用户知道「这不是
界面卡了，是这台设备当前响应慢」，并可据此决定是否断开/排查。

## 二、根因（代码定位）

### 2.1 列表查询串行 + 全命令 30s 超时（后端）

`DeviceService.list_devices()`（device_service.py:55-79）：

```python
device_ids = await self.adb.list_devices()          # adb devices，快（~0.1s）
for device_id in device_ids:                        # ← 逐台串行
    info = await self.adb.get_device_info(device_id)  # ← 每台 4 条串行 shell
```

`get_device_info`（cli.py:142-170）对每台设备串行执行 4 条命令：
`getprop model` → `getprop version` → `wm size` → `dumpsys battery`，
单条超时取自 `settings().adb.timeout`（config/base.yaml:21 = **30s**）。

后果：**N 台设备 = 4N 条串行命令**；任一设备卡顿即整表阻塞，且超时值
按「长命令」（install/screenshot）设计，对 getprop 这类快命令过大。

### 2.2 前端把「列表刷新」串进用户操作的关键路径（前端）

- `stores/device.ts` `disconnectDevice`：断开成功后 `await fetchDevices()`
  → **断开按钮的转圈一直持续到 32s 的列表响应返回**（用户感知：「关闭
  一个连接要好久」）；
- `connectDevice`：连接成功后 `await fetchDevices()`，同样被拖；
- `Dashboard.vue` onMounted：`await store.fetchDevices()` 后才 `startSSE()`
  ——列表慢时 SSE（实时事件）也推迟启动。

### 2.3 信息查询失败的既有权衡

现状 `list_devices` 对查询失败的设备 **skip**（continue，device_service.py:76）
——设备从列表消失。但设备仍在 `adb devices` 名单里（在线），
把它藏掉会让用户无法对它操作（无法断开），且列表闪没难以理解。

## 三、设计（D1-D6 后端并发+短超时+冷却、前端解阻塞；D7 慢设备红灯标识）

### D1 列表查询并发化

`list_devices` 用 `asyncio.gather` 并发所有设备的详情查询，总时长从
「Σ 各设备」变为「max(单设备)」。细节：

- 设备级信号量上限 8 由查询 task 自身获取（`_fetch_info` 内
  `async with semaphore`，同 batch_install 先例，device_service.py:127）
  ——等待复用已有 task 的调用方不占额度，信号量约束的是真实 adb 并发；
- 单台设备的意外异常在内层捕获（不掀翻整表，同 `install_one` 先例），
  统一交给 D3/D4/D5 处理。

### D2 设备信息快命令短超时 + 并发（单设备上界 5s）

- `_run_serial` / `_get_battery_level` 增加 `timeout` 透传参数；
  `get_device_info` 的 4 条命令（getprop model / getprop version /
  wm size / dumpsys battery）统一使用 `_INFO_CMD_TIMEOUT = 5`（秒）
  ——实测正常设备单条 0.15-0.2s，5s 对慢设备仍有裕量；诊断类命令
  （install/screenshot 等）继续用配置的 30s。
- 4 条命令相互独立，**由串行改为 `asyncio.gather(...,
  return_exceptions=True)` 并发**——`return_exceptions=True` 必不可少：
  否则首个异常会取消其余命令，`_run` 的超时 kill 收尾路径
  （cli.py:99-102）被跳过 → 孤儿 adb 进程。结果中任一为异常则 raise
  首个异常（维持现状「任一步失败 = 整台信息获取失败」语义，由 D3 兜底）。

效果：单设备信息查询总上界 = **max(4 条) ≤ 5s**（若维持串行则为
4×5 = 20s，不满足 §五 验收）——「整台卡死」（首命令超时）与「部分慢」
（若干命令各慢数秒）两个形态都被压入 5s。

### D3 失败设备兜底保留（语义变更：skip → 保留）

查询失败的设备不再从列表消失：
- repo 有缓存信息 → 返回缓存（battery 等可能陈旧，可接受；**不**回写
  覆盖，避免好数据被坏数据污染）；
- 无缓存（新设备首查失败）→ 返回最小信息（model/os 空、分辨率 0x0、
  battery 0、status=online）。

设备保持在列表中可见、可断开——修掉「在线设备被藏掉」的隐性缺陷。

已知副作用：新设备首查失败（不落库）时，列表可见但点「连接」进详情页
（GET /api/devices/{id} 走 repo）会 404——前端 DeviceDetail 已对该场景
优雅降级（catch 后默认值渲染，不依赖设备信息），属可接受的语义不对称，
记录在案以免日后误当缺陷排查。

### D4 失败设备冷却（负缓存 30s）

查询失败 → 记 `_info_cooldown[device_id] = time.monotonic() + 30`；
冷却期内该设备直接走 D3 兜底**不发起 adb 查询**；查询成功清除冷却；
到期后自动重试。冷却的读写在查询 task（D5 `_fetch_info`）内部完成
——置位与 task 完成原子，不存在「task 已 done、冷却未置位」窗口。
效果：卡设备在场时，列表首次付一次短超时代价（≤5s），其后 30s 内所有
列表请求秒回；30s 重试一次，骚扰频率低（对设备友好）。

`disconnect_tcp` 时清理该设备的冷却与任务表条目（防已断开设备在
`_info_cooldown` / `_info_tasks` 中残留）。

### D5 同设备查询任务复用

并发列表请求（用户手动刷新 + 断开/连接后的静默重拉 + 重进页面叠加）
对同一设备复用同一 `asyncio.Task`——不重复发起 adb 查询。实现要点：

- 统一入口 `_get_info_cached(device_id) -> DeviceInfo | None`：先查冷却
  （命中 → 直接返回 None 走 D3 兜底）；再查任务表，无任务或任务已
  done → 创建 `_fetch_info` 任务并替换引用（**检查-创建之间不得有
  await**，asyncio 单线程下即为原子）；返回 `await task` 的结果；
- `_fetch_info` 任务内部：信号量 → `get_device_info` → 成功则清冷却、
  `repo.save`、返回 info；失败则记录冷却、返回 None——**异常不出
  task**（不会出现 "Task exception was never retrieved" 噪音），冷却
  置位与结果一并原子落地；
- 等待方（复用任务）不重新获取信号量，只 await 同一 task。

### D6 前端把列表刷新移出用户操作关键路径

- `fetchDevices(opts?: { silent?: boolean })`：silent 时不置列表 loading；
  并加请求代次（generation counter）——响应返回时若代次已过期则丢弃，
  防并发重拉时**慢响应覆盖新状态**（例如把刚本地移除的断开设备复活）；
- `disconnectDevice`：成功后本地移除（已有）+ `void fetchDevices({silent})`
  ——**不 await**，按钮立即恢复；重拉仅作 adb 表残留的兜底同步
  （fetchDevices 内部自然不抛出，无 unhandled rejection 风险）
- `connectDevice`：同上改静默（连接成功对话框立即关闭，设备由后续静默
  重拉补齐；SSE 当前生产无事件流，见「已知现状」）
- Dashboard onMounted：`startSSE()` 提到 fetchDevices 之前（订阅就位
  是未来接线 SSE 的正确顺序，列表慢不推迟事件订阅）

### D7 慢设备列表红灯标识（后端瞬态字段 + 前端红 tag）

D1-D6 解决「不被拖死」，D7 解决「把慢明示给用户」（对应用户诉求：
「是否可以在设备列表页面亮红灯标识，提示用户设备 adb 连接慢」）。

**后端**（`domain/device.py`）：

- `DeviceInfo` 加 `slow: bool = False`（置于 `port` 之后）。
  **瞬态展示字段，不入库**：SQLite `devices` 表 9 列显式映射
  （sqlite.py:553+ save/get 均不涉及该字段）→ **零 migration**；
  从 DB 重建的对象 `slow` 恒为 False（默认值）。
- `list_devices` 兜底路径（D3/D4 触发）对返回对象置 `slow=True`：
  - 有缓存 → `dataclasses.replace(cached, slow=True)`（**不原地赋值**，
    避免污染 repo 返回对象；repo.get 每次重建对象，但 replace 更稳）；
  - 无缓存最小信息对象 → 构造时 `slow=True`。
- 查询成功路径恒为 False（默认值），无需额外代码。
- API 形状：`GET /api/devices` 响应设备对象**新增附加字段** `slow`
  （FastAPI dataclass 序列化自动带出），对旧消费方无破坏。

**前端**：

- `stores/device.ts` `DeviceInfo` interface 加 `slow?: boolean`
  （可选字段，后端旧版本缺省即 undefined → falsy，向后兼容）；
- `Dashboard.vue` 状态列（:66-68）在在线/离线 tag **之后并列**红灯：
  `<el-tag v-if="row.slow" type="danger" size="small">adb 慢</el-tag>`
  ——红灯与状态并列而非替换（「在线」表达连接态，「adb 慢」表达响应
  质量，两个维度独立）；
- 语义：红灯 = 「该设备信息获取失败（最常见原因为 adb 响应慢），当前
  显示的信息可能为缓存或默认值」；查询恢复成功后须**用户手动刷新
  （或重进页面）**才灭灯——当前无自动刷新来源（SSE 无事件、无轮询），
  与亮灯同源（`slow` 随列表响应瞬时生效）。

### 已知现状（评审发现，本方案不改动）

- **`_refresh_loop` 生产未接线**：`DeviceService.start()` 全仓仅测试
  调用，`backend/app/lifecycle.py` 无 device_service 启动——即后台
  轮询与 SSE 事件推送在生产从未发生；`docs/API.md` 中「每 5s 刷新
  循环」的描述与实现不符（本方案顺带修正该文档措辞）。
- **影响**：D4/D5 不依赖 `_refresh_loop`（其面向前端并发请求设计）；
  前端设备增删目前仅依赖手动刷新与操作后的静默重拉。把 loop 接上属
  独立事项（引入每 5s adb 查询与事件流行为），不在本方案范围。
- **SSE payload 不变**：`on_connected` 手写 6 字段（devices.py:85-97）
  不带 `slow`——本次不改（生产无事件来源；且事件语义为「刚查询成功的
  新设备」，`slow` 恒 False 无信息量）。若未来接线 loop，再评估补充。

### 已取消 / 不做

- **列表接口「缓存优先立即返回 + 后台补齐信息」**（方案 B）：收益是
  列表任何情况下 <0.5s，但接口语义变化大（返回值可能缺信息/陈旧）且
  波及前端渲染与全部 e2e 用例；D1-D5 后正常场景 <1s、卡场景首次 ≤5s/
  其余秒回，已覆盖用户痛点，暂不做。若未来设备数增长或验收不达标再议。
- .33 的 push 循环（浏览器旧 tab 自动重连骚扰设备）属现场人为因素，
  请用户关闭对应浏览器页面，不属本方案改动范围。

## 四、测试方向（TDD）

后端（tests/application/test_device_service.py）：

1. **并发生效**：3 台设备 fake `get_device_info` 各慢 0.3s 且记录
   「同时 in-flight 数」——断言峰值 ≥2（串行恒为 1）且总时长 <0.6s；
   顺带断言成功设备 `slow is False`；

5. **任务复用**：并发两个 `list_devices`（gather），同设备的
   `get_device_info` 只被调用一次（call_count == 设备数）；
6. **connect_tcp 容忍 info 失败**：mock `get_device_info` 抛 AdbError →
   `connect_tcp` 仍返回 device_id、不调用 repo.save、不上抛（D 补充见

## 七、风险与边界

| 风险 | 缓解 |
|------|------|
| 语义变更（skip→保留）影响其他消费方 | 消费方即前端表格与 e2e fixtures——**e2e fixtures 必须过滤 `!d.slow`**（兜底条目 status=online 且 model 空，不过滤会被 `online[0]` 选中当测试设备），已列入实施范围；现状「在线设备被藏掉」本身是缺陷 |
| 冷却期内设备信息陈旧（battery 等） | 30s 后自动重试；用户手动「刷新」随时可用；battery 陈旧属可接受代价 |
| 5s 短超时误杀真慢设备的信息查询 | 正常设备单条实测 0.15-0.2s；kiosk 慢设备最坏仍在秒级，5s 裕量足；若个别设备持续 >5s，表现为该设备信息走缓存兜底（好于全表 32s） |
| D7 红灯短暂误亮（设备偶发抖动 >5s 触发一次兜底） | 红灯语义 = 「信息获取失败，可能为缓存/默认值」而非「故障」；随 D4 冷却存活至少 30s（不闪烁抖动），查询成功且用户手动刷新后灭灯 |
| connect_tcp 行为变化（info 查询失败不再使连接报错） | 语义=「adb connect 成功即成功」；info 由列表兜底补齐——贴合事实（设备确实已连上）；单测锁定（§四 用例 6） |
| 并发查询放大 adb server 负载 | 设备级信号量上限 8 + 每设备 4 条命令并发（瞬时峰值 ≤32 个 adb 子进程；正常设备 <0.2s 全清，且 D4 冷却天然限频）——真机验收佐证 |
| 4 条命令并发取消传播留孤儿 adb 进程 | `gather(return_exceptions=True)` 确保各命令独立走完自身超时 kill 路径（D2）；复用既有 `_run` 收尾逻辑，无新进程管理代码 |
| .33 场景复测口径 | 修复验证只需只读调用；.33 被开发占用期间不主动对其做任何写操作/断连 |
