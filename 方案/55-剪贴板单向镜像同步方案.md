# 方案 55：剪贴板单向镜像同步（设备 → PC）

> 状态：设计拍板（2026-10-30 用户裁定两拍板点），待排期实施　|　提出版本：v0.7.17　|　日期：2026-10-30
> 来源：路线图第 25 项——用户于 v0.7.17 活体验收期授权「要是想做成镜像的话，也可以增加镜像能力」（方案 54 D3 拉取式之上的增量）。
> 不入 v0.7.17 验证包本体；实施另行排期。

## 1. 背景与目标

方案 54 G3 交付的是**拉取式**剪贴板同步（用户显式点按钮取回/写入），`clipboard_autosync=false` 钉死。用户观察「同步不是镜像」并授权增加镜像能力。

**镜像语义（本方案）**：设备侧发生复制时，内容**自动**出现在 PC 系统剪贴板——用户无需任何点击，设备 Ctrl+C 后回 PC 直接 Ctrl+V。QA 场景主价值：设备复制日志/文本 → 立即粘到 PC 备注/工单。

- **G1 设备→PC 单向自动推送**：会话级开关开启后，设备复制 ≤ 约 2s 内同步到 PC 剪贴板（浏览器焦点约束见 §3.4）。
- **G2 拉取式全链保持不动**：现有「取设备剪贴板/取选中文本/粘贴到设备」按钮行为零变化，镜像是叠加态不是替换态。

**非目标（用户已裁定/约束所限）**：
- PC→设备自动推送（拍板点 1：**不需要双向版**）——浏览器无焦点禁读系统剪贴板，感知任意应用内复制做不到；现有 `clipboard_set`/对话框粘贴链路已覆盖该方向的手动场景。
- 起流参数 `clipboard_autosync` 改 true（技术否决，理由见 §2.1）。
- 开关持久化（拍板点 2：默认关 + 会话级，刷新/切页即复位）。

## 2. 调研结论（2026-10-30 上游源码级 + 我方代码级实证）

### 2.1 上游 autosync 不可直接采用（路线否决依据）

留档 `logs/upstream/Controller.java` 实证：

1. **autosync 是设备→PC 单向事件驱动**：`=true` 时服务端注册 `ClipboardManager.addPrimaryClipChangedListener`（L146-161），设备复制即推 `CLIPBOARD` 帧；PC→设备方向服务端无机制（桌面客户端靠 SDL 系统事件，浏览器无等价物）。
2. **启用会破坏我方拉取链**：`getClipboard()`（L687）仅在 `!clipboardAutosync` 时才应答 `GET_CLIPBOARD`（L698-703，注释明确「不重复同步」）——起流参数改 true 后，方案 54 已验收的 `{action:'clipboard_get'}` 应答链失效（reader 侧永远等不到回帧、3s 超时），而该参数起流时钉死、会话中不可切换，**拉取与镜像无法共存于同一参数路线**。
3. **老 ROM listener 可靠性存疑**：验证设备多为 RK/Amlogic 工业盒 A7~A11，shell 身份进程的 `addPrimaryClipChangedListener` 在定制 ROM 上是否触发未证；我方轮询路线直接复用 G3 已真机全通（.25/.22/.20）的 GET 链，兼容性已被实证。
4. **环回是上游承认的真实问题**：服务端用 `isSettingClipboard` AtomicBoolean 抑制「PC 写入触发的设备监听事件」回推（L150-153、L708-710）——我方设计同样必须有防环回（§3.3）。

### 2.2 我方链路：轮询可直接复用现成件，零协议新增（除开关动作）

| 层 | 现状 | 证据 |
|---|---|---|
| 后端拉取原语 | `get_device_clipboard(copy_key, timeout=3s)`：waiters deque FIFO 关联、超时/不可用返回 None、正文不落日志 | `scrcpy.py:726-753` |
| 并发共存 | waiter 按 append 顺序关联应答，设备端每请求回一帧——**轮询与手动 get 并发在途天然安全**，无需额外互斥 | `scrcpy.py:123,736-737` |
| WS 动作分发 | `video.py _handle_input_message` 已有 `clipboard_get/clipboard_set` 分支，会话上下文持有 `websocket`+`device_id`+`stream_service` | `video.py:502-517` |
| 前端消息通道 | `VideoPlayer.vue` 包装 WS 截流 `clipboard/clipboard_error` 交 `inputController.handleClipboardMessage`；单在途仅约束手动请求，push 走独立分支不冲突 | `VideoPlayer.vue:490-502`、`inputController.ts:97-98,486-491` |
| 浏览器写权限 | `navigator.clipboard.writeText()`：安全上下文（本机 http://localhost 满足）+ **document 有焦点即可，无需用户手势**；`readText()` 才需手势+权限（本方案不读 PC 剪贴板，零触碰） | MDN/Chrome 权限模型 |
| Page Visibility | tab 隐藏停用输入逻辑已在方案 17 收口，镜像沿用同一失焦判定面 | `VideoPlayer.vue` 现有 visibilitychange 接链 |

## 3. 方案设计

### 3.1 决策记录

| 决策点 | 裁定 | 依据 |
|---|---|---|
| D1 方向 | 单向设备→PC | 用户拍板 2026-10-30「不需要双向版」；浏览器硬约束 |
| D2 开关 | 默认关 + 会话级（不持久化） | 用户拍板 2026-10-30；覆盖 PC 剪贴板属显式 opt-in 行为 |
| D3 实现路线 | 后端 1s 轮询复用 GET 链，`clipboard_autosync=false` 维持钉死 | §2.1-2/-3：autosync=true 破坏拉取且不可动态切换；轮询链已真机实证 |
| D4 失焦策略 | 失焦期只缓存+徽标，回焦自动补写一次 | 镜像语义完整性的最大化落地；writeText 无焦点必失败 |

### 3.2 后端：会话级镜像轮询 task

- **WS 动作**：`{action:'clipboard_mirror', enabled: true|false}`——`video.py` 会话输入处理新增分支：`enabled=true` 时起 task（已起则幂等），`false` 时 cancel。task 句柄与状态存于该 WS 会话上下文（闭包/局部变量，随 handler 结束自然消亡，**客户端断开即停，无跨会话泄漏**）。
- **轮询循环**：间隔 1s 常量；每轮 `encoder = stream_service.get_encoder(device_id)` 现取句柄（编码器重启/重连后自然跟上新控制 socket），`text = await encoder.get_device_clipboard(copy_key=0)`；`None` 计一次失败不推送；`copy_key=0` 纯读不注入任何按键。
- **变更判定**：与会话内 `last_text` 精确比较，不同才推；首轮读到什么推什么（开启即同步设备当前剪贴板一次——语义直觉）。
- **防环回**：同会话上下文记 `suppressed_text`——本会话 `clipboard_set` 成功后把写入文本记入；轮询读到的 `text == suppressed_text` 时不推送并清空该标记（一次性，之后恢复推送）。对齐上游 `isSettingClipboard` 语义（§2.1-4）。
- **推送帧**：`{type:'clipboard_push', text}`；`logger.debug` 只记长度（既有 E 级约束）。
- **失败收口**：连续 10 次轮询 None（≈10s 控制通道不可用）→ 自停 task 并回 `{type:'clipboard_mirror', enabled:false, reason:'poll_failed'}`，前端开关复位（防设备异常后空转与重连风暴）。

### 3.3 前端：开关 + 焦点写剪贴板

- **UI**：`VideoPlayer.vue` 工具栏「取设备剪贴板」旁增「剪贴板镜像」开关（`el-switch`，`:disabled="!wsConnected"`，默认关；组件卸载/换会话复位=会话级）。`inputController.setClipboardMirror(enabled)` 发 action；`handleClipboardMessage` 扩两类帧：`clipboard_push`（不进手动请求 pending 关联）、`clipboard_mirror`（后端自停通知→开关复位+提示）。
- **写入策略（D4）**：收到 push——
  - `document.hasFocus() && !document.hidden` → `navigator.clipboard.writeText(text)`；成功徽标一闪「已同步 N 字符」；抛错（权限等）→ 转缓存路径。
  - 否则 → 记 `pendingMirrorText`（覆盖式，只留最新）+ 徽标「设备已复制 N 字符，回焦自动同步」。
  - `focus`/`visibilitychange` 事件且开关开且有 `pendingMirrorText` → 补写一次并清缓存。
- **环回**：writeText 写入的文本本就源自设备，无 PC→设备新写入，前端无需再防；后端 §3.2 `suppressed_text` 已覆盖「用户点粘贴到设备后设备侧监听回读」场景。

### 3.4 安全与隐私

- 镜像=显式 opt-in，关=零后台读取设备剪贴板（轮询 task 不存在，非「读了不推」）。
- 正文不入日志（长度 only，沿用方案 54 约束）；WS 明文仅本机回环（M1 已收口）。
- 本方案**从不读 PC 系统剪贴板**（无 readText/权限弹窗），只写——写入范围仅设备侧复制产物，且仅镜像开启期发生。

## 5. 测试与验收

- **后端单测**：action 开/关幂等与断开会话 task 消亡；轮询变更比对（同文不推/异文推）；`suppressed_text` 一次性拦截；连续 10 失败自停 + 通知帧；正文不落日志（caplog 断言长度字段）。
- **前端单测**（jsdom mock `navigator.clipboard` 与 `document.hasFocus`）：push→有焦点 writeText 调用/无焦点走缓存；回焦补写一次即清；`clipboard_push` 不消费 `clipboardPending`（手动在途不受影响）；开关发送 action 且默认关、卸载复位。
- **真机手工判据**：设备端 App 复制→2s 内在 PC 直接 Ctrl+V 可得；开关关→无 push；「粘贴到设备」后设备侧不弹回同文；页面切后台复制→回前台自动补写；shutdown 冒烟无新增 Traceback（分段口径）。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 轮询与手动 get 并发时序（FIFO 错位） | 设备端每请求恰回一帧、waiters 按序关联（§2.2，方案 54 冒烟已含并发项）；单测钉死双在途不乱序 |
| 长会话 1s 轮询流量 | 本机 WS+adb TCP，每轮往返数百 B，静止期设备 GET 即时应答无队列堆积；可接受 |
| 回焦补写覆盖用户在别的 PC 应用刚复制的内容 | 镜像开启的既定语义（D2 显式 opt-in + 徽标可见）；用户可随时关开关，会话级不残留 |
| 老 ROM GET 慢/超时 | 超时 3s 吞轮次即过；连续失败 10 次自停上报，不打断视频流 |
| 剪贴板大文本（MB 级） | 比较为 Python 端字符串等值，无 hash 成本考量必要；WS 单帧承载沿用现链限制，超长实况冒烟记录 |
