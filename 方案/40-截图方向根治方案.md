## 一、现象（用户上报）

| 设备 | 视频流（H264） | 截图/缩略图 |

## 二、根因分析

### 信号源选错：dumpsys input 的 SurfaceOrientation 不是 Display rotation

方案 38 B1 选择 `dumpsys input` 的 `SurfaceOrientation:` 行作为 rotation
信号。调研证明该信号是 **InputFlinger 坐标系方向**（触摸/输入事件映射用），
与 SurfaceFlinger 的 display rotation 是两套语义。

**真值表（六台实证，2026-10-10）**：

| 设备 | dumpsys input SurfaceOrientation（旧信号） | dumpsys display 内置屏 mCurrentOrientation（真信号） | 正确补偿 |
|------|------|------|------|
| .19 | 1 | **0** | 不转 |
| .13 | **两行：2 与 0**（多条目噪声，首行命中错值） | **0**（且外接 HDMI 屏 rotation=2，非默认屏） | 不转 |
| .24 | 2 | **2** | ROTATE_180 ✓（方案 38 目检已验） |
| .18 | 0 | 0 | 不转 |
| .25 | 0 | 0 | 不转 |
| .16 | 0 | 0 | 不转 |

**证据链**：
1. `.13 dumpsys input` 输出两行 `SurfaceOrientation: 2` 与 `0`，
   现有解析取首行 → 命中 2 → 误施 ROTATE_180；
2. `.19` 单行 `SurfaceOrientation: 1` → 误施 ROTATE_270，后端实测把
   1280×800 横帧硬转成 800×1280 竖图（X-Rotation=1）；
3. `.24` 的 input 值 2 与 display 值 2 **恰好重合**——方案 38 唯一「蒙对」
   的设备，掩盖了信号源错误；
4. 程序化方向判定（四边亮度条带分析）：.13 raw 帧顶部状态栏极暗
   （亮度 51.7）位于帧顶，backend 图中翻到底部——raw 帧本身方向正；
5. 硬件属性旁证：`.19 ro.sf.hwrotation=90`、`.13
   ro.surface_flinger.primary_display_orientation=ORIENTATION_90`——
   车机平台的硬件方向换算已内置于合成链路，screencap 物理帧方向即
   用户所见方向；
6. 用户目视：「视频流中的方向都是正确的」——scrcpy 协议按 display
   rotation 处理，佐证真信号应为 display 语义。

**根因定性**：rotation 信号源选错（input 语义 ≠ display 语义）；
「单信号非 0 即补偿」的判据在 .24/.13 同值异行为（input 值同为 2，
一个该转一个不该转）前失效。

## 三、修复设计（路线 C）

总原则：**视频流抓帧为主（方向天然正，零判据）+ screencap 判据重建
兜底（未观看/未连接场景）**，最小侵入、不破坏方案 29/38 性能特征。

### A. 前端视频流抓帧（主路径）

```
h264VideoStream（frontend/src/services/h264VideoStream.ts）
  渲染循环已把解码帧 drawImage 到渲染 canvas（方向 = 视频流方向 = 正）
    ↓ 新增 captureFrame(): Promise<Blob>
    渲染 canvas → toBlob('image/png')（零额外画布、零新依赖）
    ↓ 消费点 1：DeviceDetail 顶栏新增「截图」按钮
      H264 活跃流 → captureFrame() 直接下载 PNG
      截图模式（无流）→ 回退 api.screenshot（B 修复后方向正）
    ↓ 消费点 2：设备列表缩略图缓存
      观看会话建立（H264 streaming 首帧渲染）后抓帧
      → 写 store.thumbnails[id]（复用既有缩略图结构：
        blob URL + 快照时间 title + TTL 逻辑，方案 36 已有）
      列表页有缓存用缓存；无缓存照旧走 api.screenshot（B 兜底）
```

- 零后端改动、零新依赖；
- 截图按钮无流时的回退文案：「当前无视频流，已回退设备端截图」。

### B. screencap rotation 判据重建（兜底路径）

**B1 信号源换挡（backend/app/infrastructure/adb/cli.py）**：
`get_rotation()` 的命令从 `dumpsys input` 换为 `dumpsys display`，
解析规则：扫描输出中**首个** `mCurrentOrientation=<n>` 行（dumpsys
display 输出按显示器分段，内置默认屏排第一，其后的 mCurrentOrientation
即默认显示器当前值）；解析失败/命令失败/行缺失 → 0（不旋转，既有语义）。

**B2 补偿映射不变**：`{1: ROTATE_270, 2: ROTATE_180, 3: ROTATE_90}`
（方案 38 B4）——真值由 B1 修正后，.19/.13 → 0 不转、.24 → 180° 转、
回归 .18/.25/.16 → 0 不转。

**B3 其余链路零改动**：TTL 30s 缓存（方案 38 B3）、X-Rotation 响应头
（B6）、PNG 后端补偿（B4）、前端 raw 链 180° 像素反转（B5）全部保留——
前端消费的 X-Rotation 值自然变正确。

**性能**：`dumpsys display` 输出与 `dumpsys input` 同量级（十 KB 级），
TTL 缓存下逐帧零成本；spike 补实测耗时记录。

### C. 回退矩阵（最终行为）

| 场景 | 数据源 | 方向保证 |
|------|--------|----------|
| 详情页观看中截图 | 视频流抓帧（A） | 视频流方向天然正 |
| 截图模式截图 | api.screenshot（B） | mCurrentOrientation 判据 |
| 列表缩略图（已观看过） | 流帧缓存（A） | 同上 |
| 列表缩略图（未观看） | api.screenshot（B） | mCurrentOrientation 判据 |
| 调试面板等后端 PNG 消费点 | device_service.screenshot（B） | mCurrentOrientation 判据 |

## 七、风险与已知限制

| 项 | 说明 | 缓解 |
|----|------|------|
| mCurrentOrientation 的动态性 | 反射屏/Presentation（.13 外接 HDMI）场景下默认屏值可能随投屏联动 | spike 观察 .13 双屏段；判据默认屏首段语义与 scrcpy 默认 display 一致 |
| 未观看设备仍依赖 B 判据 | B 判据错误时列表缩略图方向仍可能歪 | 真值表 6/6 与真信号吻合；.24 目检回归兜底 |
| .33 未纳入本档验证 | 用户指示排除 .33（通道不稳） | 判据对 .33 的适配列为已知未验证项；后续通道恢复可补测 |
| 截图模式输入事件的截图仍走 screencap | 方案 27 事件驱动截屏链路无流可抓 | B 判据修正后自然正确，无需额外处理 |
| captureFrame 竞态 | 按钮点击瞬间渲染循环可能未完成最新帧 | toBlob 读渲染 canvas 即时快照，无跨帧竞争；截图模式回退分支兜底 |
