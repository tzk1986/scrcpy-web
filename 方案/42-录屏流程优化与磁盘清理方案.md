# 方案 42：录屏流程优化与磁盘清理方案

> **状态**：立项完成（2026-10-13，基于 0.7.5 用户验证反馈的代码级调研）；
> 待用户 review，实施排期另行指示。
> **背景**：0.7.5 验证反馈三现象——①下载录像后当前设备页面不能再录制；
> ②期望停止录制后给到视频下载界面、返回设备列表可再录制；③关闭服务后
> 录像文件未清理持续占盘。调研另发现一条数据丢失路径（自然录满 60s 的
> 产物被误删）。本方案为方案 37 B3 录屏交付后的使用性问题收口。

## 一、背景与目标

**用户意图**：录屏是车队设备运维高频能力，录制 → 下载 → 再录的循环必须
顺畅；录像文件属暂存性质，服务退出后不应残留占盘。

**成功标准**：
- 同一设备页停止录制后可直接「重新录制」，无需任何绕行（刷新/重启进程）；
- 重进/刷新设备页：上一段录像可下载（文件仍存在时）或自动复位 idle
  （文件已被清理时），且始终有「重新录制」出口；
- 录制中离开设备页 → 设备端自然录满 60s 时产物**自动拉回**（不丢失、
  无假计时、无 409 残留窗口）；
- 服务优雅退出（UI 退出）→ `data/recordings/` 清空；强杀/崩溃遗留 →
  下次启动即扫清；
- 双端门禁全绿 + 真机（.25）验收：连环录制 / 自然收尾 / 关服清盘三项全过。

**约束**：四层架构（回调注入做依赖倒置，cli 不依赖 application）；零新
依赖；TDD；磁盘数据保留策略——录像为暂存（会话表纯内存，进程重启后残留
文件已无任何下载入口，属纯垃圾），故「关服清空」符合策略而非例外；
master 直做、禁 push（发布需逐次显式授权）。

**链路**：start → 设备端 screenrecord（`--time-limit 60` 上限）→ stop
（pkill -INT 收尾）→ pull 到 `data/recordings/openscrcpy_rec_<12hex>.mp4`
→ pull 后设备端即清 → 前端面板预览/下载；会话表纯内存按 device_id 键
（`backend/app/application/recording_service.py`）。

## 三、设计

### §1 后端：自然结束自动收尾（修 B、C）

**cli 侧（stop 兜底 pull 路径）**：
- 任务终结回调不再弹 `_recording_paths`（仅弹 `_recording_tasks`；路径留到
  stop 消费或被下次 start 覆盖），使 stop 在「进程已自然结束」时仍能拿到
  remote_path；
- `stop_recording` 在 task 表项缺失时不再直接返回空串：检查设备端产物是否
  存在（`ls -ld` 探测），存在则返回 remote_path 供服务端 pull；不存在才返回
  空串。

**服务侧（自动收尾）**：
- `RecordingService.start` 时经依赖倒置通道注册「自然结束监听器」（cli 新增
  `Callable[[device_id], None]` 注册点；cli 不 import application）——natural
  end（正常 time-limit 结束；降档重试中的终结不触发）时 cli 回调调度监听器；
- 监听器 → 服务收尾协程：守卫（会话 id 匹配且仍为 recording 态，否则 no-op
  ——防新 start 已被覆盖时误动）→ 复用现有 `stop()` 路径（此时经 cli 兜底
  拿到 remote_path）→ pull → done。即「系统代为执行了一次 stop」；
- 效果：录制中离开页面的语义收敛为「录满自动保存」，假计时与 409 窗口消除，
  白录路径闭合。

**取舍**：不采用「卸载即 stop」——离开页面 ≠ 想停止录制（设备端 60s 上限
已接近用户预期），且卸载时请求可靠性差；自动收尾是更稳的收敛方式。

### §2 后端：自愈覆盖 stopping/pulling（修 D）

- 巡检扩展：stopping/pulling 态超时（如 >120s 无推进）的会话收敛 failed
  （清设备端 + 保留错误日志），消除持续 409 的滞留路径。

### §3 后端：录像磁盘清理（修 E）

- `RecordingService.cleanup_all_recordings()`：删除 `data/recordings/` 下
  全部 `openscrcpy_rec_*.mp4`（注释说明依据：会话内存态 + 磁盘保留策略），
  best-effort（失败日志告警不阻塞退出）；
- **优雅退出**：lifecycle shutdown（UI 退出与正常关服共用路径）调用之；
- **启动即扫**：startup 时同样执行（覆盖 stop.bat/taskkill 强杀与崩溃遗留
  ——强杀无退出钩子，兜底由下次启动承担）；tick「先 sleep 再首跑」改为启动
  即首扫（与启动兜底合一）；
- 运行期双限（3 天/512MB 逐小时 tick）保留不动。

### §4 前端：done 态完备化（修 A）

- done 态新增「重新录制」按钮（点击复位 idle 并直接 start；互斥语义不变）；
- 挂载恢复保留（刷新页面可拿回刚才的录像），但补失效处理：恢复时 GET 会话
  若 `local_path` 已不存在（被清理/关服清空）→ 后端收敛会话并 404 → 前端
  静默回 idle（消除「有面板无文件」假象）；
- done 态补充信息行：录像文件大小（可含生成时间）——轻量增强。

### §5 测试计划（TDD 逐层）

- cli 单测：stop 在 task 已终结且设备端文件存在 → 返回路径；不存在 → 空串；
  降档重试路径不受监听器/表项保留改动影响；
- recording_service 单测：自然收尾监听器 → stop → pull → done（含 pull 失败
  → failed）；监听器守卫（会话被新 start 覆盖 → no-op）；stopping/pulling
  超时自愈；cleanup_all_recordings（清空/幂等/目录不存在）；
- lifecycle 单测：shutdown 调用链（fake service 断言被调用）；
- 前端组件测试：done 态「重新录制」→ start 调用；恢复 done + 文件缺失
  （404）→ idle；既有 `:165`（done 无 `.record-start`）断言按新行为更新；
- 真机 spike（.25，tests/manual/）：录 10s→停止→下载→同页再录（第二段
  成功）；录满 60s 不点停止→自动收尾（轮询至 done、可下载、大小>0）；
  录制中离开页面（直调 API 模拟）→ 自动收尾；优雅关服→目录清空；强杀→
  重启后目录被清。

## 五、风险与已知限制

| 项 | 说明 | 缓解 |
|---|---|---|
| 自动收尾拉取时机 | 自然结束时 pull 需设备在线；离线 → 收尾失败收敛 failed（信息与手动 stop 失败一致） | 失败原因落会话，前端提示 |
| 强杀清理时机 | stop.bat/taskkill 强杀无钩子，遗留文件到下次启动才清 | 启动即扫兜底；手册说明 |
| 多实例并存 | 启动即扫会删除同 data 目录他实例的录像（单开模式已治理，概率低；录像为暂存） | 单开模式既有约束 |
| 下载中恰逢清理 | 流式下载被中断 | 关服即中断属预期；tick 双限按 mtime 有 3 天缓冲 |
