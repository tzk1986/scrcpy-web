## 一、问题分析

### 1.1 现象（用户报告）

2026-09-22 用户报告：现有连接 `192.168.8.25`（Rockchip RK3288 工业屏，
Android 7.1.2，物理 1366x768 → 编码对齐 1360x768）使用过程中
**「时不时会有正在连接出现」**——H.264 画面间歇性退回「正在连接...」
提示后再恢复，反复发生。

### 1.2 实测数据（.25 真机，2026-09-22）

探测脚本按 scrcpy v4.1 12B 包头协议直读设备端码流（独立 scid 与
既有会话并存，不影响用户会话）。

**基线（静止画面，60 秒）**：

```
[wiggle60] duration=60.0s total_frames=77 avg_fps=1.28 total_keys=12 max_gap=26.33s
[wiggle60] key_gaps ['0.2','0.5','0.5','2.1','0.5','21.8','0.5','0.4','0.5','2.2','0.5','26.7']
```

- **完全无帧最长窗口 26.33 秒**；逐秒帧数 0 占绝大多数
- 有活动时：帧率约 10fps、IDR 间隔 0.5s（很密，非 E020 的 42-57s）
- 结论：**该设备绝大部分时间画面静止，scrcpy 静止不出帧是设计行为**
  （仅画面内容变化才产生帧；E020 已在 RK3566 上确认静止态
  repeat-previous-frame 近空帧）。静止无帧 ≠ 故障。

**RESET_VIDEO 探针（静止态发送，type=17 单字节控制消息）**：

```
[reset8] t=   8.0s >>> RESET_VIDEO sent
[reset8] t=   8.2s SESSION 1360x768
[reset8] t=   8.2s CONFIG 36B
[reset8] RESET_VIDEO→key latency 0.25s (reset at 8.0s)
[server] INFO: Video capture reset
```

- 静止态发送后 **0.25 秒**（区间 0.1-0.4s）即收到新 IDR
- 服务端日志 `Video capture reset`，并**重发 SESSION + CONFIG 包**
- 官方定位：桌面端 `MOD+Shift+R` 手动「reset video」快捷键
  （`app/src/input_manager.c:reset_video()`），即官方提供的流恢复手段

**保活模式（无帧 3s 自动 RESET_VIDEO，20 秒实测）**：

```
[keepalive2] max_gap=3.41s
[keepalive2] t=  7.0s stall=3.0s >>> RESET_VIDEO #1  → t=8.0 新 IDR
[keepalive2] t= 16.0s stall=3.0s >>> RESET_VIDEO #2  → t=16.4 新 IDR
```

- **max_gap 26.33s → 3.41s**：每次 RESET 后 0.2-0.4s 必出新 IDR
- 代价：每次 RESET 产生一个 IDR（≈23KB）；3s 间隔 ≈ 60kbps，
  约为 4Mbps 流的 1.5%

**设备特征与既有故障族**：

- 全盘唯一视频编码器 `OMX.rk.video_encoder.avc`（无软编可换，E003/E009 已证）
- 与 E009/E021 的 Rockchip 故障族同型；上一轮排查曾实测该设备用户
  会话（PID 1774）`/proc/io` 完全冻结——**真卡死（活着不产帧）在本设备
  确凿存在**，与静止无帧是两个独立故障。

### 1.3 前端「正在连接...」触发链（代码走查）

「正在连接...」唯一渲染条件（`VideoPlayer.vue:49`）：
`state === 'idle' || state === 'configuring'`。共三个来源：

1. **首次连接**：正常，非本方案关注点。
2. **回退截图模式瞬间**：`checkH264Fallback()` → `startScreenshotMode()`
   将 `state='idle'`（`VideoPlayer.vue:300`），直到截图流自身 state
   变为 streaming 才消失（截图链路数百 ms~1.5s）。
3. **回切 H264 后（长停留主嫌疑）**：恢复探测通过 → `h264Stream.resume()`
   → `state='configuring'`，直到**解码器 output 首帧**才转 'streaming'。
   WebCodecs 解码器需要 IDR 才能出首帧——若回切时设备恰好静止，
   等待时长无上界。

**静止设备上的循环**（.25 场景）：

```
静止无帧 3s → 前端判 stall → 回退截图模式（state=idle 闪现「正在连接」）
  → 截图轮询可用，用户看到截图画面
  → 设备有活动 → 恢复探测（3 窗口 × ≥4 帧）通过 → resume() 回切
  → state=configuring「正在连接...」→ 0.5s 内出 IDR 则恢复，否则继续等
  → 活动停止 → 再次静止 → 循环
```

用户感知即为此循环在静止设备上反复发生。**根因不是流故障，而是
「静止」与「故障」在现有判据下不可区分**：前端 `STALL_MS=3000`
（`services/videoFallback.ts`）对静止场景必然误判。

### 1.4 同类项目经验（网络调研）

- **WebRTC（工业标准对照）**：接收端「3 秒无可解码帧」时发送
  **关键帧请求（PLI/FIR）**而非重建链路；FIR 还专门用于接收端
  切换/新加入（对应我们的 resume）场景。**对照结论：我们拿到 stall
  信号后的动作（切截图模式）过重，标准做法是「要一个关键帧」。**
- **scrcpy 官方**：RESET_VIDEO 为手动恢复快捷键（见 1.2）；
  另有两项官方自愈机制可借鉴——`downsize-on-error`（编码失败自动
  降分辨率重编码）与 v2.0「Retry on spurious encoder error」。
- **ws-scrcpy**：暴露 `iFrameInterval` 配置（对应 scrcpy
  `video_codec_options=i-frame-interval=N`），用于控制恢复速度；
  **但静止无帧时无帧可编码，该参数对静止场景无效**（本设备活动态
  IDR 间隔已实测 0.5s，无调整必要）。
- **scrcpy 桌面客户端**：静止时不做任何处理（画面冻结即正常）——
  「不把无帧当故障」是官方行为，当前前端判据与官方相反。
- **scrcpy-helper（第三方）**：提供无线自动重连（对应我们的
  WS 自动重连缺失，见实施项 5）。

## 二、方案设计

### 实施项 1：后端空闲保活 + 卡死探针（核心）

设备端静止无帧无法改变（编码器设计），但**用 RESET_VIDEO 给静止
场景注入周期性 IDR**即可同时解决两件事：前端不再误判静止；
真卡死时探针无响应可被检测→自愈。

- **1a 空闲保活**：`ScrcpyEncoder`（`infrastructure/stream/scrcpy.py`）
  在 yield 循环记录 `last_data_at`；空闲 ≥ `stream.idle_reset_seconds`
  （新配置项，默认 5s，0=关闭）时经既有 `_control_sender` 发
  RESET_VIDEO（单字节 type=17，`control_sender.py` 需补常量）。
  实测依据：0.1-0.4s 内必出新 IDR，带宽开销 ≈ 37kbps@5s。
- **1b 卡死探针与自愈**：RESET 后 `idle_reset_seconds` 内仍无数据 →
  判定编码器卡死（E009/E021 同族故障）→ 触发编码器重启。
  重启路径复用 `StreamService.start_stream` 自适应码率的重启循环
  （epoch 机制已能通知 WS 层重置解析器与重发 config）。
- 边界：
  - 仅在流活跃（有 WS 客户端）时保活，无连接不浪费带宽；
  - RESET 与用户操作输入的并发：`_control_sender` 已有 asyncio.Lock；
  - RESET 引发的 SESSION/CONFIG 重发已被后端正确处理
    （`_handle_session_event` 更新分辨率、config 包阻塞入队），
    解析器无需改动。

### 实施项 2：前端静止感知（与后端保活对齐）

- **2a 阈值对齐**：`STALL_MS` 必须大于后端保活间隔 + 余量
  （如保活 5s → stall 阈值 ≥ 8s），否则仍会误判。两个值需要
  联动（建议前端从 config 消息或新 WS 消息读取保活间隔，
  避免双端硬编码漂移）。
- **2b 静止不切截图**：设备静止时 H264 分支保持「最后一帧冻结」——
  这是官方桌面端行为，体验优于 1.5s 轮询截图（方案 17 根因 A），
  且消除回退/回切的往返。真正的流故障（后端保活探针也判定卡死、
  或 WS 断开）才走回退。
- 可选增强：后端 WS 层周期性下发 `{"type":"keepalive"}`（1Hz），
  前端完全以「后端心跳」判活，不再依赖帧计数——彻底解耦
  「静止」与「故障」。

### 实施项 3：回切时请求关键帧（消灭「正在连接...」长停留）

- 前端 `resume()` 前经 WS 发 `{"op":"request_keyframe"}`；
  后端 `video.py:_handle_input` 增加分支 → `StreamService` →
  `ScrcpyEncoder` 立即发 RESET_VIDEO → 0.1-0.4s 出新 IDR →
  resume 后秒级出图。
- 对应 WebRTC 的 FIR 语义（接收端切换/新加入时请求关键帧）。
- 注意：RESET 后服务端重发 CONFIG（新 SPS/PPS），而
  `video.py` 的 `config_sent` 为 True 时会静默丢弃——当前 SPS/PPS
  不变时无影响（前端 resume 用缓存的 `_lastAvccDesc`）；若编码参数
  已变（分辨率/档位），需在 epoch 变化时重置 `config_sent` 允许重发。
  实施时一并处理。
- 冷却：前端每次 resume 只请求一次；后端对 request_keyframe 加
  最小间隔（如 1s）防抖。

### 实施项 4：状态提示治理（体验层）

- `startScreenshotMode()` 不再把 `state` 置为 `'idle'`
  （`VideoPlayer.vue:300`）——回退瞬间的「正在连接...」闪现消失；
  截图流有自己的状态语义。
- 回切 configuring 期间用区分文案（如「正在恢复画面…」）或直接保留
  冻结帧不提文案；「正在连接...」只保留给首次连接。
- `stateLabel` 补 'screenshot' 等新状态映射。

### 实施项 5：连接层加固（独立可选项）

- **WS 自动重连**：`services/websocket.ts` 现为注释占位
  （「自动重连（未来实现）」）；补指数退避重连 + 状态提示。
- **流结束通知**：`video.py` 流正常结束/异常时当前不给客户端任何
  消息，前端只能等 watchdog；补 `{"type":"stream_ended"}` 通知。
- WS 心跳（ping/pong）用于探测半开连接（与实施项 2 的 keepalive
  可合并设计）。

### 2.6 明确不做（已评估）

- **不换软编**：设备全盘无软编编码器（E003 报 not found，E009 同族）。
- **不加 i-frame-interval**：活动态 IDR 间隔实测已 0.5s；对静止
  无帧无作用。
- **不做分辨率/码率降档**：E021 已证卡死与码率档位无关；1360 对齐
  非主因（RK 编码器对 8 对齐要求所致，属正常）。
- **不改定制 jar**：RESET_VIDEO 已具备，无需修改 server。

## 四、验收标准

1. 静止场景 10 分钟：前端不进入截图模式（或回退次数 = 0），
   无「正在连接...」出现；画面维持最后一帧冻结。
2. 回切：request_keyframe 到重新出图 ≤ 2s（实测 RESET→IDR 0.1-0.4s）。
3. 卡死注入（对 server 进程编码线程 STOP 模拟）：≤ 2 × idle_reset
   秒内自动重启编码器并恢复出图。
4. 保活带宽开销 ≤ 100kbps（5s 间隔实测 ≈ 37kbps）。
5. 既有门禁全绿（后端 pytest/ruff/mypy + 前端 vitest/eslint/build）。

## 五、风险与待验证

- RESET_VIDEO 为无响应消息（发后不确认），探针判定依赖「是否有
  后续数据」，需覆盖 RESET 与真实帧到达竞态。
- 定制 jar 锁定 scrcpy 4.1：升级版本时需复核 RESET_VIDEO 语义。
- **待真机复现确认**：本方案的「正在连接...」链路基于代码走查，
  需在 .25 上以浏览器实测（建议开 console 观察 fallback/recovery
  日志时间戳）确认三个来源各自的实际占比，再定实施项 2/4 的具体
  参数。
- wiggle 注入触摸未稳定触发出帧（实测中仅部分时段有效）——
  可能信息：该设备桌面区域拖动无视觉反馈；保活方案不依赖此路径，
  列为工具改进项。
- **实施落地要点（8 任务 TDD，代码已合入，真机验证待执行）**：
  - 保活 tick = min(2.0, idle_reset/2)（idle=5s 时 2s 轮询）；
    reset_video 发送失败按 tick 重试（实施中修正了原设计的
    「失败锁死」缺陷——失败清锁存、下一 tick 再发，粒度
    idle_reset/2 风暴安全）；
  - 卡死检测最坏 ≈2×idle_reset（tick 相位差 + 完整 idle_reset 等待）；
  - 防风暴：60s 滑窗内 ≤3 次卡死重启、重试退避 1s×n，超出则上抛
    error 走回退链；
  - 前端阈值联动公式：STALL=2×keepalive、NO_STREAM=STALL+2s、
    HARD_TIMEOUT=NO_STREAM+5s（keepalive=0 回落默认 3s/8s/15s）；
  - 1Hz WS 心跳（实施项 2 可选增强）与消息级探活（实施项 5 心跳）
    裁定不做——RESET_VIDEO 保活 IDR 已覆盖判活语义；半开连接探测
    留待未来。
