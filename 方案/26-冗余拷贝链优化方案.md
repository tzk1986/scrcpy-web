# 方案 26：视频帧冗余拷贝链优化（后端包协议直通 + 前端扫描/组装合一）

> **状态**：已实施（2026-09-30，TDD 前后端收口；真机 spike 见 progress）。
>
> **由来**：`docs/性能对标与优化清单.md` P1-5「冗余拷贝链」——后端每帧约 4 次整帧拷贝、前端每帧 3 次拷贝，8Mbps 下数 MB/s 流量与额外内存分配。
>
> **关联**：方案 17（12B 包头协议实施项 1b——包边界即帧边界的协议事实）、方案 19（RESET_VIDEO/CONFIG 重发路径）、清单 P2-PTS（透传未做，本方案不扩大范围）。

---

## 1. 背景与现状（拷贝链逐层枚举，2026-09-30 核实）

### 1.1 后端（包协议模式，每帧 4 次整帧拷贝）

| # | 位置 | 操作 | 可否消除 |
|---|------|------|---------|
| C1 | `backend/app/scrcpy/stream_protocol.py:185` | `payload = await reader.readexactly(fh.payload_size)` | **否**（socket 必须落到新 buffer，唯一必要分配） |
| C2 | `backend/app/scrcpy/h264_parser.py:83` | `self._buffer.extend(data)` 整 chunk 追加 | 可消除（见 §3） |
| C3 | `backend/app/scrcpy/h264_parser.py:102` | `nalus.append(bytes(buf[idx:nxt]))` NALU 切片 | 可消除 |
| C4 | `backend/app/interfaces/ws/video.py:180` | `au = b''.join(forward_nalus)` 整 AU 合并（单 NALU 时 CPython join 短路，多 slice/SEI 时为整帧拷贝） | 可消除 |

协议事实（方案 17 实施项 1b 已述）：12B 包头含载荷长度，scrcpy-server 每个媒体包恰为一个编码帧输出（= 一个 AU），config 包（SPS/PPS，带 bit62 flag）单独成包。因此 **C2/C3/C4 三步在包协议模式下对媒体包全部冗余**——parser 全量重扫纯为 SPS/PPS 拦截服务，而拦截只需读型别字节，无需拷贝。

### 1.2 前端（每帧 3 次整帧拷贝）

| # | 位置 | 操作 |
|---|------|------|
| F1 | `frontend/src/services/h264NalUtils.ts:44` | `extractNalus` 每个 NALU 做 `data.slice(...)`（payload 切片） |
| F2 | 同上 | 每个 NALU 另做 `raw.slice(...)`（含起始码切片）——**帧路径完全未用 raw 字段**（仅 config 路径用 `nalu.raw` 保存 SPS/PPS） |
| F3 | `h264NalUtils.ts:74` `nalusToAvcc` | 整帧组装 AVCC：新 ArrayBuffer + 逐 NALU 拷贝 |

调用点 `frontend/src/services/h264VideoStream.ts:421-448`：`extractNalus` → `hasKeyFrame` → `shouldDropFrame` → `nalusToAvcc` → `EncodedVideoChunk`。

## 2. 设计决策

| # | 决策 | 说明 |
|---|------|------|
| D1 | 后端常态直通：包协议模式媒体包不经 parser，整包原样 `send_bytes` | 一包 = 一 AU，直通即原语义（含 SEI、多 slice 均原样转发） |
| D2 | 后端 SPS/PPS 预检扫描（零拷贝只读）：新纯函数 `scan_sps_pps(chunk)`，仅发现 NAL 型别 7/8 时才切片返回/回退 parser | config 包与罕见混包走回退完整解析，正常帧零分配 |
| D3 | 不改跨层接口：队列仍传 `bytes`，判定在 WS 接口层做内容预检 | 避免动 domain port 与 stream_service（blast radius 最小）；后续如需更彻底可在队列携带 is_config 元数据，属 v2 |
| D4 | raw 兜底模式（`packet_mode=False`）维持现状 parser + AU 启发式聚合 | 裸流无边界保证，直通不成立 |
| D5 | 前端扫描/组装两遍合一：新 `scanFrame`（零拷贝扫描，产出 offset/length + isKey）+ `frameToAvcc`（单次分配组装），置换帧路径三连 | 每帧分配 3 次 → 1 次；`extractNalus` 保留（config hex 解析路径）；`hasKeyFrame`/`nalusToAvcc` 帧路径唯一消费者，删除 |
| D6 | 不扩大范围：PTS 透传、raw 模式拷贝、webtransport 路径不动 | 分别属清单 P2/P3 项 |

## 3. 后端设计

### 3.1 新函数 `scan_sps_pps`（`backend/app/scrcpy/h264_parser.py`）

```python
def scan_sps_pps(data: bytes) -> tuple[bytes | None, bytes | None]:
    """零拷贝扫描：仅发现 SPS/PPS（NAL 型别 7/8）时切片返回，常态返回 (None, None)。

    边界语义与 H264Parser.feed 完全一致（3 字节码优先 + 00 回看修正），
    返回的均为最后出现的 SPS/PPS（与原逐 NALU 覆盖语义等价）。
    """
```

算法：单遍 `bytes.find(b'\x00\x00\x01')` 定位起始码（回看吸收 4 字节码头字节）→ 型别字节在 `idx + 3` → 记边界不切片 → 结尾仅在发现 7/8 时切片返回。

### 3.2 video.py 包协议分支重写（`backend/app/interfaces/ws/video.py`）

- SPS/PPS 拦截循环抽为内层 async 闭包 `intercept_config(nalus) -> list[bytes]`（nonlocal sps_data/pps_data/config_sent），包模式罕见路径与 raw 模式共用，语义不变。
- 包模式常态：
  ```python
  sps, pps = scan_sps_pps(chunk)
  if sps is None and pps is None:
      if config_sent and chunk:
          await websocket.send_bytes(chunk)   # 整包直通，零拷贝
          frame_count += 1
      continue
  # 罕见：config 包/混包 → 回退完整解析（parser.feed + intercept + join）
  ```
- raw 模式分支维持原样。

## 4. 前端设计（`frontend/src/services/h264NalUtils.ts`）

```ts
export interface FrameNaluPos { offset: number; length: number }  // payload（去起始码）
export interface FrameScan { nalus: FrameNaluPos[]; isKey: boolean }

/** 零拷贝单遍扫描：NALU 边界 + 关键帧判定，与 extractNalus 边界语义逐字节一致 */
export function scanFrame(data: Uint8Array): FrameScan

/** 单次分配：按扫描结果组装 AVCC（4B 大端长度前缀 + payload 直拷） */
export function frameToAvcc(data: Uint8Array, frame: FrameScan): ArrayBuffer
```

`h264VideoStream.handleBinaryFrame` 置换：

```ts
const scan = scanFrame(data)
if (shouldDropFrame(this.decoder.decodeQueueSize, scan.isKey)) { ... }   // 不变
if (scan.isKey && this.decoder.decodeQueueSize >= MAX_DECODE_QUEUE) { ... }  // 不变
const avccData = frameToAvcc(data, scan)
```

删除 `hasKeyFrame`、`nalusToAvcc`（帧路径是唯一调用者）；`extractNalus` 保留（config hex 解析用 `raw` 字段）。

## 8. 风险与回退

| 风险 | 缓解 |
|------|------|
| `scan_sps_pps` 边界语义与 parser 不一致（如假起始码、4 字节码回看）→ 误判混包/漏拦截 | 扫描算法复用 feed 同款「3 字节优先 + 回看」规则；单测用 parser.feed 结果做对照 oracle |
| 个别设备媒体包内嵌重复 SPS/PPS 头 | 混包路径回退 parser 完整解析并剥离（非直通），语义与原实现一致 |
| 直通丢 SPS/PPS 拦截导致 config 变化（卡死自愈/重编）漏检 | config 包必含 7/8，扫描命中走既有拦截逻辑下发新 config |
| 前端边界语义漂移致 AVCC 组装错位 | 与 extractNalus 逐字节对照测试锁死 |
