# 方案 29：截图模式设备端编码链路换挡（raw + gzip，spike 后立项）

> **状态**：**Phase 0 spike 已完成（2026-09-30，三机 .18/.25/.33）→ 判定可行（GZIP_WORTHY）→ 待实施（Phase 1-3）**。spike 钉死：raw 裸传不可行（4.2MB/帧，.25 全链 2625ms）；**raw|gzip -1 在 .18 照片级最坏画面同帧 594-750ms 中位 641（N=5：625/641/750）vs PNG 1171/1219/1281——约 2× 提速且 <800ms ✓**；典型 UI 画面 328-360ms（gz 58KB）；.25（rk3288/A7.1）两链路打平（~985 vs ~1000ms，旧机物理上限，不进不退）；**头格式双态钉死：A11=16B / A7.1=12B（w/h/fmt[/cs]），前端按 `len - w*h*4` 反推**；通道顺序与 PNG 逐像素一致（7 点 SAME）；gzip 往返长度精确吻合；浏览器侧原生解压（DecompressionStream）22-59ms/4.2MB。契约形态经用户确认：**`?format=raw` opt-in，默认 PNG 不变（D1）**。
>
> **由来**：`docs/性能对标与优化清单.md` P1-6 遗留（§4.5）：前端侧反馈已收口（2491→1116ms，方案 27），**<800ms 未达成——设备端 screencap PNG 编码中位 ~950-1000ms 单点已超目标本身，PNG 链路物理不可达**；§4.5 明确后续 =「设备端编码链路换挡（JPEG/raw + adb 直读 raw framebuffer）——另立方案」。
>
> **关联**：方案 27（本方案续接其遗留 T2 瓶颈；其 debounce/单飞/相位重置链路不动）、方案 17（截图模式原始实现）、性能清单 §4.5 / P1-6。

## 1. 现状走查（2026-09-30 核实）

**帧链路**（截图模式 = 前端驱动、HTTP 轮询）：

1. `VideoStream.start()`（`frontend/src/services/videoStream.ts:102-128`）——立即取首帧 + `setInterval(captureNow, refreshInterval=1500ms)`
2. 方案 27 已消除 T1 轮询相位等待：输入事件驱动 `notifyInput()`（videoStream.ts:135-144，debounce 160ms）+ 单飞 `captureNow`（:146-153）+ 尾补帧与相位重置（:155-180）
3. `api.screenshot(deviceId)`（`frontend/src/services/api.ts:224-229`）→ `GET /api/devices/{deviceId}/screenshot`（`responseType: 'blob'`）
4. 后端三层：`interfaces/http/devices.py:185-197` → `application/device_service.py:143-153` → `infrastructure/adb/cli.py:424-449`（`adb exec-out screencap -p`，PNG）
5. 渲染：`renderBlob`（videoStream.ts:230-250）——`createImageBitmap(blob)` → `ctx.drawImage`（失败降级 Image+ObjectURL，:253-）

**瓶颈**：T2 设备端 PNG 编码中位 ~950-1000ms 单点超 800ms 目标（方案 27 §4.5 已钉死），改前端无法触及——必须换设备端编码链路。

**集成面事实**：`/screenshot` 端点生产消费方仅 `videoStream.ts` 单处；后端无 GZipMiddleware（main.py:92-103 仅 CORS，`Content-Encoding: gzip` 透传无双重压缩风险）；CORS 自定义响应头需登记 `expose_headers`（main.py:101-102 已有 X-Export-* 先例）。

## 2. spike 实测（2026-09-30，`tests/manual/spike_screenshot_raw.py`）

四条候选链路（exec-out 全链耗时，同帧 N≥3）：

| 设备 | 画面 | `png -p` | `raw` | `raw｜gzip -1` | `raw｜gzip -6` |
|------|------|----------|-------|----------------|----------------|
| .18 rk3568 / A11 / 1366×768 | MSN 网页（照片级复杂） | 1125-1219 中位 1219 | 953-1484（4.2MB） | **594-750 中位 641**（wire 1.06MB） | 719-797 中位 734（wire 786KB） |
| .18 | 设置类典型画面 | 500-578 | — | 328-360（wire 58KB） | 422-437（wire 33KB） |
| .25 rk3288 / A7.1 / 1366×768 | 启动器壁纸（中复杂） | 984-1078 中位 1000 | 2625-2672（4.2MB） | 922-1047 中位 985（wire 636KB） | — |
| .33 rk3566 / A11 / 800×1280 | 简单画面 | 76590B 未测时延 | — | 594-938 | — |

**钉死事实**（N=5 复测 .18 照片级：gz1 625/641/750 vs png 1171/1219/1281 → verdict GZIP_WORTHY）：

- **raw 裸传不可行**：4.2MB/帧；.18 全链 953-1500ms，.25 全链 2625ms（≈1.6MB/s，adb over TCP 上限）。不猜测，实测钉死
- **raw|gzip -1 是强候选**：.18 照片级约 2× 于 PNG；gzip -6 压缩更小但设备端更慢（-1 已把 wire 压到 58KB-1.06MB，adb ~6.6MB/s 下传输差异不抵编码耗时）——选 **-1**
- **头格式双态**：A11（.18/.33）= **16 字节**（w/h/fmt/colorspace 各 uint32 LE）；A7.1（.25）= **12 字节**（w/h/fmt）。`len - w*h*4 ∈ {12,16}` 精确吻合；fmt=1（RGBA_8888）三台一致。**这是实施期必踩的坑，spike 提前钉死**
- **通道顺序**：raw 与同帧 PNG 解码逐像素对比 7 采样点全部 SAME（RGBA、无通道交换、无行翻转，.18）
- **gzip 往返正确**：Python `gzip.decompress` 15-47ms 解出 4196364/4196368 B 长度精确；浏览器侧 `DecompressionStream('gzip')`（Node 代理实测）22-59ms / 4.2MB——**前端解压不是瓶颈**
- **设备端 gzip = toybox**，A7.1/A11 三台均可用；`screencap -h` 仅 -h/-p/-d（无 FILENAME 即 raw stdout）

**预估端到端**（.18 照片级最坏，含前端侧）：641（设备+adb）+ ~25-60（浏览器原生解压）+ putImageData 几 ms + HTTP 开销 ≈ **~700ms < 800 ✓**；典型画面 ≈ ~400ms（对照现状反馈中位 1116ms）。.25 旧机 ≈ 现状（不进不退，PNG 也 ~1s）。

## 3. 设计决策

| # | 决策 | 说明 |
|---|------|------|
| D1 | **契约形态：`?format=raw` opt-in**（用户 2026-09-30 确认）：默认 PNG 契约不变，截图流显式请求 raw | 零外部影响；导出/其他潜在消费方与端点文档契约不动；可回退 |
| D2 | **透传：设备端 gzip 字节原样返回 + `Content-Encoding: gzip`** | 浏览器网络层原生透明解压（实测 22-59ms），后端零 CPU、不接触像素；响应头 `X-Frame-Format: raw-rgba` 供前端分支渲染（登记入 CORS `expose_headers`，main.py:102 先例）。备选（若中间层破坏透明解压）：自定义头 + 前端 `DecompressionStream`——见 §6 |
| D3 | **前端渲染：头自适应 + ImageData 直上**：`headerSize = len - w*h*4` ∈ {12,16} 且 fmt==1 → `new ImageData(new Uint8ClampedArray(buf, headerSize), w, h)` → `putImageData`；canvas 尺寸对齐 | 跳过 createImageBitmap 解码（PNG 600KB 解码亦有开销）；双头格式由长度反推 |
| D4 | **双层回退，不新增错误态**：① 后端 gzip 链路 exec 失败（无 gzip 设备等）→ 单请求内回退 PNG（`X-Frame-Format: png`）；② 前端校验失败（头非法 / fmt≠1 / 长度不符 / 头格式头缺失）→ 丢弃该帧并按 PNG 继续（会话内降级记忆 `_rawUnsupported`） | 旧设备零回归；格式不认识就退回已知好路径——不猜（E002 教训） |
| D5 | **不动项**：WS/H264 链路、方案 27 的 debounce/单飞/相位重置、截图下载端点既有 PNG 契约、refreshInterval=1500ms 节奏 | blast radius 限制在「截图流取帧格式 + 渲染分支」两点 |
| D6 | **测量锚**：设备侧复用 spike 脚本；端到端 Phase 3 真机以帧计数 + 输入注入时的反馈时延对比（同方案 27 口径，临时日志实施期加、收口删） | 生产零埋点 |

**任务 3：`services/api.ts` 新增 `screenshotRaw(deviceId)`**

- 用例（`api.test.ts`）扩展。

**任务 4：`services/videoStream.ts` raw 渲染分支 + 降级记忆**

- `captureFrame`：请求 raw → `format === 'raw-rgba'` → `renderRawFrame(blob)`：读 ArrayBuffer → 头解析（w/h/fmt + `headerSize = len - w*h*4 ∈ {12,16}`）→ `ImageData` + `putImageData`；校验失败或 `format === 'png'` → 既有 `renderBlob` 路径；校验失败置 `_rawUnsupported`，后续直接请求 PNG（不再试 raw）
- 用例（`videoStream.test.ts`）：
  1. 16B 头 raw 帧 → putImageData 渲染（尺寸对齐 canvas）
  2. 12B 头 raw 帧 → 同上

  4. `format === 'png'` 回退帧 → 既有 renderBlob 路径
  5. 既有 PNG 路径回归（renderBlob/renderBlobFallback 不动）

## 6. 风险

- **`Content-Encoding` 透明解压被中间层破坏**（Vite dev proxy / 未来反向代理）：实施后 **dev 与构建版双路径验证**；若破坏 → 切换 D2 备选（后端仍原样透传 gzip 字节 + 自定义头，前端 `DecompressionStream('gzip')` 显式解压，代码量略增、性能等价）
- **头格式第三态**（非 12/16B / fmt≠1 / future colorspace 语义变化）：校验失败即降级 PNG——不猜不猜测式适配（E002 教训）
- **.25 旧机无收益**：如实标注（PNG 也 ~1s，rk3288 物理上限）；本方案承诺是「不进不退」
- **每帧 4.2MB 解压缓冲分配**：0.7fps 节奏下 GC 无压力；缓冲复用作 P2 备选（有实测需要再立）
- **gzip 字节 > PNG 的极端内容**（.25 启动器实测 gz 636KB > png 461KB）：wire 增大但耗时打平（压缩档 -1 的 CPU 省于 PNG 编码）——不影响判定，如实记录
- **gzip 可用性探测策略**：首帧失败即回退（D4），不做预探测（少一次 RTT；失败路径已真机注入验证）
