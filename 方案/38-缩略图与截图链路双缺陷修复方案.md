# 方案 38：缩略图与截图链路双缺陷修复方案

> **状态**：立项完成（2026-10-10），待实施。
> **背景**：方案 36 第三批增补验收期用户上报两起截图缺陷：
> ① .16 设备列表缩略图显示「fail」；② .24 设备缩略图倒置。
> 根因调研（约束 7 前置）已完成，本文档固化根因证据链与修复设计，随后 TDD 实施 + 真机 spike。

## 一、现象（用户上报）

| 设备 | 现象 | 视频流（H264） |
|------|------|----------------|
| 192.168.8.16 | 缩略图 fail（PNG 解码失败链路） | 正常 |
| 192.168.8.24 | 缩略图倒置（180°） | 正常 |

## 二、根因分析

### 缺陷 A：.16 多显示器 screencap 警告污染输出流

**设备环境**：.16 为双显示器（内置 1280×800 + HDMI 800×1280）。

**证据链**：
1. `adb exec-out` 合并设备 stderr → stdout（项目经验记录已载）；
2. 多显示器设备上 `screencap` 打印「Multiple displays were found」警告至 stderr，
   实测 347 字节，随 exec-out 混入数据流首位；
3. 实测 .16 两条截图链路输出均以 347B 文本打头，PNG 魔数 `\x89PNG` 与
   gzip 魔数 `\x1f\x8b` 均偏移 347：
   - PNG 链路（`screencap -p`）：浏览器拿到「文本 + PNG」混合物，解不出图 → 缩略图 fail；
   - raw+gzip 链路（`screencap | gzip -1`）：警告走 screencap 的 stderr，
     未进 gzip 管道（实证 gzip 魔数位于输出偏移 347 而非被压缩进流内），
     但同样污染 exec-out 输出首位——浏览器 gzip 透明解压前即拿到脏流。
4. 单显示器设备（.18/.33/.25）无此警告，链路正常——与舰队一致性吻合。

**根因定性**：screencap 的 stderr 噪声经 exec-out 传输层合并进入数据流，
两条截图链路均无防御。

### 缺陷 B：.24 设备 rotation=2 倒置

**设备环境**：.24 物理倒装横屏（`dumpsys display` 实测 `mCurrentOrientation`
/`mOverrideDisplayInfo` rotation=2，即 180°）。

**证据链**：
1. SurfaceFlinger 以 rotation=2 渲染正确正向画面 → scrcpy 视频流按 rotation
   处理，画面正常；
2. `screencap` 输出**物理 framebuffer 方向**（不随 display rotation 旋转），
   rotation=2 设备上即 180° 倒置；
3. rotation=0 设备（.18/.33/.25）截图正向——与舰队一致性吻合。

**根因定性**：截图链路（PNG 与 raw 两条）缺失 rotation 补偿，而视频链路
（scrcpy 协议按 rotation 处理）正确，形成「流正常、截图倒置」的差异。

## 三、修复设计

总原则：**两层防御 + rotation 补偿**，最小侵入、不破坏既有链路性能特征。

### 3.1 修复 A：命令硬化 + 魔数剥前缀（backend 基础设施层）

**A1 命令硬化**（治本，设备端丢弃 stderr 噪声）：

- PNG 链路：`exec-out screencap -p` → `exec-out sh -c "screencap -p 2>/dev/null"`
  （exec-out 传输层合并发生在设备 shell 之后，设备端重定向先于合并生效）；
- raw+gzip 链路：`sh -c "screencap | gzip -1"` → `sh -c "screencap 2>/dev/null | gzip -1"`；
- 不启用 `-d 0` 显示选择参数（部分 Android 版本不支持，静态启用有回归风险）；
  多屏「取哪块屏」与流内容一致性交由真机 spike 验证（§五），若不匹配再评估
  按设备自适应探测。

**A2 魔数剥前缀**（兜底，`backend/app/infrastructure/adb/cli.py`）：
新增私有助手 `_strip_lead_junk(data: bytes, magic: bytes) -> bytes`，
`data.find(magic)` 命中且偏移 > 0 时从魔数处切片；未命中或已在 0 位原样返回
（只增不减，不引入新失败路径）。`screenshot()` 用 `b"\x89PNG"`、
`screenshot_raw_gzip()` 用 `b"\x1f\x8b"`。

**层级说明**：A2 位于基础设施层，两条链路共用，HTTP 端点（interfaces）与
前端零改动即自动受益（缩略图 PNG 链路经由该层）。

### 3.2 修复 B：rotation 查询（TTL）+ PNG 补偿 + raw 前端补偿

**B1 rotation 查询（infra）**：`cli.get_rotation(device_id) -> int`，
执行 `dumpsys input`（轻量命令，较 dumpsys display 输出小一个数量级），
本机解析 `SurfaceOrientation: <n>`（0-3）；缺失/不可解析/命令失败 → 0（不旋转）。

**B2 协议层**：`ports.py` 增加 `get_rotation` 抽象方法。

**B3 应用层 TTL 缓存**：`device_service.get_rotation(device_id)`——内存
字典 `{device_id: (rotation, ts)}` 缓存 30s（成功与失败同 TTL，失败值 0），
截图模式逐帧调用不产生 dumpsys 风暴。

**B4 PNG 补偿（应用层）**：新增 `backend/app/application/image_ops.py`：
`rotate_png_payload(data: bytes, rotation: int) -> bytes`。rotation ∈
{1,2,3} 时经 PIL `Image.transpose` 顺时针补偿（映射 1→`ROTATE_270`、
2→`ROTATE_180`、3→`ROTATE_90`；rotation 0/越界原样透传）。
`device_service.screenshot()` 内部串联：adb 截图 → get_rotation（命中 B3 缓存）→ rotate_png_payload。
缩略图/截图/调试面板全部 PNG 消费点统一受益，前端 PNG 路径零改动。

**B5 raw 链路补偿（前端）**：raw+gzip 为逐帧链路，后端不解压不重压缩
（保护方案 29 性能特征），补偿放前端显示层：
- `api.screenshotRaw` 解析 `X-Rotation` 响应头（缺失按 0，防中间层吞头）；
- `videoStream.renderRawFrame`：rotation==2 时 canvas `ctx.save();
  translate(width, height); rotate(π); putImageData; restore()`；
- 仅实现 rotation==2（舰队实证场景）；1/3 列为已知限制（§七）。

**B6 端点响应头**：`GET /api/devices/{id}/screenshot` 三个分支（raw-gzip /
raw 回退 png / png）均附 `X-Rotation: <n>`（值经 B3 缓存，逐帧无成本）。

### 3.3 依赖变更

`pyproject.toml` 增加 `pillow>=10.0.0`（本地环境已装 12.3.0；>10 自带
py.typed，mypy strict 无碍；exe 打包 PyInstaller 自动收集，约 +3.5MB）。
若 mypy 对 PIL 报缺 stub（理论情形），按既有先例追加
`[[tool.mypy.overrides]] ignore_missing_imports`。

   魔数在 0 位 → 原样；无魔数 → 原样；
2. `screenshot` / `screenshot_raw_gzip` 命令断言更新（sh -c 形态）+ 脏流入参

   缺失 → 0；命令失败 → 0；

   失败值同缓存；过期后重查（monkeypatch 时钟）；
5. `rotate_png_payload`：PIL 生成 2×3 四角异色图，rotation=2 → 重开断言像素
   位置互换；rotation=0 → 字节原样；1/3 映射断言；越界 → 透传；

**frontend（vitest）**：

   x-frame-format 缺失防吞头既有用例手法）；
9. `renderRawFrame` rotation==2 → 断言 ctx translate/rotate/putImageData
   序列；rotation 0 → 无变换调用。

**门禁**：pytest `--cov-fail-under=80` + ruff（backend/app + 改动测试文件口径）
+ mypy strict；前端 vitest + vue-tsc --noEmit。

## 五、真机 spike 清单（tests/manual/）

1. **.16**：新链路截图 PNG → 魔数 0 位、PIL 可解、尺寸 1280×800（内置屏）；
   raw+gzip → 魔数 0 位；**内容与视频流一致性**（若取到 HDMI 屏则启动
   `-d 0` 自适应方案评估）；缩略图浏览器显示正常；
2. **.24**：PNG 截图正向（与流一致）；截图模式（若触发）raw 帧正向；
   缩略图正向；
3. **回归 .18/.33/.25**：PNG 截图字节有效、画面正向（rotation=0 链路
   零变化）；raw+gzip 链路无损。

## 七、风险与已知限制

| 项 | 说明 | 缓解 |
|----|------|------|
| .16 多屏取屏与流不一致 | screencap 默认屏可能与 scrcpy 流不同 | spike 第 1 项验证；不一致 → 评估按设备 `-d` 探测 |
| 警告走 stdout 进 gzip 流 | 假设性场景（未见实证） | A2 剥前缀仍保 raw 流魔数干净；流内污染列为残留风险 |
| rotation 查询失败 | 返回 0 不旋转，30s 内不重试 | 缓存期后自动重查 |
| 前端 raw 仅补偿 180° | rotation 1/3 设备的截图模式 fallback 仍颠倒（舰队无此设备） | 已列明，未来设备扩充时按映射补齐 |
| Pillow 新依赖 | exe 体积 +~3.5MB，需重打包 | 依赖已固化于 pyproject；重打包纳入发版队列 |
