## 一、问题（清单条目与实测核查）

### 1.1 清单原文与现实的关系

清单 P3 原文：**「后端每 chunk info 日志」**。逐点核查后发现条目描述
与现状不符，真身是另外几处：

- `video_chunk_progress`（video.py:162-165）**早已节流**——每 100 chunk
  一条（30fps 下 ≈ 3.3s/条），不是「每 chunk」；
- 实测最大的日志源是 **SPS/PPS 幂等重发**（见 1.2），清单未列。

### 1.2 实测数据（快照）

样本：`.scratch/server.log`，2026-10-08 01:05:00Z → 03:04:13Z（119 分钟，
含 .18 旋转 e2e 与诊断操作），6201 行（其中 395 行非 JSON，为 uvicorn
启动横幅与 access log）：

| 事件 | 条数 | 占比 | 性质 |
|------|------|------|------|
| sps_received + pps_received | 2077 + 2077 = **4154** | **67%** | 幂等重发仍每次打点 |
| video_chunk_progress | 219 | 3.5% | 已节流（每 100 chunk） |
| session_meta_received | 192 | 3.1% | 幂等重发（79% 内容不变）仍打点 |
| control_resolution_updated | 163 | 2.6% | 分辨率不变仍打点 |
| idle_reset_video_sent | 122 | 2.0% | 低频事件（30s 空闲节律），保留合理 |
| video_frame_sent | 110 | 1.8% | 每会话前 5 帧，合理 |
| 输入链 5 事件 | 110 | 1.8% | **交互爆发项**（测试期输入少） |
| scrcpy_server_log | **0** | 0% | v4.1 运行期 stderr 静默 |
| frame_before_config | **0** | 0% | 未引爆（config 通常首包即就绪） |

**幂等率实测**（决定降级后残余 INFO 量）：

| 序列 | 总条数 | 相邻内容变化 | 幂等率 |
|------|--------|--------------|--------|
| SPS（按 nalu_size） | 2077 | 2 | **99.9%** |
| PPS（按 nalu_size） | 2077 | 0 | **100%** |
| session_meta（按宽高） | 192 | 40 | 79.1% |

**SPS 重发周期**：间隔中位数 **0.50s**（<0.5s 958 次、0.5–2s 741 次）
——视频活跃期 scrcpy-server 以 ~0.5s 周期重发 SPS/PPS（内容幂等），
每轮在 `intercept_nalu` 产生 2 条 INFO，即活跃流时段 ≈ 4 条/秒。

### 1.3 输入链的交互爆发潜力

每次前端输入在链路双层共打 4–5 条 INFO：

- `video.py`：`input_received`（含完整 data 字典）/ `sending_input_via_encoder` /
  `input_sent`（3 条，:350/:357/:361）；
- `scrcpy.py`：`send_input_called`（1 条，:592）+ touch/long_press 各多 1 条
  （`sending_touch`/`sending_long_press`，:610/:620）。

拖动场景（mousedown 后每 mousemove 一条 swipe JSON）可产生秒级数十条输入
→ 200 条+/秒量级 INFO。为潜在最大爆发源（e2e 期间仅 18 次输入未显形）。

### 1.4 其他事实

- `scrcpy_server_log`（scrcpy.py:292）实测 0 条：v4.1 启动后 stderr 静默；
  启动等待期读取已是 debug（:263）。保留 INFO 为潜在风暴源（异常 ROM 的
  server 若持续输出会逐行 INFO）；
- `frame_before_config`（video.py:194/204/228）：config 未下发期间每帧 INFO
  的分支存在但未引爆（正常流 SPS/PPS 首包即到）；raw 兜底缺 SPS/PPS 时
  可每帧刷屏——防御性治理；
- **落盘增长**：打包版日志（`logs/openscrcpy.log`）为追加模式、无轮转
  （launcher.redirect_std_streams，backend/app/core/launcher.py:128）；
  降噪直接减缓文件增长。日志轮转是独立议题，本方案不引入。

## 二、设计（按幂等性精准降级，不引入限速器）

### 2.1 选型：降级而非限速

清单与用户口径曾提「限速/降级」两手段，选**降级**：

- 实测表明机器人内容是**幂等重发**（SPS 99.9% / PPS 100% / session 79%
  与上次相同）——按「内容是否变化」降级可精准保留全部有信息的条目；
- 限速器（token bucket）会随机丢弃信息尾部，排障时恰缺关键几条；对
  幂等重发而言，丢弃与降级等价但限速实现更重；
- 降级至 debug：默认 INFO 级别零噪音；排障时把 `app.log_level` 调
  DEBUG（配置文件 / `OPENSCRCPY_` 前缀环境变量）一键恢复全量。

### 2.2 治理清单（7 项）

| # | 日志点 | 位置 | 现状 | 治理 |
|---|--------|------|------|------|
| 1 | `sps_received` / `pps_received` | video.py:130/135 | 每次到达 INFO | 与已缓存值不同（首次/参数变化）→ INFO；相同（幂等重发）→ debug |
| 2 | `input_received` / `sending_input_via_encoder` / `input_sent` | video.py:350/357/361 | 每输入 3 条 INFO | 全部降 debug |
| 3 | `send_input_called` / `sending_touch` / `sending_long_press` | scrcpy.py:592/610/620 | 每输入 1–2 条 INFO | 全部降 debug |
| 4 | `session_meta_received` | scrcpy.py:560 | 每次 12B 包 INFO | 宽高变化 → INFO；不变 → debug |
| 5 | `control_resolution_updated` | control_sender.py:75 | 每次调用打点 | 分辨率实际变化才打 INFO（相同直接提前 return） |
| 6 | `frame_before_config` | video.py:194/204/228 | config 前每帧 INFO | 仅首帧打一次（flag），其余静默 |
| 7 | `scrcpy_server_log` | scrcpy.py:292 | 逐行 INFO | 降 debug（对齐 :263 启动等待期；实测 0 条，防御性） |

关键实现约束：

- 第 1 项只改**打点条件**，幂等判断与 config 重发的既有语义（方案 19
  终审 Minor #3：SPS 分支只做变化检测、PPS 分支配对发送）**不减不改**；
- 第 4 项首次接收时 `_resolution==(0,0)` 必然变化 → INFO 保留；
- 第 5 项 `update_resolution` 的提前 return 语义与第 4 项变化检测一致
  （两者叠加时同一次变化最多 2 条 INFO，低频可接受）。

### 2.3 预期收益

- 活跃流时段日志量降 **~75%**（SPS/PPS 67% + session/resolution 4% +
  输入 2% 部分）；交互使用时（拖动爆发）改善更大；
- 治理后残余 INFO：每会话级低频事件（启停/重启/idle reset/前 5 帧/
  参数变化），保持运行概览可读性。

### 2.4 明确不做

- `video_chunk_progress` 周期调整（每 100 chunk ≈ 3.3s 已合理；改动还会
  牵动既有测试语义，收益小）；
- uvicorn access log（HTTP 请求 + WS 连接事件，生产使用下近乎为 0）；
- 通用限速器、日志轮转/大小上限（独立议题，另议）；
- P3 另两项（每帧 60 个事件循环对象、raw 模式潜在秒级延迟）——待
  spike 量化后另立方案。

## 三、测试方向（TDD）

日志断言采用 `structlog.testing.capture_logs()`（测试环境 structlog
未 configure、无级别过滤，可直接捕获含 `log_level` 的条目；项目尚无
日志断言先例，本次建立模式）。

`tests/unit/test_video.py`（FakeStreamService/video_client 基建已有）：

1. **SPS/PPS 幂等降级**：同一 SPS/PPS 再次到达 → capture 中无 INFO 级
   `sps_received`/`pps_received`（debug 级存在）；不同 SPS/PPS → INFO +
   config 重发行为不回归（既有
   `test_packet_mode_merges_nalus_and_intercepts_sps_pps` 联动验证）；
2. **输入链降级**：touch 事件转发 → `input_received`/`sending_input_via_encoder`/
   `input_sent` 均为 debug；转发行为与 restarting 通知不回归；
3. **frame_before_config 一次性**：config 未就绪期间多帧到达 → INFO 至多 1 条。

`tests/scrcpy/test_scrcpy_encoder.py`：

4. **send_input 降级**：`send_input_called`/`sending_touch` 为 debug；控制
   发送行为不回归；
5. **session_meta 幂等降级**：同宽高 12B 包二次到达 → debug；宽高变化 →
   INFO + `update_resolution` 调用不回归。

control_sender 对应用例：`update_resolution` 传入相同值 → 无 INFO 且
不触发重复状态更新。

门禁：pytest 全量 + ruff + mypy strict（零新依赖）。

## 四、验收（实施后回填）

- 单测全绿 + 覆盖率门禁不变；
- 真机（.18/.25）回归：e2e `video-stream` / `stream-stability` 用例 passed；

  （预期活跃流时段 INFO 降 ~75%）；
- 排障可用性抽查：`app.log_level=DEBUG` 下输入链/SPS 明细完整可见。

## 六、风险与边界

| 风险 | 缓解 |
|------|------|
| 输入链降 debug 后常规排障缺输入明细 | DEBUG 级别一键恢复；在 docs/经验记录.md 补注「输入链路排障开 DEBUG」 |
| SPS/PPS 打点条件改动波及 config 重发链路 | 只动日志行与打点条件，变化检测语义不动；回归含「变化时重发 config」既有用例 |
| `scrcpy_server_log` 降 debug 后 server 崩溃信息不可见 | 崩溃诊断链已有 `server_process_ended`/returncode/error 事件；需要时 DEBUG |
| session/resolution 条件化后丢失「重发频率」观测 | 频率本身是幂等噪音，无观测价值；确需时 DEBUG |
