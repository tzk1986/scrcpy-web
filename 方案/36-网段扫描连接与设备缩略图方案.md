## 一、问题（诉求与现状）

诉求：输入一个网段（如 `192.168.8.0/24`）→ 自动扫描开放 5555 端口的主机 →
自动尝试 adb 连接 → 连接成功的设备出现在设备列表中，并**展示其屏幕缩略图**，
让用户在多设备场景下一眼分辨「这台设备屏幕上是什么」。

现状差距：

1. 设备接入只有「单台手动输入 IP:port」路径（Dashboard「添加设备」dialog →
   POST /api/devices/connect）——网段批量接入无。
2. 设备列表为纯文本行（设备ID/型号/系统/分辨率/电量/状态/操作），无屏幕预览。
3. 后端无网段解析工具（`ipaddress` 依赖已有，但仅用于 IPv6 相关逻辑）——
   CIDR 解析需新增。

## 二、调研事实（spike 证据 + 代码定位）

### 2.1 spike 实测（2026-10-10）

| 测量 | 结果 |
|------|------|
| `192.168.8.0/24` 全段 254 地址、254 并发 `asyncio.open_connection` 探测 5555（2s 超时/台） | **2.02s**，发现 18 台开放主机 |

### 2.2 现有可复用代码（核验结论）

| 复用点 | 现状 |

| `_port_has_listener`（launcher.py:54-87） | `socket.connect_ex` 模式参照 |

### 2.3 关键事实约束

- 无截图缓存层：截图每次实时 screencap（~1s/台）——缩略图需要前端 TTL 缓存控制频率。
- StreamService 视频流按设备独占 token——多路 H264 实时缩略图流不可行。
- 扫描出的 18 台开放主机**不全是 adb 设备**（5555 可被任意服务占用）→
  必经 `adb connect` 逐台过滤（connect_tcp 判定语义即过滤）。
- `connect_tcp` 服务层内含 `repo.save`（有状态写入）——批量连接时
  并发 gather 调用，各设备 ID 独立，asyncio 单线程下安全。
- Windows 下 ProactorEventLoop 已配置（run_server.py）——254 并发
  open_connection 无平台坑（spike 即在 Windows 实测）。

## 三、设计（D1-D6：探测 → 编排 → 端点 → 批量连接 → 缩略图 → 前端 UI）

### D1 网段探测（基础设施层）

`reachability.py` 新增：

```python
async def scan_open_hosts(
    network: IPv4Network,
    port: int = 5555,
    concurrency: int = 254,
    probe_timeout: float | None = None,
) -> list[str]
```

- 输入为已解析的 `IPv4Network`（解析/校验在接口层，见 D3）；
- `asyncio.Semaphore(concurrency)` + 逐 host `open_connection` 探测
  （复用 probe_tcp 的异常分类逻辑，但**不抛异常**：单台不可达吞掉，仅成功者入结果）；
- 结果稳定排序（ipaddress 数值序）、含 `.0` 网络地址与 `.255` 广播地址
  （`ip_network().hosts()` 已排除，无需特判）；
- `concurrency` 默认取 `settings().adb.scan_concurrency`（config 新增，默认 254
  ——spike 实测值，注释依据）。

**上限保护（接口层）**：前缀长度 **/22 至 /32**（1-1024 个地址）。超出 /22
返回 422（信息含上限说明）。依据：spike 254 并发 /24 = 2.02s → /22 = 4 批
约 8s，仍是「一次点击内可等」的时长；/16 需分钟级，不提供。

### D2 扫描连接编排（应用层）

`DeviceService` 新增：

```python
@dataclass
class ConnectAttempt:
    ip: str
    ok: bool
    device_id: str | None = None
    reason: str | None = None   # not_adb_device / unreachable / error

@dataclass
class ScanResult:
    cidr: str
    probed: int
    open_hosts: list[str]
    connect_results: list[ConnectAttempt]
    truncated: bool = False

async def scan_and_connect(
    self, cidr: str, connect: bool = True, port: int = 5555
) -> ScanResult
```

- **互斥**：`self._scan_inflight: bool`——asyncio 单线程下「检查-置位」原子；
  重复请求抛 `ScanBusyError`（新领域异常）→ 409。`finally` 复位。
- **阶段 1**：`scan_open_hosts`。
- **阶段 2（connect=true）**：
  - 对全部开放主机 `gather(self.connect_tcp(ip, port), return_exceptions=True)`
    ——`return_exceptions=True` 必不可少：单台失败不取消其余（防孤儿 adb 进程，
    同方案 35 D2 先例）；
  - **连接并发上限 16**（信号量，常量注释依据：16 台 × 每台 probe+connect
    ~1-2s 摊薄后单批 ≤2s）；
  - 结果三分类：`connect_tcp` 正常返回 → `ok`（含 already connected）；
    `DeviceUnreachableError` → `unreachable`（扫描已确认可可达，此处基本不会
    触发，保底分类）；其余异常 → `not_adb_device`（端口开放但非 adb 服务，
    adb connect 输出不含 connected）。
- **截断保护**：开放主机数超过 `MAX_CONNECT = 64`（模块常量）时仅对前 64 台
  执行阶段 2，其余记入 `open_hosts` 不连接，`truncated=True`。病态场景
  （网段内大量非 adb 的 5555 服务）全链路最坏时长上界：
  探测 8s（/22）+ 64/16×2s ≈ 16s ≤ 30s，仍为同步响应可接受范围。
  正常场景（家庭/办公网，开放主机 ≤20）：探测 2s + 连接 ~2s ≈ 5s 内。

### D3 HTTP 端点

POST `/api/devices/scan`，body `{cidr: str, connect: bool = true, port: int = 5555}`：

- pydantic 模型 + validator：`ipaddress.ip_network(cidr, strict=False)`；
  非 IPv4 或前缀 <22 → 422（中文错误信息）；
- 同步返回 ScanResult（序列化 JSON）——无异步任务/进度轮询（决策见「不做」）；
- 注入安全性：ip 均产自 `IPv4Address` 对象（无用户字符串直达 shell），
  `adb connect "ip:5555"` 参数化调用——无命令注入面。
- 语义：**只连接不查信息**。连接成功后设备经「阶段 2 的 repo.save」入库，
  前端拿到响应后走既有 `fetchDevices()` 静默刷新（方案 35 D6 已有 silent
  能力），信息由列表补齐——与方案 35「连接成功判定 = adb connect 成功」口径一致。

### D4 批量连接细节核验（实施注意）

- connect_tcp 内 probe 预检与扫描探测**重复**——接受冗余：单台多付 ~一次
  TCP connect（毫秒级，端口已确认开放），换取零新 adb 代码；扫描阶段的
  过滤价值在前（快速排除端口不开放的 254 台中 236 台）。
- 「already connected」自然判成功（2.2 已核验）——重复扫描幂等，且刚连过的
  设备二扫不产生副作用。
- 已离线设备：connect_tcp 失败属正常过滤路径，不影响整体。

### D5 列表缩略图（前端 + 复用现有截图端点）

数据流：`GET /api/devices/{id}/screenshot?format=png` → blob URL → `<el-image>`。

- **定位：静态快照，非实时视频**。StreamService 设备独占 + 多路 H264
  缩略解码复杂度高；需求本质是「分辨这台设备在跑什么」，快照已满足。
- **前端会话缓存**：`Map<deviceId, {objectUrl, ts}>`，TTL 30s——命中直接
  显示，过期/缺失才重拉（单台 ~1s 设备端执行，缓存避免每次进页面全表打设备）。
- **并发池 3**：批量加载时同时最多 3 台 screencap（对设备温和，避免 N 台
  并发争抢单台设备的 adb 通道与 CPU）。
- **触发时机**：
  1. 扫描成功后：对 `connect_results` 中 `ok` 的设备自动加载缩略图
     （满足「连接成功并返回屏幕展示到列表」的核心诉求）；
  2. 列表缩略图列常驻「点击加载」占位（已有设备按需加载，不自动全表拉取）；
  3. 全局「刷新缩略图」按钮 + 单行刷新 icon。
- 与截图模式（详情页实时帧链路）共用 screencap：adb 单管道排队，无冲突但
  可能轻微延迟——可接受，记录在案。

### D6 前端 UI

- **网段扫描区**（工具栏/顶部操作区）：
  - `el-input`（placeholder `192.168.8.0/24`）+ 整数端口输入（默认 5555）+
    「扫描并连接」按钮 + `checkbox`「仅扫描不连接」（默认不勾，对应
    `connect: true`）；
  - 扫描中：按钮 loading + 状态文案「正在扫描网段…」；完成后：`el-alert`
    结果回显（探测 N 台 / 发现开放 M 台 / 连接成功 K 台 / 失败原因分类摘要）
    + `void fetchDevices()` 静默刷新 + 对新成功设备启动缩略图加载（D5）。
- **「屏幕」列**（el-table 新列，置于设备ID之后）：缩略图（40×70 卡片，
  `<el-image>` 点击预览放大）+ loading 态 + 「点击加载」占位；hover 显示
  快照时间。
- 「添加设备」dialog 保留不变（单台手动连接仍是场景之一）。
- 扫描 409（并发冲突）与 422（网段非法）错误提示走既有消息组件。

### 已取消 / 不做

- **异步扫描任务 + 进度轮询端点**：同步响应 + 截断保护（最坏 ≤24s、正常
  ≤5s）已满足，任务状态机复杂度不值。
- **实时视频缩略图（多路 H264 缩略解码）**：StreamService 独占语义冲突 +
  复杂度高，静态快照满足需求。
- **IPv6 网段扫描**：不支持，422 拒绝（adb 无线调试 IPv6 场景几乎不存在）。
- **批量截图后端端点**（一次请求多台）：复用现有点对点端点 + 前端并发池
  已够，后端零新增截图代码。
- **扫描结果持久化/历史**：一次性操作，不入库。

## 四、测试方向（TDD）

后端（tests/application/test_device_service.py + tests/infrastructure +
tests/unit/test_http_devices.py）：

1. **CIDR 校验**：非法字符串 / `/21`（超上限）/ IPv6 → 422；`/24`、`/32`
   合法 → 200（HTTP 层）。
2. **探测并发生效**：注入 fake probe（monkeypatch `open_connection`），
   254 目标记录同时 in-flight 峰值 ≥200（串行恒为 1），总时长 <3s，结果
   稳定排序。
3. **单台失败吞掉**：fake 中某 host 抛 TimeoutError → 不入结果、其余正常。
4. **编排分类**：mock scan 返回固定 open_hosts（8 台）+ mock connect_tcp
   4 成功 / 2 DeviceUnreachableError / 2 AdbError → 结果 ok=4、
   unreachable=2、not_adb_device=2。
5. **截断**：mock 65 台开放 → `connect_tcp` 仅调用 64 次、`truncated=True`。
6. **互斥**：并发两个 `scan_and_connect` → 一个 409（ScanBusyError）；
   结束后下次扫描恢复（finally 复位）。
7. **阶段 2 失败不掀翻**：connect_tcp 全抛异常 → 响应仍返回（逐台分类），
   无 unhandled task 异常（return_exceptions 语义锁定）。
8. **connect=false**：仅探测返回，connect_tcp 零调用。

前端（frontend/src/stores/device.test.ts + Dashboard.test.ts）：

9. **scanSubnet**：mock api → 结果状态落 store、成功后触发 silent
   fetchDevices + 新设备缩略图加载。
10. **缩略图 TTL**：假时钟推进 30s → 对象过期重拉（api 调用数 +1）；
    未过期命中（调用数不变）。
11. **并发池 3**：6 台同时加载 → screenshot api 同时 in-flight ≤3。
12. **Dashboard 渲染**：扫描按钮 loading 态、结果 alert 文本、缩略图列
    img（blob URL）渲染、「点击加载」占位（注意既有测试的表格 stub 限制，
    同方案 35 用例 13 的做法补渲染行 stub）。

e2e：不入 CI 常规集；fixtures 不加扫描（依赖真实网段环境），由真机手工
spike 覆盖（见验收）。

## 七、风险与边界

| 风险 | 缓解 |
|------|------|
| 254 并发扫描对局域网压力 | 仅 TCP connect 无载荷、spike 实测 2s 完成、单任务互斥、仅用户主动触发；/22 地址上限 |
| 病态网段长耗时（大量开放主机） | MAX_CONNECT=64 截断 + 同步响应有界（最坏 ≤24s）+ 前端 loading 明示 |
| 扫描期间并发请求 | `_scan_inflight` 互斥 409（asyncio 单线程原子） |
| 缩略图增加设备负载 | 按需 + TTL 30s 缓存 + 并发池 3 + 手动刷新；不自动全表轮询 |
| 缩略图与详情页截图模式并发 screencap | adb 单管道排队，轻微延迟可接受；记录在案 |
| 快照陈旧（设备画面已变） | 30s TTL + 手动刷新 + hover 显示快照时间 |
| 非 adb 主机（5555 被他服务占用） | adb connect 输出判定过滤（connect_tcp 既有语义），单测锁分类 |
| 公网/非私网网段误扫 | 工具绑定 127.0.0.1 仅本机可用；扫描为无载荷 TCP 探测无破坏性；不禁私网（VPN 网段 10.x 属正常场景） |
