## 一、问题（诉求与现状）

诉求：输入一个网段（如 `192.168.8.0/24`）→ 自动扫描开放 5555 端口的主机 →
自动尝试 adb 连接 → 连接成功的设备出现在设备列表中，并**展示其屏幕缩略图**，
让用户在多设备场景下一眼分辨「这台设备屏幕上是什么」。

现状差距：

1. 设备接入只有「单台手动输入 IP:port」路径（Dashboard「添加设备」dialog →
   POST /api/devices/connect）——网段批量接入无。
2. 设备列表为纯文本行（设备ID/型号/系统/分辨率/电量/状态/操作），无屏幕预览。
3. 后端无网段解析工具（`ipaddress` 依赖已有，但仅用于 IPv6 相关逻辑）——
   CIDR 解析需新增。

### 2.3 关键事实约束

- 无截图缓存层：截图每次实时 screencap（~1s/台）——缩略图需要前端 TTL 缓存控制频率。
- StreamService 视频流按设备独占 token——多路 H264 实时缩略图流不可行。
- 扫描出的 18 台开放主机**不全是 adb 设备**（5555 可被任意服务占用）→
  必经 `adb connect` 逐台过滤（connect_tcp 判定语义即过滤）。
- `connect_tcp` 服务层内含 `repo.save`（有状态写入）——批量连接时
  并发 gather 调用，各设备 ID 独立，asyncio 单线程下安全。
- Windows 下 ProactorEventLoop 已配置（run_server.py）——254 并发
  open_connection 无平台坑（spike 即在 Windows 实测）。

## 三、设计（D1-D6：探测 → 编排 → 端点 → 批量连接 → 缩略图 → 前端 UI）

### D1 网段探测（基础设施层，经 Protocol 暴露）

**层级**（走查裁决）：走 `domain/ports.py` 的 `AdbDriver` Protocol 正统路径，
不随 4 处既有漂移直 import（DEVELOPMENT.md 约束 3）。三处改动：

1. `domain/ports.py` `AdbDriver` 新增：

```python
async def scan_hosts(
    self,
    network: IPv4Network,
    port: int = 5555,
    timeout: float | None = None,
    concurrency: int | None = None,
) -> list[str]:
    ...
```

2. `infrastructure/adb/reachability.py` 新增模块函数 `scan_open_hosts(...)`
   （实现体；惰性默认：`timeout=None` → `settings().adb.probe_timeout`、
   `concurrency=None` → `settings().adb.scan_concurrency`，需补
   `from app.core.config import settings`——cli.py 同层先例）；
3. `infrastructure/adb/cli.py` `AdbCliDriver.scan_hosts` 薄包装调 1 行。

实现要点：

- `asyncio.Semaphore(concurrency)` + 逐 host `open_connection` 探测；
- **静默分类**（不逐台打日志）：catch `asyncio.TimeoutError /
  ConnectionRefusedError / socket.gaierror / OSError` 四类 → 该台不入结果；
  结束打一条汇总日志（`scan_completed`：总数/发现数/耗时）。**不复用 probe_tcp
  逐台调用**——否则 /24 扫描产生约 236 条 warning 污染运行日志（走查发现）；
- 目标取 `list(network.hosts())`（**天然排除 .0 网络地址与广播地址**；
  /24 = 254 台、/22 = 1022 台）；结果稳定排序（ipaddress 数值序）。

**上限保护（接口层）**：前缀长度 **/22 至 /32**（/32 = 1 地址 … /22 = 1022
主机）。越界返回 422（中文信息含上限说明）。依据：spike 254 并发 /24 = 2.02s
→ /22 ≈ 4 批 ≈ 8s，仍是「一次点击内可等」的时长；/16 需分钟级，不提供。

### D2 扫描连接编排（应用层）

`DeviceService` 新增（`ConnectAttempt`/`ScanResult` dataclass 置于
`device_service.py` 模块内；`MAX_CONNECT = 64` 模块级常量，同
`_COOLDOWN_SECONDS`/`_INFO_CONCURRENCY` 先例；`_scan_inflight: bool` 加入
`__init__` 字段列表）：

```python
@dataclass
class ConnectAttempt:
    ip: str
    ok: bool
    device_id: str | None = None
    reason: str | None = None   # unreachable / connect_failed / error
    message: str | None = None  # 失败摘要（异常/输出短文本，前端回显）

@dataclass
class ScanResult:
    cidr: str                   # str(network)
    probed: int
    open_hosts: list[str]
    connect_results: list[ConnectAttempt]
    truncated: bool = False

async def scan_and_connect(
    self, network: IPv4Network, connect: bool = True, port: int = 5555
) -> ScanResult
```

- **签名口径**（走查裁决）：service 收已解析的 `IPv4Network`（解析/校验在
  接口层，见 D3；`ScanResult.cidr = str(network)`）。
- **互斥**：`self._scan_inflight: bool`——asyncio 单线程下「检查-置位」原子
  （同 `_get_info_cached` 先例）；重复请求抛 `ScanBusyError` → 409。
  `finally` 复位。
- **阶段 1**：`await self.adb.scan_hosts(network, port)`（Protocol 调用）。
- **阶段 2（connect=true）**：
  - 对全部开放主机 `gather(self.connect_tcp(ip, port, timeout=_SCAN_CONNECT_TIMEOUT),
    return_exceptions=True)`——`return_exceptions=True` 必不可少：单台失败不
    取消其余（防孤儿 adb 进程，同方案 35 D2 先例）；
  - **连接并发上限 16**（本地信号量，`_SCAN_CONNECT_CONCURRENCY` 模块常量）；
  - **单台连接短超时**（走查裁决）：`_SCAN_CONNECT_TIMEOUT = 5s` 经
    `connect_tcp` timeout 透传（见 D4）——非 adb 服务在握手阶段静默时可拖满
    默认 30s，不加此值最坏 64/16×30 = 120s；
  - 结果三分类：`connect_tcp` 正常返回 → `ok`（含 already connected）；
    `DeviceUnreachableError` → `unreachable`（扫描已确认可达，此处基本不
    触发，保底分类）；其余异常（`AdbError` 等）→ `connect_failed`
    （覆盖「非 adb 服务」「握手超时」「adb 子进程异常」；`message` 附异常短
    摘要，前端回显分类）。连接失败不打断整体。
- **截断保护**：开放主机数超过 `MAX_CONNECT = 64` 时仅对前 64 台执行阶段 2，
  其余记入 `open_hosts` 不连接，`truncated=True`。全链路最坏时长上界：
  探测 ≈8s（/22）+ 连接 64/16×5s = 20s → **≤30s**（前端超时 40s 内）。
  正常场景（家庭/办公网，开放主机 ≤20）：探测 2s + 连接 ~2s ≈ 5s 内。
- **并发落库说明**（走查修正措辞）：阶段 2 并发 `repo.save` 走 aiosqlite
  连接池（池大小 5）+ WAL + busy_timeout=5000——排队串行落库，无正确性
  风险。

### D3 HTTP 端点

POST `/api/devices/scan`，**query 参数** `cidr: str, connect: bool = True,
port: int = 5555`（走查裁决：仓库全仓无 pydantic 对象 body 先例，且
`docs/API.md:33` 明文约定「创建端点参数放查询串」——与 /connect 端点同构）：

- CIDR 校验（handler 内）：`ipaddress.ip_network(cidr, strict=False)` 解析；
  非 IPv4 / 前缀不在 /22-/32 → raise `InvalidScanRangeError`（下一条）；
- **异常归属统一 `backend/app/core/exceptions.py`**（走查裁决：全仓唯一
  异常定义位置，handler 按 status_code 自动映射，零 main.py 改动）：
  - `class ScanBusyError(OpenScrcpyException): status_code = 409`（code
    `SCAN_BUSY`，中文 message）——扫描互斥；
  - `class InvalidScanRangeError(OpenScrcpyException): status_code = 422`
    （code `INVALID_SCAN_RANGE`）——CIDR 非法/超上限；
- 同步返回 ScanResult（序列化 JSON）——无异步任务/进度轮询（决策见「不做」）；
- 端点插入位置：`POST /connect`（devices.py:224）邻近；无路由遮蔽（唯一
  单段 POST 字面路径）；
- 注入安全性：ip 均产自 `IPv4Address` 对象（无用户字符串直达 shell），
  `adb connect "ip:5555"` 参数化调用——无命令注入面。
- 语义：**只连接不查信息**。连接成功后设备经「阶段 2 的 repo.save」入库
  （info 查询失败也不影响连接入库语义，同 connect_tcp 现状），前端拿到
  响应后走既有 `fetchDevices()` 静默刷新（方案 35 D6 已有 silent 能力），
  信息由列表补齐——与方案 35「连接成功判定 = adb connect 成功」口径一致。
- **「新成功设备」识别**（走查补写）：前端直接用响应 `connect_results` 中
  `ok=true` 的 `device_id` 集合触发缩略图加载，不做列表 diff。

### D4 批量连接细节核验（实施注意）

- **connect_tcp timeout 透传**（走查裁决，新增小改）：`AdbCliDriver.connect_tcp`
  与 `AdbDriver` Protocol 签名加 `timeout: int | None = None`，传入既有
  `_run(..., timeout=timeout)`（cli.py:69 已支持该参数，3 行级改动）；
  `device_service.connect_tcp` 同步透传；默认 None 保持现状
  （`settings().adb.timeout`=30s，`POST /connect` 语义不变）。扫描编排路径
  传 `_SCAN_CONNECT_TIMEOUT=5s`（理由见 D2）。测试 fake（MagicMock）无碍。
- connect_tcp 内 probe 预检与扫描探测**重复**——接受冗余：单台多付 ~一次
  TCP connect（毫秒级，端口已确认开放），换取零新 adb 探测代码；扫描阶段的
  过滤价值在前（快速排除端口不开放的 254 台中 236 台）。
- 「already connected」自然判成功（`"connected" in output.lower()` 子串
  判定，已核验 cli.py:348；失败输出 "failed to connect"/"unable to connect"
  均不含该子串）——重复扫描幂等。
- 已离线设备：connect_tcp 失败属正常过滤路径，不影响整体。

### D5 列表缩略图（前端 + 复用现有截图端点）

数据流：`GET /api/devices/{id}/screenshot?format=png` → blob URL → `<el-image>`
（走查核实：blob+objectURL 有先例 videoStream.ts:320 等；无鉴权无自定义
header，机制可行）。

- **定位：静态快照，非实时视频**。StreamService 设备独占 + 多路 H264
  缩略解码复杂度高；需求本质是「分辨这台设备在跑什么」，快照已满足。
- **前端会话缓存**（走查修订）：`ref<Record<deviceId, {url, ts}>>`
  响应式载体（**非裸 Map**——Vue 响应式不会跟踪裸 Map 的增改；Pinia state
  以可序列化 plain object 为惯例），新 state 与 action 须加入 store 的
  return 暴露区（device.ts:198-209）。TTL 30s——命中直接显示，过期/缺失
  才重拉（单台 ~1s 设备端执行，缓存避免每次进页面全表打设备）。
- **revoke 策略**（走查补写）：TTL 过期换新前 revoke 旧 objectURL（先例
  videoStream.ts:316-321）；设备从列表移除（断开）时清理条目并 revoke；
  store 常驻不负责页面卸载清理。
- **并发池 3**（走查补细节）：批量加载时同时最多 3 台 screencap（对设备
  温和）；store/services 无信号量先例，自建 3 槽队列且 in-flight 数可观测
  （支撑测试并发峰值 ≤3 断言）；**同设备 in-flight 去重合并**（重复点击/
  行复用不重复请求）。
- **失败态**（走查补写）：截图失败（设备离线/超时）显示「加载失败 + 重试」
  占位；**失败不写入 TTL 缓存**（下次点击直接重拉）。
- **触发时机**：
  1. 扫描成功后：对 `connect_results` 中 `ok=true` 的设备自动加载缩略图
     （满足「连接成功并返回屏幕展示到列表」的核心诉求）；
  2. 列表缩略图列常驻「点击加载」占位（已有设备按需加载，不自动全表拉取）；
  3. 「刷新缩略图」按钮 + 单行刷新 icon（落位约束见 D6）。
- 与截图模式（详情页实时帧链路）共用 screencap：adb 单管道排队，无冲突但
  可能轻微延迟——可接受，记录在案。

### 已取消 / 不做

- **异步扫描任务 + 进度轮询端点**：同步响应 + 截断 + 短超时保护（最坏
  ≤30s、正常 ≤5s）已满足，任务状态机复杂度不值。
- **实时视频缩略图（多路 H264 缩略解码）**：StreamService 独占语义冲突 +
  复杂度高，静态快照满足需求。
- **IPv6 网段扫描**：不支持，422 拒绝（adb 无线调试 IPv6 场景几乎不存在）。
- **批量截图后端端点**（一次请求多台）：复用现有点对点端点 + 前端并发池
  已够，后端零新增截图代码。
- **扫描结果持久化/历史**：一次性操作，不入库。

## 七、风险与边界

| 风险 | 缓解 |
|------|------|
| 254 并发扫描对局域网压力 | 仅 TCP connect 无载荷、spike 实测 2s 完成、单任务互斥、仅用户主动触发；/22 地址上限 |
| 病态网段长耗时（大量开放主机 + 握手静默） | MAX_CONNECT=64 截断 + **单台连接短超时 5s**（走查修订：原设计最坏 30s/台） + 同步响应有界（最坏 ≤30s）+ 前端超时 40s 内 + loading 明示；负向 spike 实测锁定 |
| 扫描日志噪音（236 台失败逐条 warning） | scan_open_hosts 静默分类 + 仅汇总日志（走查修订） |
| 扫描期间并发请求 | `_scan_inflight` 互斥 409（asyncio 单线程原子） |
| 缩略图增加设备负载 | 按需 + TTL 30s 缓存 + 并发池 3 + 手动刷新；不自动全表轮询 |

| 截图失败（设备离线/超时） | 「加载失败 + 重试」占位；失败不写 TTL 缓存（走查补写） |
