# 方案 22：恢复探针判据相位敏感修复（卡死自愈后滞留截图模式）

- 日期：2026-09-23
- 状态：已实施并真机验收通过（结论见 §六）
- 关联：[20-推流HARD超时误判修复](./20-推流HARD超时误判修复.md)（真机复测第 3 步暴露）、
  [19-推流连接稳定性优化](./19-推流连接稳定性优化.md)（实施项 2 前端探针本体的引入）、
  `frontend/src/services/videoFallback.ts`（`evaluateH264Recovery`）

## 一、问题

### 1.1 现象（方案 20 真机复测暴露，2026-09-23）

.25 卡死注入后（复测第 3 步 run4）：后端已自愈重启编码器、WS 持续
转发帧（页面内采样器 bin 计数持续增长，均值 ~3.7fps），但前端**停留
截图模式 84s+**（用例结束时仍未回切），无角标、无「正在连接」、无报错。
同代码同设备另三次复测（run3/5/6）均在注入后 6.5-17.3s 回切成功——
**时快时慢，可复现的间歇缺陷**。

### 1.2 根因

**判决器**（videoFallback.ts）要求探针连续 3 个 2s 窗口（`WINDOW_MS`）
**每窗**帧数 ≥4（`MIN_FRAMES`，≈2fps 下限）且最新采样在 `FRESH_MS`(3s) 内。

**实测帧到达形态**（run4 时间线 bin 序列反推）：突发-静默交替，
~3s 一突发（约 1s 内 8-12 帧 + ~2s 静默）。后端日志佐证突发源为
设备端内容节律（该时段保活 `idle_reset_video_sent` 未触发，可排除
保活 IDR 驱动）。2s 探针窗与 3s 突发的相对相位决定窗口内容，相位
不利时窗序列形如 `[11,10,1,11,10,1,…]`——**每 3 窗必掉 1 窗，最长
连续达标仅 2 窗**，判据结构性不可满足。

**量化**（以 run4 实测到达序列模拟，相位步长 0.1s 扫描 20 个相位）：

| 相位 | 结果 |
|---|---|
| p=0.0-0.3（4/20） | 90s 内**永不触发** |
| 其余 16 个 | 触发延迟 6.6-63.9s（设计预期 ~6s） |

run4 恰落在永不触发区；run3/5/6 落在有利相位（验证：run5 实测回切
延迟 6.05s 与模型 p=0.6-0.8 区间 6.6-6.8s 吻合）。

**缺陷本质**：判据的「连续 3 窗」要求与帧到达的周期性掉窗形成共振——
窗宽（2s）×窗数（3）与出帧周期（~3s）成简单整数比时相位敏感被放大。

### 1.3 影响

- 卡死自愈后前端可能**永久滞留截图模式**（只读、输入失效），正是
  方案 19 实施项 2 要消灭的现象；
- 回切延迟不可预期（6-64s 或永不），用户感知为「恢复慢/恢复不了」；
- E2E 用例偶发失败（方案 20 复测第 3 步 4 次运行命中 1 次）。

## 二、修复设计

### 2.1 核心改动（videoFallback.ts `evaluateH264Recovery`）

判据由「逐窗严格」改为「窗口聚合 + 末窗非零」，保留 2fps 均值语义：

```ts
export const RECOVERY_THRESHOLDS = {
  WINDOWS: 3,
  MIN_TOTAL_FRAMES: 12,   // 近 3 窗（6s）总帧数下限 = 2fps × 6s
  WINDOW_MS: 2000,
  FRESH_MS: 3000,
}

// 近 3 窗总帧数 ≥ MIN_TOTAL_FRAMES 且末窗 ≥1 帧且最新采样新鲜 → 可回切
const recent = samples.slice(-WINDOWS)
const latest = recent[recent.length - 1]
if (now - latest.at > FRESH_MS) return false
if (latest.frames < 1) return false
return recent.reduce((s, r) => s + r.frames, 0) >= MIN_TOTAL_FRAMES
```

### 2.2 数值验证（同一实测序列，同相位扫描）

| 判据 | NEVER 相位 | 触发延迟 |
|---|---|---|
| 现状（3 窗各 ≥4） | 4/20 | 6.6-63.9s |
| **聚合（近 3 窗和 ≥12 且末窗 ≥1）** | **0/20** | **6.0-9.1s** |
| 备选（近 4 窗中 3 窗 ≥4） | 0/20 | 8.0-11.9s |

伪恢复序列（0.3fps 稀疏单帧）：聚合判据与现状一致地**正确拒绝**
（3 窗和 ≈1-3 « 12）；`[12,0,0]` 型「突发后静默」由末窗 ≥1 拒绝。

### 2.3 为何不是「降低 MIN_FRAMES」

- 降到 2：run4 形态仍失败（掉窗为 1-2 帧）；
- 降到 1：连 0.x fps 伪恢复也放行，违背原始设计意图（排除伪恢复）。
- 聚合形态同时满足「相位不敏感」与「伪恢复排除」，是唯一同时成立的
  简单形态；备选（近 4 窗中 3 窗）亦可但触发更慢。

### 2.4 不改清单

- 防横跳既有机制不动：回切后 30s 冷却（`resumeCooldownUntil`）、
  回退 watchdog 重新武装（`h264FallbackDone` 复位）、`FRESH_MS` 新鲜度；
- `suspend/resume`、探针节拍（2s）、`checkH264Fallback`、后端全部代码；
- 方案 20 的 HARD 守卫修复不动。

## 三、测试（TDD）

先写失败测试，再改实现。

1. **核心锁定（run4 形态）**：样本 `[11,10,1,11]` 序列下，第 4 窗后
   近 3 窗和 =22 ≥12 且末窗 11 ≥1 → 回切（旧判据在同序列永不回切，
   可用第 3 窗后 `[11,10,1]` → 旧 false 新 true 作为最小失败用例 →
   注意旧判据此处也是 false（1<4），修复后为 true，构成红→绿）；
2. **伪恢复拒绝**：`[0,0,1]`、`[1,0,1]` → 不回切（和 < 12）；
3. **突发后静默拒绝**：`[12,0,0]` → 不回切（末窗 0）；
4. **既有语义保持**：`[4,3,4]`（和 11 <12）→ 不回切；`[4,5,4]`、
   `[0,4,4,4]` → 回切；「最新采样过期」「采样不足 3 个」用例原样通过；
5. `resumeCooldownUntil` 路径（探针冷却）相关用例不回归。

实施流程照项目规范：失败测试先行 → 最小修复 → 全量门禁
（vitest/eslint/build；本修复不触后端，pytest 基线不回归）。

## 六、真机验收结论（2026-09-23，.25）

| 步骤 | 结果 |
|---|---|
| 1 卡死注入 ×5 连跑 | **PASS**：5/5 回切成功，注入→回切 16.61-17.29s 窄分布收敛（修复前 run4 滞留 84s+）；角标→出图 0.20-0.30s |
| 2 角标→出图 ≤2s 断言 | **PASS**：5/5 全过（修复前该断言在滞留形态下结构性必挂） |
| 3 WS 瞬断回归 | **PASS**：31.8s，回退→恢复路径不受聚合判据影响 |
| 4 静止观察 600s | **PASS**：帧 0→2296，回退日志 0 条，无横跳 |

**注入→回切时长构成说明**：16.6-17.3s ≈ 后端卡死检测链
（STALL 探针 ~10s + 编码器重启）+ 前端探针判据触发（~6s，
与 §2.2 数值验证 6.0-9.1s 吻合）。§四 期望表中「注入→回切
6-12s」仅覆盖前端判据部分、未含后端自愈链时长，实际端到端
以 16.6-17.3s 稳定收敛为准；本方案的验收判据是无滞留 + 窄分布
（对照修复前 84s+ 滞留或永不回切）。

**残留观察项**：设备端帧到达的突发-静默节律（§1.2 量化 ~3s
突发周期）不改——静态场景出帧率低是编码器正常行为，前端判据
已按该节律修正；若未来设备内容节律变化（如更长的突发放电周期），
`MIN_TOTAL_FRAMES`/`FRESH_MS` 需按新节律复核。
