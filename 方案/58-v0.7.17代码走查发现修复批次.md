## 三、T1——P1 六项逐项设计（建议首批实施）

### 3.1 58A-01 ｜ SQLite 池连接异常归还未回滚——半事务幽灵提交（数据完整性）

- **位置**：`backend/app/infrastructure/persistence/sqlite.py:78-86`（`connection()` 归还路径）；全文件 `grep rollback` 为 0 处。
- **证据**：`async with pool.connection() as conn: yield conn` 后 `finally: await self._pool.put(conn)`——不检查 `conn.in_transaction`、不回滚。各写方法（`save_session:198-209`、`save_logs_bulk:282-290`、`save_*_samples_bulk:786-794` 等）失败即抛异常出 with，隐式事务（isolation_level 默认 ''，首个 DML 自动 BEGIN）残留在连接上带回池。
- **影响**：任一条 INSERT/executemany 中途失败（db 满 / busy_timeout 超时 / 约束错误）→ 连接带未提交事务回池 → **下一个借用者首次 DML 在同一事务内继续执行，其 commit 把上一失败者的半批行一并提交**。批量日志/指标出现「半个批次幽灵提交」，残留事务还可能持锁加剧争用。
- **修复方案**：`connection()` finally 中 `try: await conn.rollback() except Exception: pass`（或按 `conn.in_transaction` 条件）后再 put。
- **测试点**：桩 `executemany` 中途抛错 → 断言归还连接 `in_transaction` 为 False；后续借用者插入不回放旧半批；正常路径 commit 行为不变。

### 3.2 58A-02 ｜ pull_recording 未显式传超时——大录屏被默认 30s 截断丢产物（数据丢失）

- **位置**：`backend/app/infrastructure/adb/cli.py:1353-1382`（调用点 :1376）；`_run` :415 `timeout = timeout or settings().adb.timeout`（默认 30，config/settings.py:135）。
- **证据**：`pull_recording` 调 `_run_serial(device_id, "pull", remote_path, local_dir)` **无 timeout 参数**——本文件 :852-869 `pull()` 注释自己写明「大文件传输须显式传长超时，否则默认 30s 会中断超过 30s 的拉取」；`application/recording_service.py:218` 调用处同样无超时能力。
- **影响**：默认 4M×60s≈30MB 尚可；8M 码率 + 长时长（time_limit 上限 1800s）产物数百 MB，经无线调试（10-40Mbps）拉取远超 30s → 超时 kill → AdbError → 会话置 FAILED，**录屏产物丢失**——与方案 42/51-E5「保全产物」方向直接相悖，录满+慢链路正是 51-E5 明示支持的场景。
- **修复方案**：`cli.pull_recording` 与 ports 协议补 timeout 参数，调用侧传 `time_limit + 60`（对齐 `start_recording` :1208-1210 的 time_limit+30 惯例），或设录屏专属 pull 超时配置项。
- **测试点**：单测断言 pull_recording 收到的 timeout 为 time_limit+60；真机冒烟大文件（可用 fake 慢 pull）验证不再 30s 截断。

### 3.3 58A-03 ｜ start() 早败窗口/枚举降级 → 设备端 scrcpy server 孤儿 → stray 检测永久阻断（需复核）

- **位置**：`backend/app/infrastructure/stream/scrcpy.py:368-375, 381, 1089-1103, 1158-1165, 1018-1049`。
- **证据**：socket 连接失败即 raise（:368-375），此时 `_remote_pids` 尚未枚举（:381 在连接成功之后）；枚举超时/异常一律返回 []（:1089-1103）；`stop()` 在 `_remote_pids` 为空时**完全跳过设备侧 kill**（:1158-1165）；下次 `start()` 残留检测命中即抛 `ScrcpyOccupiedError`（:183/1018-1049）。
- **影响**：两条支路留孤儿——① adb server 抖动/端口竞态致连接失败 → 上层 finally 调 `encoder.stop()` 但 pids 为空只杀本地 shell，设备端 app_process（tunnel_forward 下阻塞 accept）存活 → 无 FINALIZING 登记 → 该设备推流**终生阻断**直至手动清理；② 慢设备 `/proc` 全枚举踩 5s 超时返回 [] → 正常整场结束后 stop 同样杀不到设备侧，下次连接即被占用文案拦截。属方案 48 D2 / 51-B2 的覆盖空隙。触发概率需复核（低端机/慢存储易踩，如 .20 RK3568 A7）。
- **修复方案**：stop() 在 `_remote_pids` 为空但本地 process 存在时兜底重跑一次 `_enumerate_remote_pids` 再 kill，并登记 `_FINALIZING_PIDS`；或 start() 连接失败路径先执行一次枚举+设备侧 kill 再抛错。
- **测试点**：桩枚举抛超时 → 断言 stop 兜底重枚举 + kill 被调用、下次 start 不被 stray 阻断；真机 .20 连发起停 20 轮无孤儿（`ps -A | grep scrcpy`）。

### 3.4 58B-01 ｜ 一条畸形帧终结输入循环——全会话输入面静默失效

- **位置**：`backend/app/interfaces/ws/video.py:149-167`（`handle_input` 终身 while）、:523（`int(data.get("copy_key", 0) or 0)` 直转）；根因面 `backend/app/interfaces/ws/protocol.py:39-45`（`parse_video_input` 只校验顶层键型）。
- **证据**：循环仅捕 `WebSocketDisconnect`（:164-165），其余异常落入 :166-167 catch-all 后**直接结束 task、无重启**。触发向量：客户端发 `{"action":"clipboard_get","copy_key":"abc"}` → ValueError；发二进制帧 → `receive_text()`（:150）KeyError。
- **影响**：任意畸形帧（前端 bug 或被干扰的客户端）一发即杀整条输入通道——touch/key/text/clipboard 全静默失效，`restarting` 预告（:155-163）也不再下发（客户端 watchdog 宽限丢失）；视频照常播放，用户误以为设备无响应，只能重连。暴露面远大于单点报错。
- **修复方案**：① 循环体 per-message try/except（除 Disconnect 外记日志后 continue）；② protocol 层对已知 action 补嵌套字段类型校验，copy_key int 化失败按 0 处理或回 error 帧；③ 可加异常率阈值保活计数。与 8.1 横切「入站校验层」合并实施。
- **测试点**：WS 集成测：连发 copy_key 非 int / 二进制帧 / 未知 action → 断言后续 touch 帧仍被处理；单测 protocol 嵌套校验。

### 3.5 58D-01 ｜ 回退+截图错误态点「重新连接」= 画面永久冻结（方案 51 F1-01 残留半边）

- **位置**：`frontend/src/components/stream/VideoPlayer.vue:939-950`（reconnect）、`h264VideoStream.ts:285-296 / 393-417 / 545-556`、`backend/app/interfaces/ws/video.py:129 / 205-224`。
- **证据**：错误态「重新连接」按钮只调 `h264Stream.start()`；start() 仅清状态，**不重建解码器、不发 request_keyframe**；而 resume()（:394-417）有 `ws.send({op:'request_keyframe'})` + `initDecoder(_lastCodec, _lastAvccDesc)` 两条救命逻辑。后端同会话 config 只发一次（video.py:129 `config_sent`，仅 SPS/PPS 变化复位 :205-218）——手动重连不新建 WS、不触发新 SPS → 永无 config。
- **影响**：h264 回退截图模式后 videoStream 进 error 终态（方案 51 A01 的 30s 截屏超时路径）→ 用户点重连 → 解码器仍 null、无 config、每帧 noteDrop 不算探测帧、截图链路未重启、probe 永假、watchdog 因 `h264FallbackDone=true` 停摆 → **画面永久冻结直到整页刷新**。51-F1-01 只修了 `_suspended` 复位这半边。
- **修复方案**：reconnect() 改为「h264Stream 存在且 suspended 时走 resume()，否则 start()」，并同时重启 videoStream（截图模式仍是当前展示链路）；或在 start() 内镜像 resume() 的重建+请求关键帧逻辑。
- **测试点**：补「start() 后无 config 到达」用例（现 h264VideoStream.test.ts:1105-1117 人工重注入 CONFIG_MSG 掩盖了死路）；断言 reconnect 在 suspended 态调用 resume 路径、request_keyframe 发出、initDecoder 被调。

### 3.6 58E-01 ｜ FileManager 目录列表无请求代次——慢响应覆盖新目录（错误结果）

- **位置**：`frontend/src/views/FileManager.vue:195-218`（`cd`/`loadList`）。
- **证据**：`entries.value = await api.listFiles(props.id, currentPath.value)` 直接赋值；cd 仅改 `currentPath` 后 `await loadList()`，无请求代次/AbortController。
- **影响**：快速连点面包屑（或设备 A→B 直跳复用组件，方案 51 F2-15 路径）时，慢目录迟到响应覆盖新目录列表——表格内容与面包屑不一致，用户在新路径上勾选的实为旧目录条目，删除/下载作用错对象。
- **修复方案**：loadList 捕获发起时路径快照 + 代次计数（或 AbortController），响应返回校验路径/代次未变才写入。并入 8.3「请求代次/在飞守卫范式」横切批。
- **测试点**：单测模拟乱序响应（慢请求先发后至）→ 断言 entries 不被过期响应覆盖。
