# 方案 23：绿色版退出机制与单开模式（进程生命周期管理）

> **状态**：调研完成，待方案评审（2026-09-28）。
> **由来**：方案 15 打包产物投入使用后，用户提出三个使用问题（如何关闭 / 再启动是否双进程），
> 排查中发现一个端口探测缺陷（D1）。本方案覆盖退出机制与单开模式两块，并给出实施分解。
> **关联**：方案 15（§9.6 全链路验证、发布文档）、任务 4 shutdown 端点评估见 §5.2-T3。

## 1. 背景

### 1.1 使用中暴露的问题

| # | 用户问题/现象 | 本质 |
|---|--------------|------|
| Q1 | 关闭浏览器是否等于关闭服务？如何关闭？ | 缺退出通道：exe 无窗口、无托盘，用户唯一途径是任务管理器 |
| Q2 | 再启动一个 exe 会不会有两个进程？ | 单开模式的**用户预期确认**（现状已满足：mutex 互斥 + 二启只开浏览器） |
| Q3 | （排查中发现）双击的 exe 与 dev 服务同时占用 8765 | 端口探测缺陷 D1：通配绑定共存场景误判 |

### 1.2 缺陷 D1 实测证据（2026-09-28）

现场 netstat（两进程同时 LISTENING，同一端口号 8765）：

```
TCP    0.0.0.0:8765    0.0.0.0:0    LISTENING    42888   # dev 后端（uvicorn 绑 srv.host=0.0.0.0）
TCP    127.0.0.1:8765  0.0.0.0:0    LISTENING    45944   # 打包 exe（绑 127.0.0.1）
```

机制：
- Windows 允许「通配地址绑定（0.0.0.0:8765）」与「具体地址绑定（127.0.0.1:8765）」共存；
- 连接路由**具体地址优先**——浏览器访问 `127.0.0.1:8765` 被 exe 接受，`port.txt` 写 8765；
- `find_available_port`（`backend/app/core/launcher.py`）试绑 `127.0.0.1:8765` 成功 → 判定"可用" → exe 与 dev 服务**同端口号共存**、按来源地址分流。

后果：端口回退逻辑在最需要它的场景（同机已有一份服务在跑）失效；用户视角"两个界面/两份服务"混乱；局域网访问（0.0.0.0）与本地访问打到不同进程。

## 2. 调研：同类绿色/便携包怎么做

### 2.1 退出管理：四种主流模式

| 模式 | 做法 | 典型案例 | 优缺点 |
|------|------|---------|--------|
| M1 托盘图标 | 任务栏托盘右键菜单「退出」；关闭主窗口仅最小化 | Docker Desktop、Everything、qBittorrent 便携版、Clash 系 | 桌面应用标准体验；**需引入托盘技术栈**（pystray→pywin32+Pillow，或 ctypes 手写 Shell_NotifyIconW） |
| M2 UI 内退出 | Web 界面内「退出/关闭服务」按钮触发优雅停机 | Jupyter Lab「Shut Down」、Syncthing Web UI | **零新依赖**；web 服务天然契合（界面永远在）；需服务端停机端点 |
| M3 管理脚本 | 随包 `stop.bat`（taskkill）或 CLI 子命令 | nginx/redis Windows 绿色包、便携服务型工具 | 零成本兜底；需用户找到 bat；强制杀无优雅清理 |
| M4 保留控制台 | 不设 `--noconsole`，用户 Ctrl+C / 关窗 | 开发向工具（uvicorn 直跑） | 最直观、排错方便；牺牲「无窗口」体验，关错窗口有误杀风险 |

组合惯例：主流桌面工具 = M1（主）+ M3（排障兜底）；web 服务型 = M2（主）常见。

### 2.2 单开模式：Windows 单实例行业标准

业界共识（Microsoft 文档 + .NET/原生生态惯例）：

1. **Named Mutex 是标准机制**（非进程名扫描）——内核对象、原子创建、进程崩溃自动释放；
2. 创建用 `CreateMutex` + `GetLastError == ERROR_ALREADY_EXISTS` 判定（原子 check-and-create，无竞态）——**方案 15 任务 3 已按此实现**；
3. 命名规范：`Global\` 前缀（跨终端服务会话全局互斥）/ 无前缀（默认 `Local\`，每会话独立）；GUID 后缀防撞名。我们对每个用户桌面独立服务，`Local\` 语义（无前缀）**符合预期**；
4. **二启行为**：不只是退出，而是「激活已有实例」——GUI 应用用 `FindWindow + ShowWindow + SetForegroundWindow` 前置已有窗口；web 服务型等价物 = **打开浏览器指向已运行实例 URL**——**方案 15 任务 3 已实现**（读 `data/port.txt` 回放端口）；
5. 句柄保活：mutex 句柄须持有至进程结束（勿被 GC/作用域释放）——现实现为进程级持有，符合；
6. `AbandonedMutex` 语义：持有者崩溃后系统自动释放，下一次创建照常获得——CreateMutex 路径天然覆盖。

**结论：单开机制主体已达标**；待补的是 D1 修复与少量规范化（见 §4.2）。

## 3. 现状评估

### 3.1 已有能力（方案 15 交付，验证实证）

- 单实例互斥（`launcher.acquire_single_instance_mutex`，WinDLL use_last_error 修正后可靠）
- 端口探测回退（`find_available_port`，8765→8769 最多 5 个）
- 二启行为：读 `port.txt` → 浏览器指向已运行实例 → exit 0
- 就绪等待（15s 超时失败退出而非开死页）、文件日志、`port.txt` 落点

### 3.2 缺口 G1：无退出通道

无任何用户可达的停止方式：关闭浏览器只断开界面，服务继续占端口/轮询设备；唯余任务管理器。发布文档（`docs/Windows-exe-发布说明.md`）亦无「退出」章节。

### 3.3 缺陷 D1：探测与通配绑定共存误判

`find_available_port` 仅试绑目标地址（127.0.0.1），无法感知同端口被通配绑定（0.0.0.0）的进程；该场景下应判「端口已占」并回退 8766。

## 4. 候选方案

### 4.1 退出机制候选

| 候选 | 内容 | 新增依赖 | 体验 | 成本 |
|------|------|---------|------|------|
| A. UI 退出按钮 | 前端顶栏「退出服务」+ 确认框 → `POST /api/system/shutdown` → uvicorn 优雅停机（`server.should_exit = True`） | 无 | 好（浏览器内一键） | 小（后端 ~30 行 + 前端按钮） |
| B. 托盘图标 | 托盘右键「打开界面 / 退出」；pystray 或 ctypes 自绘 | pystray→pywin32+Pillow（需从 spec excludes 移除、体积约 +5-10MB）；ctypes 自绘零依赖但 ~100 行易错代码 | 最"桌面应用" | 中-大 |
| C. stop.bat 兜底 | 随包 `stop.bat`（`taskkill /IM OpenScrcpy.exe /F`）+ 发布文档「退出」章节 | 无 | 一般（需找到脚本） | 极小 |
| D. 组合 | **A + C**（推荐）或 B + C | 随 A/B | 最佳性价比 | 小 / 中 |

### 4.2 单开模式改进项

| 项 | 内容 | 说明 |
|----|------|------|
| S1（必做）| 修复 D1：探测前先**连接预检**（`connect_ex("127.0.0.1", port)` 成功即视为已占）或等价手段，任何监听者（含通配绑定）都触发回退 | 保持"与同机其他服务互不干扰"；补回归测试（0.0.0.0 占位时须回退 8766） |
| S2（评估）| mutex 命名加项目 GUID 后缀 | 现名 `OpenScrcpy-SingleInstance-Mutex` 已可用；改名会导致新旧版本互不互斥（升级期短暂双实例），**建议维持现名**，本项仅记录评估结论 |
| S3（随 A）| 退出端点与 mutex 协同：优雅退出后 `port.txt` 保留还是清除？建议保留（复用端口记忆）并在下次启动覆盖 | 细节在实施时定 |
| S4（观察项）| 系统关机/注销时的优雅清理（WM_QUERYENDSESSION / console ctrl handler） | 现状：进程被直接终止，设备端 adb forward 残留无害（下次连接自清理）；低优先级 |

## 5. 推荐与实施要点

### 5.1 推荐组合

**A（UI 退出按钮）+ C（stop.bat 兜底）**：零新依赖、改动小、覆盖"在界面上"与"找不到界面"两种用户路径；托盘（B）保留为后续可选增强（若要求桌面应用级体验再上，成本见 §4.1）。

### 5.2 实施任务分解（供评审后转实施计划）

- **T1 修复 D1**：`launcher.find_available_port` 增加占用预检（connect_ex）；`tests/unit/test_launcher.py` 补「0.0.0.0 占位 → 回退」回归用例。
- **T2 退出端点**：接口层 `POST /api/system/shutdown`（仅本地语义；若 `BACKEND_HOST` 显式放开需评审是否加约束）；run_server 冻结分支保存 uvicorn `Server` 实例并暴露回调（架构归属：接口层薄适配，停机动作留在启动器）；前端顶栏「退出」按钮 + 二次确认 + 退出后页面轮询停止的友好提示。
- **T3 兜底脚本与文档**：`stop.bat` 入产物（spec datas 注入 exe 同级）；`docs/Windows-exe-发布说明.md` 新增「退出服务」章节（任务管理器 / stop.bat / UI 按钮三路径）；方案 15 §8.6 相关观察项同步。
- **T4 打包与回归**：spec datas 加 stop.bat；重建 zip；干净环境复测（含 D1 场景双跑、退出后端口释放、二启行为不回退）。

### 5.3 打包与文档影响

- T1/T2/T4 不引入新依赖，spec 体积无变化；stop.bat 为纯文本注入。
- 若未来选 B（托盘）：需从 spec `excludes` 移除 `pywin32`、加 pystray/Pillow hiddenimports 与图标 datas——届时单独评估。

## 6. 待决策点

1. **退出机制**：A + C（推荐，零依赖） / 直接上 B + C（托盘，体验最佳但引入依赖与体积） / 仅 C（最小改动）；
2. **D1 修复立即排期还是随下一轮打包**（当前产物的规避手段：先退出 exe 再用 dev，或给 dev/exe 设不同端口）；
3. 退出端点是否需要二次确认与"全屏播放中禁止退出"等交互细化（默认：仅二次确认）。
