## 1. 背景与现状

### 1.1 现状（代码事实，2026-09-28 核实）

**后端采样管线（两服务同形态）**

- 性能：`PerformanceService._sampling_loop`（`backend/app/application/performance_service.py:98-145`）每采样点 append 缓冲 → 推订阅者队列（maxsize 60，满丢旧）→ 录制落盘。订阅队列是 WS 推送的数据源。
- 网络：`NetworkService._sampling_loop`（`backend/app/application/network_service.py:100-152`）形态同上，但**无订阅者队列**；`GET /api/network/{device_id}/stats`（`backend/app/interfaces/http/network.py:51-78`）为 HTTP 轮询入口（NetworkView 每 2s 拉取）。

**交付通道**

- 性能：WS `/ws/perf/{device_id}`（`backend/app/interfaces/ws/performance.py:37-82`）把每个样本序列化为扁平 JSON 直发——**无 type 信封、无告警字段**。
- 网络：轮询响应为 `stats` 字段的平铺字典（ts/rx_bytes/tx_bytes/rx_rate_kbps/tx_rate_kbps/active_connections/wifi_connected/wifi_ssid）。

**前端（展示级警示已有，通知层缺失）**

- `PerfView.vue` 硬编码展示色：CPU > 80（:57）、FPS < 30（:80）→ `.metric-value.warning`（:494）——**只变色，无任何通知**，且不可配置、无防抖（单点尖峰即变色）。
- `NetworkView.vue` 无任何阈值视觉。
- 无告警聚合 UI（面板关闭后用户对异常完全无感知）。

**配置**

- `MetricsConfig`（`config/settings.py:186-194`）+ `config/base.yaml` metrics 节点（42-50）**无阈值字段**。
- 热重载机制已具备：`config_watch.py` → `reload_settings()` 替换单例；采样循环内每轮重读 `settings()` → **阈值热重载零额外成本**。

### 1.2 缺口

| # | 缺口 | 后果 |
|---|------|------|
| G1 | 无判定层 | 用户须主动盯面板；离开页面无感知 |
| G2 | 硬编码 80/30 | 不可配置、无防抖、无网络侧判据 |
| G3 | 无通知 | 即使面板开着，异常也无显式提示（变色易被忽略） |

## 2. 设计决策

| # | 决策 | 说明 |
|---|------|------|
| D1 | 后端判定 | 评估在应用层采样循环挂点；前端零判定逻辑 |
| D2 | 复用既有通道，不新建 WS | perf 走 WS `/ws/perf`（样本消息内嵌 `alerts` 数组）；network 走 `/api/network/{id}/stats` 轮询响应内嵌。网络侧 WS 化超出本方案范围 |
| D3 | 状态化下发，非边缘事件 | 每条样本携带**当前活动告警快照**（含精确的 `notify` 标志）→ 重连/多订阅者不丢状态、不重复通知 |
| D4 | 前端提示 | 新触发 toast（`ElMessage.warning`）+ 活动告警徽标条；**解除仅徽标消失，不做恢复 toast**（降噪，与 21/22 治理精神一致） |
| D5 | 不落库 | 不进 `MetricRecorder`、不进导出、不进历史 API；内存态随监控释放清空（面板关闭/设备失联后无残留） |
| D6 | 防误报三件套 | 连续 N 次越限触发 + 迟滞余量/连续 M 次解除 + 冷却抑制重复通知（方案 21/22 误判教训的机制化） |
| D7 | 前端卡片警示色统一由 alerts 驱动 | 移除 `> 80` / `< 30` 硬编码表达式，单一事实源；默认阈值与原表达式一致，**肉眼无差异** |

## 3. 配置设计

### 3.1 `config/base.yaml` 新增 `metrics.thresholds`

```yaml
metrics:
  # ...既有关键字不变...
  # 阈值告警（方案 24）：连续 N 次越限触发；迟滞余量 + 连续 M 次安全解除；
  # 冷却期内重复触发仍进徽标但不弹 toast。以上均为「采样次数/秒」口径（@1s 采样）
  thresholds:
    cpu_percent:    { above: 80.0, consecutive: 3, clear_margin: 5.0, clear_consecutive: 3, cooldown: 60 }
    memory_percent: { above: 90.0, consecutive: 3, clear_margin: 5.0, clear_consecutive: 3, cooldown: 60 }
    fps:            { below: 30.0, consecutive: 3, clear_margin: 5.0, clear_consecutive: 3, cooldown: 60 }
    rx_rate_kbps:   { enabled: false, above: 0, consecutive: 3, clear_margin: 0, clear_consecutive: 3, cooldown: 60 }
    tx_rate_kbps:   { enabled: false, above: 0, consecutive: 3, clear_margin: 0, clear_consecutive: 3, cooldown: 60 }
```

字段语义：

| 字段 | 默认 | 语义 |
|------|------|------|
| `enabled` | `true`（网络两条 `false`） | 网络速率无通用阈值，需用户按场景启用并填值 |
| `above` / `below` | — | 二选一，**方向即判据**（above=越大越坏；below=越小越坏）。同缺同存 = 无效规则：启动时记 `alert_rule_invalid` warning 并跳过 |
| `consecutive` | 3 | 连续越限 N 次才触发（@1s 采样 ≈ 3s 滤波） |
| `clear_margin` | 5.0 | 迟滞余量：above 规则须回落至 `threshold - margin` 以下、below 规则须回升至 `threshold + margin` 以上，才算「安全样本」 |
| `clear_consecutive` | 3 | 连续安全 M 次才解除（迟滞带内样本既不算越限也不算安全，保持现状） |
| `cooldown` | 60 | 同一规则两次**通知**的最小间隔（秒）；冷却内触发照常进徽标，仅不弹 toast |

口径补充：

- `memory_percent` 指标源头是 used/total MB，由评估器计算 `used/total×100`（`total=0` 时跳过该样本）。
- `fps` 受 gfxinfo 降频影响（非 gfxinfo 轮为 `None`）：**`None` 样本跳过评估**——不计越限也不计安全，不改变计数器（详见 §4.1）。
- 热重载：每采样点重读 `settings()` 并 `sync()` 规则集——新增规则新建状态、移除规则丢弃、参数变化规则计数重置（§4.1）。

### 3.2 新增 settings 模型（`config/settings.py`）

```python
class AlertRuleConfig(BaseSettings):
    enabled: bool = True
    above: float | None = None
    below: float | None = None
    consecutive: int = 3
    clear_margin: float = 5.0
    clear_consecutive: int = 3
    cooldown: float = 60.0


class MetricAlertsConfig(BaseSettings):
    cpu_percent: AlertRuleConfig = Field(default_factory=lambda: AlertRuleConfig(above=80.0))
    memory_percent: AlertRuleConfig = Field(default_factory=lambda: AlertRuleConfig(above=90.0))
    fps: AlertRuleConfig = Field(default_factory=lambda: AlertRuleConfig(below=30.0))
    rx_rate_kbps: AlertRuleConfig = Field(default_factory=lambda: AlertRuleConfig(enabled=False, above=0.0))
    tx_rate_kbps: AlertRuleConfig = Field(default_factory=lambda: AlertRuleConfig(enabled=False, above=0.0))


class MetricsConfig(BaseSettings):
    # ...既有关键字不变...
    thresholds: MetricAlertsConfig = Field(default_factory=MetricAlertsConfig)
```

YAML 嵌套字典经 `Settings(**config)`（`config/settings.py:277`）由 pydantic 自动coerce为嵌套模型，沿用现有加载路径，无新增机制。

## 4. 后端设计

### 4.1 告警评估器（新文件 `backend/app/application/alert_engine.py`）

纯逻辑状态机，无 I/O、无框架依赖——与 `bitrate_advisor.py` 同层同风格（既有先例）。

```python
@dataclass
class AlertRule:
    id: str                  # 指标名 = 规则标识（cpu_percent / memory_percent / fps / rx_rate_kbps / tx_rate_kbps）
    enabled: bool
    above: float | None
    below: float | None
    consecutive: int
    clear_margin: float
    clear_consecutive: int
    cooldown: float


class AlertEngine:
    """按设备实例化；每规则独立状态机。

    状态转移：
      非活动 --连续 N 次越限--> 活动（记 fired_ts/notified_ts；冷却内 notified_ts=None）
      活动   --连续 M 次「越过迟滞余量」的安全样本--> 非活动
      迟滞带内样本：保持现状、计数清零
      None 样本：整条跳过，不触碰任何计数器
    """

    def sync(self, rules: list[AlertRule]) -> None: ...
    def evaluate(self, metric_id: str, value: float | None, ts: float) -> None: ...
    def snapshot(self, sample_ts: float) -> list[dict[str, Any]]: ...
```

**`sync(rules)` 热重载语义**：按 id 比对——规则消失则状态丢弃；新 id 则新建状态；参数（dataclass 相等性）变化则该规则计数/活动态重置。

**`snapshot(sample_ts)` 通知标志设计（关键）**：返回当前活动告警列表，其中 `notify` 为**时间精确匹配**而非「一次性消费」：

```python
notify = (state.notified_ts == sample_ts)
```

即：`evaluate()` 在触发样本上记 `fired_ts = ts`；冷却允许时同时记 `notified_ts = ts`（否则 `None`）。`snapshot()` 只认「本样本时刻」——多订阅者各自读到同一快照均能正确 toast；重连客户端只有当恰好落在触发样本上才收到 notify，否则只看到徽标（状态不丢）。**这避免了 consume-once 标志在多 WS 连接/轮询多端下的丢失问题**。

**无效规则**：`enabled=True` 但 above/below 同缺或同存 → 记 `alert_rule_invalid` warning，跳过该规则（不抛异常）。

**模块级辅助**：`build_rules(metric_ids: tuple[str, ...]) -> list[AlertRule]` 读取 `settings().metrics.thresholds` 组装规则列表（供两服务共用）。

### 4.2 快照 JSON 形状（两端一致）

```json
{
  "id": "cpu_percent",
  "value": 87.2,
  "threshold": 80.0,
  "direction": "above",
  "since": 1726045200.123,
  "notify": true
}
```

- `value`：该规则最近一次评估值（与触发样本可能有 ±1 样本的显示差，可接受——notify 判定只依赖 ts 精确匹配）。
- 无活动告警时为 `[]`。

### 4.3 服务挂点

## 5. 前端设计

### 5.1 共享模块 `frontend/src/services/alerts.ts`（+ 同目录 `alerts.test.ts`，沿用 services 层惯例）

```typescript
export interface AlertItem {
  id: string
  value: number
  threshold: number
  direction: 'above' | 'below'
  since: number
  notify?: boolean
}

const ALERT_LABELS: Record<string, string> = {
  cpu_percent: 'CPU 使用率',
  memory_percent: '内存使用率',
  fps: '帧率',
  rx_rate_kbps: '接收速率',
  tx_rate_kbps: '发送速率',

export function alertLabel(id: string): string  // 映射兜底返回原 id
export function extractAlerts(data: unknown): AlertItem[]  // 防御式：非数组/脏字段 → []
```

- `notifyAlerts`：仅对 `notify === true` 逐条 `ElMessage.warning({ message, grouping: true })`，文案如 `CPU 使用率 87.2% 超过阈值 80.0%`（below 为「低于阈值」）。

- `PerfMetrics` 接口增加 `alerts?: AlertItem[]`。

- **徽标条**：`metrics-grid` 上方，`v-if="activeAlerts.length"`，每个活动告警一枚 chip（标签 + 当前值），warning 色系。

## 6. 测试策略

**后端**（`tests/application/test_alert_engine.py` 新建；服务/接口/配置测试扩展）：

1. 连续判定：N=3 时前 2 次越限不触发、第 3 次触发；触发样本 `notify=true`，其后越限样本 `notify=false`
2. 迟滞：回落至阈值内但未过余量 → 保持活动；过余量且连续 M 次 → 解除
3. 冷却：解除后再次触发在冷却窗内 → 活动恢复但 `notify=false`（`notified_ts=None`）；超窗后 → `notify=true`
4. `None` 样本（fps 空窗）：不改变计数、不误触发、不误解除
5. 无效规则（above/below 同缺同存）：跳过且不抛
6. `sync`：规则移除丢状态；参数变化计数重置；新增从零起
7. 服务集成（fake sampler 造越限序列）：`get_alerts` 快照形状；`stop_monitoring`/失联释放后返回 `[]`
8. 接口：WS 消息含 `alerts` 键；`/api/network/{id}/stats` 含 `alerts` 键（无告警时为空数组）
9. 配置：`metrics.thresholds` 默认值 + YAML 覆盖解析（`test_metrics_config.py` 扩展）

**前端**（vitest）：

1. `alerts.test.ts`：`extractAlerts` 防御（undefined/非数组/脏字段）；`notifyAlerts` 只对 `notify=true` 弹且 `grouping: true`；标签映射与兜底
2. `PerfView.test.ts` 扩展：带 alerts 消息 → 徽标渲染 + 卡片 warning 类；`notify=true` → `ElMessage.warning` 调用；无 alerts → 无徽标无 toast（既有用例保持绿）
3. `NetworkView.test.ts` 扩展：轮询响应含 alerts → 徽标渲染

**门禁**：pytest + ruff + mypy strict + vitest + eslint 全绿。

## 7. 验收标准

- 配置 `cpu_percent.above=50`（实机或开发环境）→ 连续 3 次越限后 toast + 徽标；回落至 45 以下（含余量口径）连续 3 次 → 徽标消失
- fps 空窗（gfxinfo 降频轮）不误触发、不误解除
- 面板关闭 → 空闲守卫停采 → 重开面板无残留告警
- 录制导出内容不含告警字段；历史 API 响应无变化
- 零告警、默认阈值下 UI 与现状肉眼一致（D7）
- 零新依赖、零 DB 变更

## 8. 边界与不做项

- 不做：告警落库/历史查询/趋势；恢复 toast；多级严重度；Webhook/邮件/桌面通知；每设备独立阈值（全局阈值，YAGNI）；前端静音开关（用配置 `enabled` 控制）
- 不做：网络侧 WS 化（维持轮询内嵌）；logcat 侧告警（范围外）
- 不做：`metrics.recording` 与告警的耦合（录制开关不影响告警判定）
