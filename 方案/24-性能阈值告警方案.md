## 1. 背景与现状

### 1.1 现状（代码事实，2026-09-28 核实）

**后端采样管线（两服务同形态）**

- 性能：`PerformanceService._sampling_loop`（`backend/app/application/performance_service.py:98-145`）每采样点 append 缓冲 → 推订阅者队列（maxsize 60，满丢旧）→ 录制落盘。订阅队列是 WS 推送的数据源。

**交付通道**

- 性能：WS `/ws/perf/{device_id}`（`backend/app/interfaces/ws/performance.py:37-82`）把每个样本序列化为扁平 JSON 直发——**无 type 信封、无告警字段**。
- 网络：轮询响应为 `stats` 字段的平铺字典（ts/rx_bytes/tx_bytes/rx_rate_kbps/tx_rate_kbps/active_connections/wifi_connected/wifi_ssid）。

**前端（展示级警示已有，通知层缺失）**

- `PerfView.vue` 硬编码展示色：CPU > 80（:57）、FPS < 30（:80）→ `.metric-value.warning`（:494）——**只变色，无任何通知**，且不可配置、无防抖（单点尖峰即变色）。
- `NetworkView.vue` 无任何阈值视觉。
- 无告警聚合 UI（面板关闭后用户对异常完全无感知）。

**配置**

- `MetricsConfig`（`config/settings.py:186-194`）+ `config/base.yaml` metrics 节点（42-50）**无阈值字段**。
- 热重载机制已具备：`config_watch.py` → `reload_settings()` 替换单例；采样循环内每轮重读 `settings()` → **阈值热重载零额外成本**。

## 2. 设计决策

| # | 决策 | 说明 |
|---|------|------|
| D1 | 后端判定 | 评估在应用层采样循环挂点；前端零判定逻辑 |
| D2 | 复用既有通道，不新建 WS | perf 走 WS `/ws/perf`（样本消息内嵌 `alerts` 数组）；network 走 `/api/network/{id}/stats` 轮询响应内嵌。网络侧 WS 化超出本方案范围 |
| D3 | 状态化下发，非边缘事件 | 每条样本携带**当前活动告警快照**（`notify` 按通知窗口标记，客户端按 episode 去重）→ 重连/多订阅者不丢状态、不重复通知 |

## 3. 配置设计

### 3.1 `config/base.yaml` 新增 `metrics.thresholds`

```yaml
metrics:
  # ...既有关键字不变...
  # 阈值告警（方案 24）：连续 N 次越限触发；迟滞余量 + 连续 M 次安全解除；
  # 冷却期内重复触发仍进徽标但不弹 toast。consecutive 按「有效判定样本数」计，
  # 各指标墙钟时限不同（fps 仅计实测 gfxinfo 窗口），见方案 §3.1 时限表
  thresholds:
    cpu_percent:    { above: 80.0, consecutive: 3, clear_margin: 5.0, clear_consecutive: 3, cooldown: 60 }
    memory_percent: { above: 90.0, consecutive: 3, clear_margin: 5.0, clear_consecutive: 3, cooldown: 60 }
    fps:            { below: 30.0, consecutive: 3, clear_margin: 5.0, clear_consecutive: 3, cooldown: 60 }
    rx_rate_kbps:   { enabled: false, above: 0, consecutive: 3, clear_margin: 0, clear_consecutive: 3, cooldown: 60 }
    tx_rate_kbps:   { enabled: false, above: 0, consecutive: 3, clear_margin: 0, clear_consecutive: 3, cooldown: 60 }
```

字段语义：

| 字段 | 默认 | 语义 |
|------|------|------|
| `enabled` | `true`（网络两条 `false`） | 网络速率无通用阈值，需用户按场景启用并填值 |
| `above` / `below` | — | 二选一，**方向即判据**（above=越大越坏；below=越小越坏）。同缺同存 = 无效规则：启动时记 `alert_rule_invalid` warning 并跳过 |
| `consecutive` | 3 | 连续越限 N 次才触发（按有效判定样本计，墙钟时限见下方时限表） |
| `clear_margin` | 5.0 | 迟滞余量：above 规则须回落至 `threshold - margin` 以下、below 规则须回升至 `threshold + margin` 以上，才算「安全样本」 |
| `clear_consecutive` | 3 | 连续安全 M 次才解除（迟滞带内样本既不算越限也不算安全，保持现状） |
| `cooldown` | 60 | 同一规则两次**通知**的最小间隔（秒）；冷却内触发照常进徽标，仅不弹 toast |

口径补充：

- `memory_percent` 指标源头是 used/total MB，由评估器计算 `used/total×100`（`total=0` 时跳过该样本）。
- `fps` 受 gfxinfo 降频影响（`sampler.py:132-135`）：**非 gfxinfo 轮沿用上次有效值**（`_last_fps`，非 `None`）、首轮无基准或解析失败时可为 `None`。两类样本（沿用值 + `None`）**对 fps 规则均不计数**——不计越限也不计安全，不改变计数器（新增 `fps_fresh` 标志，详见 §4.3）。
- 热重载：每采样点重读 `settings()` 并 `sync()` 规则集——新增规则新建状态、移除/禁用规则丢弃（徽标同步消失）、参数变化规则计数重置（§4.1）。

**时限口径（`consecutive`/`clear_consecutive` 计的是「有效判定样本数」，各指标墙钟时限不同）**：

| 指标 | 一次计数对应的实测间隔 | 默认 3 次的触发/解除时限 |
|------|------------------------|--------------------------|
| `cpu_percent` / `memory_percent` | 1s（每轮实测） | ≈3s |
| `fps` | 1 个实测 gfxinfo 窗口（每 5 轮 1 次 ≈5s；沿用轮不计） | ≈15-20s（持续性判定） |
| `rx_rate_kbps` / `tx_rate_kbps` | 2s（`network_interval`，每轮实测） | ≈6s |

## 4. 后端设计

### 4.1 告警评估器（新文件 `backend/app/application/alert_engine.py`）

纯逻辑状态机，无 I/O、无框架依赖——与 `bitrate_advisor.py` 同层同风格（既有先例）。

```python
@dataclass
class AlertRule:
    id: str                  # 指标名 = 规则标识（cpu_percent / memory_percent / fps / rx_rate_kbps / tx_rate_kbps）
    above: float | None
    below: float | None
    consecutive: int
    clear_margin: float
    clear_consecutive: int
    cooldown: float


class AlertEngine:
    """按设备实例化；每规则独立状态机。

    构造参数：
      notify_window: 通知窗口（秒）——触发后窗口内的快照 notify=True，
                     由服务按采样间隔推导（max(3×interval, 5.0)）。

    状态转移：
      非活动 --连续 N 次越限--> 活动（记 fired_ts；冷却允许时记 notified_ts，否则 None）
      活动   --连续 M 次「越过迟滞余量」的安全样本--> 非活动
      迟滞带内样本：保持现状、计数清零
      无效样本（None / fps 沿用值即 fresh=False）：整条跳过，不触碰任何计数器
    状态字段（每规则）：breach_count / ok_count / active / fired_ts / last_value /
                      notified_ts / last_notify_ts（跨 episode 持久，冷却基准）
    """

    def sync(self, rules: list[AlertRule]) -> None: ...
    def evaluate(self, metric_id: str, value: float | None, ts: float,
                 fresh: bool = True) -> None: ...
    def snapshot(self, sample_ts: float) -> list[dict[str, Any]]: ...
```

**`sync(rules)` 热重载语义**：按 id 比对——规则消失则状态丢弃；新 id 则新建状态；参数（dataclass 相等性）变化则该规则计数/活动态重置。

**`snapshot(sample_ts)` 通知标志设计（关键）**：`notify` 为**窗口匹配 + 客户端 episode 去重**，而非「一次性消费」也非「ts 精确相等」：

```python
notify = (state.notified_ts is not None and 0 <= sample_ts - state.notified_ts <= self.notify_window)
```

即：`evaluate()` 在触发样本上记 `fired_ts = ts`；若距 `last_notify_ts` 已过冷却，则记 `notified_ts = ts` 并更新 `last_notify_ts`（否则 `notified_ts = None`，告警照常进徽标、仅不通知）。`snapshot()` 在窗口内一律返回 `notify=True`——由此：

- 同一 episode 会连续多帧携带 `notify=True`，**客户端按 `id:since` 去重**（§5.1）后只弹一次；
- **治愈三种丢通知路径**：① 轮询（2s 间隔）与采样相位漂移、触发样本的 ts 可能整条未被任何一次轮询返回；② WS 订阅队列满（maxsize 60）丢样本；③ 窗口内新订阅/重连的客户端也能收到一次通知。
- **`ts` 精确相等方案（初稿）已废弃**：在 ① ② 两类场景下 toast 会永久丢失。

状态字段中 `last_notify_ts` 跨 episode 持久（冷却以「上次通知时刻」为基准），`fired_ts` 则是每个 episode 独立。

**无效规则**：enabled 规则的 above/below 同缺或同存 → 记 `alert_rule_invalid` warning，跳过该规则（不抛异常）。

**模块级辅助**：`build_rules(metric_ids: tuple[str, ...]) -> list[AlertRule]` 读取 `settings().metrics.thresholds`，**只产出 enabled 的规则**（`enabled=False` 等效不产出——热重载禁用时 `sync` 视为移除：状态丢弃、徽标同步消失；重新启用则从零起算）。

## 5. 前端设计

### 5.1 共享模块 `frontend/src/services/alerts.ts`（+ 同目录 `alerts.test.ts`，沿用 services 层惯例）

```typescript
export interface AlertItem {
  id: string
  value: number
  threshold: number
  direction: 'above' | 'below'
  since: number
  notify?: boolean
}

const ALERT_LABELS: Record<string, string> = {
  cpu_percent: 'CPU 使用率',
  memory_percent: '内存使用率',
  fps: '帧率',
  rx_rate_kbps: '接收速率',
  tx_rate_kbps: '发送速率',
}

export function alertLabel(id: string): string  // 映射兜底返回原 id
export function extractAlerts(data: unknown): AlertItem[]  // 防御式：非数组/脏字段 → []

/** 每个视图实例创建一个：内含 episode 去重状态（视图生命周期内有效）。 */
export function createAlertNotifier(): { update(alerts: AlertItem[]): void }
```

- `update(alerts)`：见 `notify === true` 的条目按 `id:since`（episode 键）去重——未见过的 episode 弹一次 `ElMessage.warning({ message, grouping: true })`（文案如 `CPU 使用率 87.2% 超过阈值 80.0%`，below 为「低于阈值」）并记入已通知集；已通知集随当前活动列表裁剪（列表清空时整体重置）。窗口内多帧 `notify=true` 因此只弹一次；新 episode（换了 `since`）不受旧记录影响。
- 服务端降噪（迟滞 + 冷却）与客户端去重两层职责分明：服务端决定「值不值得通知」，客户端保证「同一 episode 不重复弹」。
- 标签映射放前端（后端只发原始 id）：告警引擎保持展示无关。
- 去重状态放工厂闭包而非模块级单例：PerfView / NetworkView（及多设备多实例）互不串扰。

## 6. 测试策略

**后端**（`tests/application/test_alert_engine.py` 新建；服务/接口/配置测试扩展）：

1. 连续判定：N=3 时前 2 次越限不触发、第 3 次触发；触发后窗口内样本 `notify=true`（窗口外 `false`）
2. 迟滞：回落至阈值内但未过余量 → 保持活动；过余量且连续 M 次 → 解除
3. 冷却：解除后再次触发（新 episode）在冷却窗内 → 活动恢复、窗口内 `notify=false`；超冷却后新 episode → `notify=true`
4. 无效样本两条路径：`None`（fps 空窗）与 `fresh=False`（fps 沿用值）都：不改变计数、不误触发、不误解除
5. 无效规则（above/below 同缺同存）：跳过且不抛
6. `sync`：规则移除/禁用丢状态（`build_rules` 过滤 disabled）；参数变化计数重置；新增从零起
7. 服务集成（fake sampler 造越限序列）：`get_alerts` 快照形状；`stop_monitoring`/失联释放后返回 `[]`（perf 与 network 两路）
8. 接口：WS 消息含 `alerts` 键；`/api/network/{id}/stats` 含 `alerts` 键（无告警时为空数组）
9. 配置：`metrics.thresholds` 默认值 + YAML 覆盖解析
10. **WS perf 端点补测**：`tests/` 现存零覆盖（无 `ws/perf` 用例）——新建 `tests/unit/test_ws_performance.py`，复用 `websocket_connect` + 依赖覆盖范式（`tests/unit/test_ws_debug.py`/`test_video.py` 先例）

## 7. 验收标准

- 配置 `cpu_percent.above=50`（实机或开发环境）→ 连续 3 次越限（≈3s）后 toast + 徽标，同 episode 只弹一次；回落至 45 以下（含余量口径）连续 3 次 → 徽标消失
- fps 规则：沿用轮与空窗样本不计数（触发/解除时限 ≈15-20s，与 §3.1 时限表一致）
- 网络规则（启用后）：轮询响应携带 alerts，toast 只弹一次、徽标随采样更新
- 面板关闭 → 空闲守卫停采 → 重开面板无残留告警（300s 宽限期内重开则可见活动告警）
- 录制导出内容不含告警字段；历史 API 响应无变化
- 零告警、默认阈值下 UI 与现状肉眼一致（D7）
- 零新依赖、零 DB 变更

## 8. 边界与不做项

- 不做：告警落库/历史查询/趋势；恢复 toast；多级严重度；Webhook/邮件/桌面通知；每设备独立阈值（全局阈值，YAGNI）；前端静音开关（用配置 `enabled` 控制）
- 不做：网络侧 WS 化（维持轮询内嵌）；logcat 侧告警（范围外）
- 不做：`metrics.recording` 与告警的耦合（录制开关不影响告警判定）
