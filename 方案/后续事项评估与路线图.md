## 1. 安全审查专项（P1）

- **范围**：后端暴露面——HTTP API 认证缺失面、路径穿越/文件名净化（`/api/export` 族）、`debug.py` shell 通道命令注入面、WS 消息解析、静态托管；绑定已限 `127.0.0.1`（降低外部暴露风险）。
- **资源**：无外部依赖；复用 `docs/reviews/` 留档机制。
- **时间**：审查 0.5 天 + 修复（预期小修）0.5 天。
- **影响面**：近零（审查不改码；修复局部）。
- **计划**：审查留档 → 逐项修复提交 → 门禁回归。无发现则仅留档。

## 2. 屏幕工具（P1）

- **范围**：录屏（`adb shell screenrecord`，系统自带零 root）→ 流式拉取 MP4 → `<video>` 预览+下载；GIF 前端抽帧；标注（canvas 叠加）。
- **资源**：真机三台；零新后端依赖。
- **时间**：录屏 1 天 + GIF 0.5-1 天 + 标注 0.5 天。
- **影响面**：低（新服务 + 面板新 tab）。
- **风险与规避**：低端设备编码器 err=-38（**.25 Android 7.1.2 已实测**：大分辨率失败 → `--size 256x144` 成功）→ 自动降档重试；大文件 → 挂方案 18 双限清理。
- **状态**：2026-10-10 调研——见方案 37。

## 3. 应用检查（P1）

## 6. 设备 offline 退避治理（P2，方案 34 D5）

- **前置**：D7 观测数据积累（真实 offline 事件）。真机拔线/`adb kill-server` 可构造。
- **时间**：1-1.5 天。**影响面**：中（stream_service 探针入口状态注入）。
- **风险与规避**：offline 信号只做「跳过本轮」不做「修改阈值」，与判死窗公式解耦；参数 config 可开关，默认关→真机验证→默认开；价值不足则如实结案。
- **2026-10-19 模拟验证与收口**（用户指示「对 6 进行模拟验证，并收口」）：
  - ①**活体（disconnect 式 offline）**：8766 隔离实例（源码 `BACKEND_PORT=8766` + 5039 独立 adb server）+ .25 真机起流出帧稳定（~4.4fps）后 `adb disconnect` → 服务端 `queue_sentinel_received` → 清理链（stop/terminate/stopped/ended）**135ms 收敛，零探针、零重启、无后续活动**；设备恢复后重连起流出帧正常。spike `tests/manual/spike_34d5_offline.py`，日志 `logs/spike34d5_backend.log`。
  - ②**静态论证（半死/flap 式 offline，即 05:35「三连打」场景）**：现码已有三层收敛——探针发送失败有界（方案 34 D2：3 次→`probe_send_failed` 上抛）、判死窗 10s（D1 加宽）、重启预算（方案 19 实施项 1b：60s 滑窗 ≤3 次 + 1s/2s 递增 sleep + 超抛 error 终止会话）。半死设备在单 WS 会话内最多约 3 轮重启尝试即终止，无无界循环；原风暴日志的「三连打」正是该 3 次预算本身。
  - **结论（按既定「价值不足则如实结案」）**：D5 offline 退避对既有结构收敛无增量——**如实结案，不立项**。若 D7 观测数据在真实日志中出现无界风暴再议（根因分析链见方案 34 §D5/§1.4）。

## 8. 网络抓包（P3，Phase 2 首选大项）

- **关键约束**：真机均非 root、无 tcpdump → push tcpdump 路线不可行。两条替代：
  - A. mitmproxy 前置代理（`adb reverse` + 设备 http_proxy）——仅代理感知流量；引入 mitmproxy 依赖（破「零新依赖」惯例需用户拍板）
  - B. 设备端 VPN 抓包 apk（PCAPdroid 式）——全流量但需装 app、需长期维护 Android 包，破坏「零安装」定位
- **时间**：spike 0.5-1 天 + 实施 2-3 天 + 验收 0.5 天。
- **影响面**：高（新 traffic 域横跨采集/传输/展示/导出）。
- **风险与规避**：spike 先行止损（抓取率不达标即如实结案）；独立 traffic 域不 import 核心链；分期（HTTP 明文 pcap → HAR 解析 → HTTPS 可选）；依赖引入需用户批准。

## 9. 脚本沙箱（❌ 不建议）

- 安全面大（注入/资源滥用）、设备端普遍无 Python 运行时、与远程 Shell 价值重叠。
- **若坚持**：降级为「预定义命令白名单 + 参数校验」快捷脚本（0.5 天），不做通用执行器。

## 10. 100+ 设备规模化（P3）

- **资源**：模拟设备压测（mock adb 输出 + 压测脚本）。
- **时间**：压测量化 1 天 → 瓶颈修复 1-2 天（视数据）。
- **风险与规避**：先量化再动手；N=50 无瓶颈则如实归档「规模上限证据」，不做预防性重构。
- **2026-10-19 模拟验证与归档**（用户指示「对 10 进行模拟验证，并收口」）：mock 压测 `tests/manual/spike_scale_devices.py`（对 `AdbCliDriver._run`/screenshot 打桩模拟真实 adb 子进程 40-120ms/次，其余**全走真实代码路径**：列表端点/SSE/SQLite 落库/冷却兜底；DB 隔离 `logs/spike_scale_N*.sqlite`），N=50/100 两轮，结果 `logs/spike_scale_N50.json`/`logs/spike_scale_N100.json`：
  - `GET /api/devices`：N=50 约 **0.9s**（cold/warm 一致）、N=100 约 **1.7s**——方案 35 并发 8 下近线性（50→100 延迟 ×1.9），无超线性拐点；事件循环心跳漂移 p99 14-49ms，无饿死；
  - 内存：RSS 81.5→82.0MB（N=50→100），稳态 30s 采样**平坦**，无按 N 超线性增长；
  - 缩略图风暴：N=100 全设备截图 16 并发**全过**（50 台墙钟 1.4s / 100 台 2.7s，单张 p50 ~0.4s/p95 ~0.53s）；
  - **附带架构事实**：`DeviceService.start()`（5s 刷新循环）全仓装配点**无人调用**（lifecycle 未接）——SSE `/api/devices/events` 无事件生产者（实测 200 空闲 0 块），列表实际更新=前端「挂载拉取 + 操作后静默刷新」事件驱动、非周期后台轮询；规模化成本因此集中在首查/操作后单次列表延迟（即上表口径）。
- **结论**：N=50 无瓶颈、N=100 单次列表 1.7s 可接受——按既定口径**归档「规模上限证据」结案，不做预防性重构**。留白如实记录：①前端 100 行渲染与缩略图 DOM 压力未量化（浏览器侧，如实际遇到再专项）；②若要启用 SSE 事件推送需先接生产者（现轮询路径可用，不构成阻塞）。
- **2026-10-19（同日后续）留白②接线完成**（用户拍板「让自动播报真正工作」）：`lifecycle.py` 启动末 `await get_device_service().start()`、停机逆序首步 `stop()`——纯接线，`_refresh_loop`/回调/SSE 端点/前端 `startSSE` 监听均为既有代码（`start()` docstring 本就注明「应在应用启动时调用」）。语义核实：轮询的「断开」判定=`adb devices` 仅 `device` 态行，与 GET /api/devices **完全同口径**，推送只是让前端更快到达所见态（半死 slow 行 state=device 不受误删；state 转 offline 后原手动刷新也会消失，行为一致无分歧）。验证：门禁后端 1255 passed/cov 93.61% + ruff/mypy 零红（`test_lifecycle.py` 补替身断言启动 start/停机 stop）；半死链冒烟（mock adb、其余真实：lifespan→循环→回调→SSE）N=2 实测 `connected` 事件 2 条到达 HTTP 流（接线前 N=50/100 两轮均 0），停机 `stopping_device_refresh` 按逆序收敛；真机活体（.25 connect→connected/disconnect→disconnected）因授权设备当时全离线顺延为日常人工验收项。行为变化如实声明：后端常驻每 5s 一次 `adb devices`（本地 adb server 查询，开销数十 ms；原首轮全设备按「新设备」广播 connected，前端已按 id 判重幂等无害）。**已随 v0.7.12 正式发布**（2026-10-19，tag + GitHub Release 附包 SHA `2492af6c…df18`，CI 三 job 绿）。

## 15. 设备连接假成功治理（P2，2026-10-13 新增，✅ 2026-10-15 已实施进 0.7.9）

- **来源**：2026-10-13 用户实操反馈——两人协作场景「同事请求连接同一设备，提示连接成功，但设备列表未显示」。
- **根因（代码级）**：`cli.py:716` connect 成功判定为字符串 `"connected" in output.lower()`——adb 对已登记地址回 `already connected to …`（**不尝试重连**）同样命中 → 假成功提示；`cli.py:485` 设备列表仅保留状态为 `device` 的行，`offline` 行被过滤不显示；SSE 事件只播设备集合「新增/消失」差集，已登记但 offline 的设备无任何提示。
- **范围**：connect 链路对 `already connected` 分支补一次 `adb devices` 状态复核——offline/不在 → 返回明确失败提示（含「先断开重连」指引）；可选自动 `disconnect` 后重连一次。涉及 `AdbCliDriver.connect_tcp` + 前端连接对话框错误回显（Dashboard.vue）。
- **时间**：0.5 天。**影响面**：低（connect 链路 + 错误文案）。
- **实施记录（2026-10-15，用户反馈 .25 假成功触发）**：按评估范围落地——`connect_tcp` already connected 分支补 `_device_states()` 设备表复核，非 `device` 态抛 `DeviceNotReadyError`（400 `DEVICE_NOT_READY`，offline/unauthorized/不在表三类中文指引；fresh connected 零额外调用，scan 编排经既有 `except Exception` 自动归 failed 带原因）。前端零改动（extractApiError 原样回显后端文案）。「自动 disconnect 重连一次」未做（保持最小影响面，指引代替）。真机实证：.23（unauthorized）与 .25（offline）经新代码均从假成功改为准确拦截文案；门禁 1235 passed / cov 93.62%。
- **尾巴闭环（2026-10-20 B5 实施）**：列表侧 offline/unauthorized 可见性——后端 `list_device_states()` adb 全状态表单源，列表追加失联行（有缓存按方向 `replace(status=state)`、无缓存最小 DeviceInfo 不回写库）；`_refresh_loop` 状态迁移 diff 播 SSE `unreachable` 事件（保缓存不删，恢复走 connected 整体替换）；前端 Dashboard「离线/待授权」中文标签 + row-offline 置灰 + 失联清 stale 缩略图 + connected 存在则替换。详录进度追踪一百零五次。
