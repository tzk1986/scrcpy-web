## 一、问题（.33 切页滞后的真凶：结构性误判 + 放大器链）

### 1.1 用户现象与初步结论

用户报告：.33（RK3566）体验中点击按钮后设备屏幕已切页，浏览器画面仍停留旧页
6-8s 以上（任务 #251）。逐层测量结论：**链路本身不慢**（健康期点击→浏览器可见
0.3-0.6s），瓶颈在**设备源头**（kiosk 静止出帧 1-4fps、突发—静默节律）与
**仓库自愈机制的放大效应**。本方案治理后者（前者属设备性能，超出本仓库可控
范围）。

### 1.2 保活探针机制现状（方案 19）

`scrcpy.py:485-528`：队列 `tick=min(2.0, idle_reset/2)=2s` 无数据 →
`now - last_data_at >= idle_reset_seconds(5)` → 发 RESET_VIDEO（type=17，单字节）
并锁存 `reset_sent_at`；数据到达即清锁存；**发针后再等 `idle_reset`（5s，tick
粒度下实际 5~7s）无数据 → `EncoderStalledError`** → StreamService 全量重启
scrcpy-server（黑屏 8-17s，60s 滑窗 ≤3 次、超限上抛）。

### 1.3 实测：RESET_VIDEO 应答延迟呈重尾分布（结构性误判铁证）

`tests/manual/spike_33_reset_probe_latency.py`（本方案调研工具，已入库）在 .33
上实测「探针→响应」延迟三轮（20/10/9 针）：

| 轮次 | 设备面 | 探针→下一帧 p50 | p90 | max | ≥5s 判死阈针数 |
|------|--------|-----------------|-----|-----|----------------|
| 跑 1 | 输入法键盘开（有持续重绘） | 24ms | — | 250ms | 0/20 全快 |
| 跑 2 | 键盘关、静止菜谱面 | 4141ms | 10657ms | 10657ms | **4/9** |
| 跑 3 | 同跑 2 复跑 | 578ms | — | 3531ms | 0/9 |

**判死窗口（5~7s）正落在重尾分布中段**：跑 2 每针有 ~44% 概率越过 5s 阈、
合并三轮约 10-25% 概率被假判死。跑 1 与跑 2 对比说明延迟随**设备面是否
持续重绘**剧烈摆动——恰好是 kiosk 最典型的静止画面场景最危险。

### 1.4 打包版日志时间线实证（用户风暴期 05:27-05:46 UTC）

- **05:27-05:37**：每 12-25s 一轮 idle_reset 探针；5 次 stall
  （05:32:10/05:33:48/05:34:35/05:35:19 等），每次 stall 前均有探针发出且
  支部无帧落入；05:32:27 客户端 fps=1.0（重启黑屏期样本）→ 码率降档重启；
  05:33:11 fps=38、距降档 44s（<120s 复核窗）→ 回弹重启（方案 21 复核路径）；
  05:35:20-22 设备 offline 三连打；
- **05:37-05:46**：e2e-runner（我）与 user-1 双会话并发 → 05:41:01-35 双流
  崩溃循环（returncode=134/1、socket_read_error「0 bytes read」、双轨 chunk
  0/10-13 交替）；05:44:15/45:08/45:30 三连 stall；
- **06:08-06:40（本方案 spike 时段）**：06:19:43、06:26:55、06:27:37 三次
  stall 在 spike 期间真实发生（其中 06:26:55 由 06:26:48 idle_reset 直接
  引发）——生产风暴在打包版上的活体复现。

### 1.5 放大器链（误判后的级联放大）

单次误判只黑屏一次，但以下环节把它放大成风暴：

1. **fps 统计污染**：重启期空白使客户端 `{op:"stats",fps}` 报 1.0/4.0/8.0 →
   BitrateAdvisor 降档 → **第二次重启**（重启本身制造更多坏样本）；
2. **复核回弹**（方案 21 路径）：降档后新窗口填满好样本 → 44s 即回弹档位 →
   **第三次重启**；
3. **stale pending 跨流残留**（stream_service.py:253）：旧流 finally 无条件
   pop `_pending_bitrate` 晚于新流启动时，新流首帧循环即看到残留 pending
   （:176 不清 event）→ 启动 1 秒内被强制降档重启（05:40:59 实证）；
4. **并发踩停缺陷**（独立发现，见 1.6）：被拒/空流客户的 teardown 踩停他人
   活跃流 → ping-pong 重启循环。

### 1.6 并发互踩缺陷（代码级确认，独立于探针误判）

`stream_service.py:343-354` 的 `stop_stream` **无条件**写
`active_streams[device_id] = False`；`video.py:269` 每个 WS 的 finally 都调用
它。第二客户端 start_stream 被拒（3×1s 守卫后空迭代）后走 finally → 写 False
踩停第一客户端的活跃流 → 双客户端互相踩停 + 双 scrcpy-server 并发启动 →
returncode=134(SIGABRT)、socket_read_error 5s 循环（05:41-05:43 日志实证，
含我与用户会话互踩）。

### 1.7 调研方法的诚实性标注

三轮 spike 中，慢响应窗口 >6s 时**后端自身 idle 探针会注入额外 RESET_VIDEO**
（06:26:48→06:26:55 stall 与我的探针并发）——跑 2 的 10.6s max 可能部分含
双针叠加。据此列出三个候选机制，且三者**同向支持同一修法**：

1. 设备编码会话重建慢（RK3566 慢路径，重尾主因）；
2. 静止面无持续新帧（探针后设备出帧意愿低）；
3. 双针叠加（后端 idle 针 + 客户端 request_keyframe 针并发，均走
   `control_sender.reset_video()`，无串行化）。

## 二、设计（D1-D7：加宽窗口 + 削减爆炸半径 + 修并发缺陷）

### D1 判死窗口解耦加宽（核心）

判死窗从 `idle_reset` 提至 **`max(2×idle_reset, 10s)`**（配置 idle=5 →
10s）。单针语义不变（`reset_sent_at` 锁存已保证一针在途不追加第二针）。
真卡死时后端自愈延迟从 ~10s 增到 ~15s（多 ~5s 黑屏），由前端 fallback
截图兜底（D6），可接受。

- 改点：`scrcpy.py:525` 的 `now - reset_sent_at >= idle_reset` → 用
  独立常量/配置 `stall_grace_seconds = max(2×idle_reset, 10)`；
- 探针段时钟注入：为单测可控，探针段 `time.monotonic()` 改为构造函数
  注入时钟（默认 `time.monotonic`）；
- **尾段残余诚实标注**：跑 2 实测 max=10.6s 仍越过 10s 窗（若含双针叠加则
  真实值更低）。10s 是第一档；实施后凭 D7 延迟采样数据再评估是否上调。
  残余误判的代价已从「风暴」降为「单次重启 + 截图兜底」。

### D2 探针发送失败快路径

现状 `scrcpy.py:519-524`：send 失败清锁存、下个 tick 重试——控制通道坏死时
**无限静默重试、永不判死**。改为：发送异常即抛
`EncoderStalledError("probe_send_failed")`（distinct reason）→ 立即走自愈。
控制通道与视频同属 scrcpy-server 进程，send 失败≈进程已死，等窗口无意义；
误判代价由 60s 滑窗 ≤3 限制。

### D3 重启爆炸半径

- **D3b 决策器样本窗清零**：`BitrateAdvisor` 新增 `reset()`——清空
  `_samples` 与「降档复核」状态（`_down_baseline`/`_down_from_idx`），保留
  档位 `_idx` 与冷却状态。StreamService 在 **stall 重启分支**（:238 epoch+1
  处）与**码率降档重启分支**（:219）调用——重启期 fps 样本全属黑屏期，
  不得参与决策与复核（根治 05:32:27→05:33:11 降档-回弹级联）；
- **D3c claim 时清残留 pending**：`start_stream` claim 成功（:148-149）后
  立即 `_pending_bitrate.pop(device_id, None)`——claim 成功即旧流已死/收尾，
  pending 必为残留，不得让新流首循环消费（根治 05:40:59 一秒被重启）。

### D4 并发互踩修复（acquire/release 拆分）

公开面从「stop_stream 无条件踩停」改为 token 持有制：

```python
token = await stream_service.acquire_stream(device_id)  # None=已有活跃流
if token is None:
    await ws.send_json({"type": "stream_ended"})
    return  # 关键：被拒客户不得触达 stop_stream/release
try:
    async for pts, chunk in stream_service.start_stream(device_id, token):
        ...
finally:
    await stream_service.release_stream(device_id, token)
```

- `acquire_stream`：移植现 start_stream 守卫（3×1s 重连收尾窗 + truthy 检查，
  stream_service.py:113-126）与 claim（:148-149），返回 token | None；
- `start_stream(device_id, token)`：内部循环与 finally 按传入 token 做
  identity 守卫（现 :157/:242-250 已具该结构，收紧即可）；不再含守卫循环；
- `release_stream(device_id, token)`：
  `if active_streams.get(device_id) is token: active_streams[device_id] = False`
  （置 False 让帧循环退出，teardown 由 start_stream finally 完成）；
- `stop_stream`/`stop_all_streams` 保留给应用关闭场景（无条件停全量，
  stop_all 语义正确）；video.py:269 改为 release；
- 不变量：**只有持有 token 者能停流**。第二客户无论如何退出都不影响第一流。

### D5 设备 offline 退避

**暂缓**（证据较轻：05:35:20-24 三连打、05:53:25 push 30s 超时）。待 D7
观测数据积累后另案。

### D6 前端回退阈值联动

`videoFallback.ts:57-64`：`STALL_MS = max(3000, keepaliveMs*2)`。后端判死窗
加宽后，慢探针恢复期最长可达 ~15s（空闲 5s + 判死 10s），现有 10s 阈值会
在中途误进截图 fallback（呼吸循环风险，方案 20 教训）。改为：

```ts
const STALL_MS = Math.max(3000, keepaliveMs * 2 + 2000)  // idle=5 → 12s
```

- 12s 覆盖了「空闲窗（5s）+ 探针应答 p50 量级」的慢恢复段；
- 尾段（12-15s 才恢复）仍可能短暂落 fallback 截图，随后经方案 22 恢复
  探针回流——这是**有意设计**：真死时 12s 落截图优于等后端 15s 自愈；
- `NO_STREAM_MS`/`HARD_TIMEOUT_MS` 随 STALL_MS 顺延（现公式已相对计算）；
- 纯前端改动，config 已下发 `idle_reset_seconds`（方案 19 遗留通道）。

### D7 观测性

- `EncoderStalledError` 携带 reason（`no_data_after_reset` /
  `probe_send_failed`），`encoder_stalled` 日志含 reason；
- 探针应答延迟 debug 采样：数据到达清锁存处（scrcpy.py:499-500）记录
  `reset→data` 间隔（debug 级，避免日志噪音——方案 33 定调）；
- 供实施后真机验收回填 §四（用延迟分布判断 10s 窗是否需要二档上调）。

### 已取消

- D3a（stall 重启向客户端发「restarting」通知）：前端 fallback 截图已兜底，
  且码率重启路径已有该通知（video.py 方案 19 遗留），不对称性可接受。

1. **探针窗口加宽**（tests/scrcpy/test_scrcpy_encoder.py，更新

## 六、风险与边界

| 风险 | 缓解 |
|------|------|
| 判死窗加宽后真卡死时自愈延迟 +5s（~15s） | 前端 STALL_MS 12s 先落截图兜底（D6），次序为「先兜底后自愈」 |
| 10s 窗仍低于跑 2 实测 max（10.6s，或含双针叠加） | 残余误判代价已从风暴降为单次重启；D7 延迟采样支撑验收后二档上调决策 |
| 双针并发（后端 idle 针 + 客户端催帧针）加重设备重建延迟 | 本轮不引入串行化（改动面过大）；窗口加宽已覆盖其帧面后果，作为边界记录待观测 |
| acquire/release 拆分改动 WS 控制面，重连竞态回归风险 | 移植现守卫与 identity 语义（方案 19/R2 既有结构），§三用例 4 钉死防踩停；重连窗（False 放行）行为不变 |
| advisor.reset() 若误清「有效降档」的复核基线 | 仅清样本与复核态、保留档位与冷却；决策语义单测钉死（§三用例 2） |
| 前端 STALL_MS 上调使中速设备冻结容忍变长 | 12s 仍远小于后端 15s 自愈窗；恢复了仍进 fallback 的场景由方案 22 恢复探针回流 |
| 设备 offline 场景未治理（D5 暂缓） | 已列为另案；offline 期 id_reset 探针判死也走 D1 大窗，风暴强度已同步下降 |
