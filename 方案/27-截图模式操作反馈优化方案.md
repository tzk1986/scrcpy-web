# 方案 27：截图模式操作反馈 <800ms（事件驱动截屏 + 单飞防抖）

> **状态**：实施中——Phase 0 spike 基线完成（2026-09-30，.18 真机）：`screencap -p` 中位 916–982ms（4 次复测一致）、旧基线反馈中位 **2491ms**（实测印证方案 17 的 1.5–2.5s）、事件驱动变体中位 **1414ms**（1.76×）。**判定预判**：<800ms 在 PNG screencap 链路上物理不可达（T2 单点 ~950ms 已超目标）——前端事件驱动照常实施（拿下 1.76×、接近该链路上限），<800ms 的剩余差距需设备端编码链路换挡（JPEG/raw，另立方案调研）。
>
> **由来**：`docs/性能对标与优化清单.md` P1-6「截图模式目标 <800ms 未实施（方案 17 遗留）｜操作反馈滞后 1.5-2.5s」。方案 17 根因 A 已定位主因为固定 1.5s 轮询，并给出改进方向（输入后立即截屏），本方案落地该方向并补齐细节设计。
>
> **关联**：方案 17（根因 A/B、回退机制）、方案 19（回退/恢复链路）、`frontend/src/services/videoFallback.ts`（回退判定）。本方案不改后端、不改跨层接口，与方案 26 的「最小 blast radius」原则一致。

---

## 1. 现状走查（2026-09-30 核实）

截图模式激活链路：`VideoPlayer.checkH264Fallback`（h264 卡死/错误）→ `h264Stream.suspend()` + `startScreenshotMode()`（`new VideoStream(deviceId, canvas, ws)`，refreshInterval 默认 **1500ms**）。

- **前端轮询**：`frontend/src/services/videoStream.ts:118` `setInterval(captureFrame, 1500)`；`captureFrame` → `api.screenshot(deviceId)`（GET `/api/devices/{id}/screenshot`，blob）→ `createImageBitmap` → `drawImage`
- **后端**：`interfaces/http/devices.py:185` → `device_service.screenshot` → `infrastructure/adb/cli.py:424` `adb exec-out screencap -p` 单命令管道输出 PNG（方案 17 已评最优——三步合一）
- **输入**：`VideoPlayer` 鼠标/触摸处理器 → `InputController.sendTap/sendSwipe/sendKey/sendText/sendLongPress` → `ws.send({action…})` → 后端 `interfaces/ws/video.py:316` `_handle_input` → `encoder.send_input`（scrcpy 控制协议 <5ms，回退 adb shell input）
- **输入与截屏完全解耦**：全仓 grep `refreshOnInput/onInput/notifyInput` 无命中——无事件驱动刷新，操作反馈只能等下一轮轮询到期

## 2. 延迟构成（操作 → 画面反馈）

| 段 | 当前值（估） | 说明 | 可消除性 |
|----|----|------|---------|
| T1 轮询相位等待 | 0–1500ms，**平均 750ms** | 固定 setInterval，操作时刻到下一轮截屏的随机等待 | **主因，事件驱动可消除** |
| T2 设备端 `screencap -p` 编码 | ~300–700ms | RK 设备软件 PNG 编码主导（方案 17 根因 A 实测数百 ms） | 物理限制，spike 实测钉死 |
| T3 adb 往返 + PNG 传输 | ~50–150ms | 已单命令管道，PNG 数百 KB | 不可再省 |
| T4 HTTP 往返（前端↔后端） | <20ms | 同机/内网 | 可忽略 |
| T5 createImageBitmap + drawImage | ~30–80ms | PNG 1360×768 解码渲染 | 固定 |
| T6 设备 UI 响应输入 | ~50–200ms | 注入后应用动画/响应 | 应用自身责任 |

- 现状合计：平均 ≈ 1.4–1.6s，最坏 ≈ 2.5s——与实测 1.5–2.5s 吻合
- 事件驱动后理论：`0 + T2 + T3 + T4 + T5`（T6 与 T2 并行重叠，注入 <5ms 后可忽略）≈ **400–1000ms**——<800ms 达成与否取决于 T2 实测，这正是 Phase 0 spike 先行钉数据的原因

## 3. 设计决策

| # | 决策 | 说明 |
|---|------|------|
| D1 | **事件驱动截屏（主实施）**：`InputController` 在每次输入发送后回调通知 `VideoStream.notifyInput()`，`VideoPlayer` 仅在截图模式接线 | 消除 T1，操作反馈从「平均 750ms 轮询等待」变为「输入后主动截取」 |
| D2 | **debounce 合并**（默认 160ms，spike 校准）：连续输入窗口内重置计时器，只截一张 | 理由：设备 UI 响应 T6 约 50–200ms——立即截屏大概率截到旧画面（白截+浪费）；160ms 让 UI 先响应。长按（DOWN→保持→UP 多消息）与快速连续点击被自然合并，终帧必反映最新状态 |
| D3 | **单飞 + 尾部补帧**：截屏 in-flight 时新请求只置 pending 标志；完成后有 pending 立即补截 | 并发截屏 ≤1（screencap 是设备端重量操作，不加重负载）；ping 循环保证「最后一帧反映最新输入」，乱序渲染不可能发生 |
| D4 | **相位重置**：事件截屏完成后重新 setInterval（从完成时刻起算下一周期） | 避免「事件截屏刚完成，200ms 后定时器又到期双发」的浪费尖峰 |
| D5 | **轮询间隔保持 1500ms 不动** | 提高轮询频率（如 800ms）只改善最坏等待，代价是 screencap 负载 +87%；事件驱动后操作反馈与轮询间隔解耦，调频无收益 |
| D6 | **后端零改动** | `exec-out screencap -p` 已单命令最优；screencap 无分辨率缩放参数（`-h` 仅 `-p`/`-d display-id`）；设备端 PNG 编码时长是物理量——由 spike 实测分解并入判定，不盲改 |
| D7 | **触发点 = 「输入已发送」**：`sendKey/sendTap/…` 每次 ws.send 后即回调 | 顶栏按键（返回/主页/多任务）走 sendKey 自动联动，无需额外接线 |
| D8 | **h264 模式不触发**：`mode !== 'screenshot'` 时回调空转 | h264 帧流天然实时（本会话 P1-5 已收口 30fps），截屏徒增设备负载 |
| D9 | **启动即截首帧 + stop 清理 debounce**：`start()` 的立即截屏同样走单飞入口 | 与既有行为一致（start 先 captureFrame 一帧），避免两套截屏路径 |

## 4. 实施项

### Phase 0 — spike 基线（先行钉数据，`tests/manual/spike_screenshot_feedback.py`，需真机）

不写生产代码，只测。脚本直连真机（httpx 轮询截图接口 + websockets 客户端注入），测两组：

- **A. 后端截屏分段耗时分布**（N=20）：subprocess 直接计时 `adb exec-out screencap -p`（= cli.py 同命令）与 HTTP 接口各一组——分层 T2+T3（命令）与 T2+T3+T4（HTTP），差值即 T4
- **B. 旧基线端到端反馈**（N=10，模拟现状前端）：按 1500ms 固定相位轮询截图接口；注入点击（切换设备端画面）→ 检出「画面变化」→ 反馈时延 = 检出时刻 − 注入完成时刻
- 画面变化检出法：**PNG 响应大小突变**（≥3× 差异）——设备端 ACR 打开「黑白全屏切换按钮页」（复用 P1-5 spike 的 adb reverse + http server 8000 先例，clock 页加按钮切 body 纯色类）；纯色页 PNG 仅 ~20KB vs 复杂页 ~500KB，突变 25× 远超噪声，无需图像解码（无 Pillow 依赖）
- 判定输出：若 A 组中位数 T2 > 600ms，则 <800ms 目标需在文档中如实重述（前端优化后达「设备端物理上限」，剩余时长为编码器限制）

### Phase 1 — TDD 前端实施（3 任务，每任务 RED→GREEN→提交）

**任务 1：`frontend/src/services/videoStream.ts` 增加 `notifyInput()`**

- 新增私有状态：`inputDebounceMs = 160`、`_inFlight`、`_pendingRefresh`、`_debounceTimer`
- `notifyInput()`：state 非 streaming 直接返回；重置 debounce 计时器；到期调统一入口
- 统一入口 `captureNow()`：in-flight → 置 pending 返回；否则 `doCapture()`（`_inFlight` 环绕 `captureFrame`，finally 里 pending 则补截、无 pending 则**相位重置**）
- `start()` 的立即首帧与周期定时器回调改走 `captureNow()`；`stop()` 清 debounce 计时器
- 测试（vitest fake timers，`videoStream.test.ts` 扩展）：
  1. `notifyInput` 160ms 后触发一次截屏
  2. 连续 3 次 notifyInput（间隔 <160ms）只截 1 张
  3. in-flight 期间 notifyInput → 完成后自动补截 1 张
  4. 事件截屏完成后相位重置（下一次周期截屏从完成时刻起算 1500ms）
  5. stopped/error 状态下 notifyInput 不触发截屏

**任务 2：`frontend/src/services/inputController.ts` 增加 `setInputHandler`**

- 构造可选回调字段 `onInputSend?: () => void`；`setInputHandler(handler)` setter
- `sendKey/sendText/sendTap/sendSwipe/sendLongPress` 每次 ws.send 后调 `this.onInputSend?.()`
- 测试（`inputController.test.ts` 扩展）：5 种输入各触发 handler 一次；未设置 handler 不抛错

**任务 3：`frontend/src/components/stream/VideoPlayer.vue` 接线**

- `inputController` 创建后：`inputController.setInputHandler(() => { if (mode.value === 'screenshot') videoStream?.notifyInput() })`
- 测试（`VideoPlayer.test.ts` 扩展）：截图模式下 handler 触发 `videoStream.notifyInput`（mock spy）；h264 模式下不触发

门禁：每任务 vitest + vue-tsc + eslint；全部完成后 `PYTHONPATH=backend python -m pytest tests/ --ignore=tests/e2e` + ruff + mypy strict（确认后端零波及）。

### Phase 2 — 真机复测收口

- 用 Phase 0 同脚本同法复测（spike 脚本加 `--new-pipeline` 变体）：注入 → debounce 160ms → 截屏单飞/补帧循环模拟新前端策略 → 反馈时延分布（N=10，画面 A/B 交替注入）
- 判定：**C 组中位数 < 800ms → P1-6 收口**（回写性能清单 §4.5）；若受设备端 screencap 物理限制未达标 → 如实回写「前端侧已达理论下限 + 后端时长分解数据」，用户据实校准目标
- 附带观察：事件截屏对设备 CPU/负载无异常尖峰（单飞生效）

## 6. 风险

- **debounce 窗口内操作序列合并**：快速「点击→滑动」只截终态画面——可接受（终态即用户所见目标）
- **设备端 UI 响应慢的应用**（T6 > 300ms）：仍可能 >800ms——应用自身责任，判定数据如实（spike 用系统级即时响应控件：按钮切色，T6 最小化）
- **事件截屏与 recovery probe 并行**：一个 HTTP 截图、一个周期 WS 帧计数观察，无状态共享冲突
- **h264 suspend 期间后端仍推流**：设备负载非本方案范围（恢复探测依赖帧计数，后端不可停）
