# 方案 17：推流流畅度优化

- 日期：2026-09-18
- 状态：设计中（待评审），评审通过后实施
- 关联：[05-视频流方案](./05-视频流方案.md)（如存在）、[14-调试面板其他标签完善](./14-调试面板其他标签完善.md)、[16-设备连接可达性预检优化](./16-设备连接可达性预检优化.md)

## 一、问题分析

### 1.1 现象（用户报告）

1. **操作后画面比实际屏幕滞后**：点击/滑动后，画面反馈明显晚于设备实际屏幕。
2. **连接多设备时单独看一台设备更卡**：同时连接多台设备推流时，即使只看其中一台，
   该台的流畅度也低于只连一台时的表现。
3. **日志无条件采集浪费资源**：打开设备详情页即在后端启动 logcat 采集 + 前端拉取
   历史日志，即使用户从不看日志（新增需求：不需要日志时不请求，开启日志时才拉取
   并滚动显示）。

### 1.2 现状链路走查

单设备视频链路：

```
设备屏幕 → scrcpy-server 硬编码(OMX/rk) → TCP(adb forward 隧道)
  → 后端 read_socket(64KB chunk) → _data_queue(maxsize=100)
  → ScrcpyEncoder.start yield → video.py: H264Parser.feed 逐 NALU 解析
  → websocket.send_bytes → 浏览器 H264VideoStream → VideoDecoder.decode
  → output 回调 drawImage(canvas) → 用户眼睛
```

平行负载（每设备）：`PerformanceSampler` 1s 间隔串行执行 5 个 adb shell
子进程命令（见 1.3 根因 F）。

### 1.3 根因（按证据强度与影响排序）

**A. 截图模式固定 1.5s 轮询（滞后主因，截图模式下）**

- 位置：`frontend/src/services/videoStream.ts:49`（默认 refreshInterval=1500ms）
  + `backend/app/infrastructure/adb/cli.py:421-435`（`screencap -p` 单命令）。
- `screencap -p` 在 rk3568 上实测需数百 ms，加上 HTTP 往返与 createImageBitmap，
  用户操作后的画面反馈滞后 **1.5~2.5s**。截图模式是 .18（Rockchip）设备的
  当前主模式（H264 编码器故障，见根因 B），因此感知最直接。
- 改进空间：轮询间隔参数化/自适应；输入操作后立即触发一次截屏刷新（事件驱动
  截屏），操作反馈从 1.5s 降到 ~500ms。

**B. Rockchip 设备硬编码器故障导致 0.4fps（单设备大滞后，设备端）**

- 实测证据（后端日志 2026-09-18 会话 2）：06:46:39.6 第 5 帧后停帧，
  06:50:02 恢复至 frame 97、06:54:05 frame 197 —— **恢复后
  243 秒仅 100 帧 ≈ 0.4fps**。设备 OMX.rk.video_encoder.avc 先崩溃
  （14:44 session：`Observer died` + `Cleaning up`）后进入低性能卡顿态
  （vpu_api_legacy 周期性 rate-control 重配置、只吐 SPS/PPS 不出帧）。
- 与 docs/经验记录.md E009（RK3288）同族。**无软件根治**，靠
  「故障时回退截图 + 恢复后自动回切」（已实施于 2026-09-18，commit 508d0b8）
  兜底。后续可评估 30fps/2Mbps 降档是否降低故障率（实验项，见 2.4）。

**C. 前端无解码队列积压控制（H264 模式滞后随时间单调增长）**

- 位置：`frontend/src/services/h264VideoStream.ts:309-323`。每帧无条件
  `decoder.decode()`，WebCodecs 内部解码队列没有积压检测与丢帧策略。
- 渲染/解码跟不上（CPU 抖动、后台 tab 争抢、多设备同屏）时，队列积压 →
  画面滞后随时间无界增长。桌面 scrcpy 参考实现（genymobile/scrcpy
  `app/src/video_buffer.c` / js 参考实现）的标准做法：`decodeQueueSize()`
  超阈值且当前为 delta 帧时丢弃（不丢 key 帧）。
- `optimizeForLatency: true` 已设置（`h264VideoStream.ts:382`）✓，但缺少
  队列水位控制。

**D. 后端 socket 无 TCP_NODELAY**

- 位置：`backend/app/infrastructure/stream/scrcpy.py:297-300、339-341`
  （`asyncio.open_connection`，默认不启用 TCP_NODELAY）与 `video.py`
  WS 发送侧。
- 设备端 scrcpy 对控制/视频 socket 都启用 nodelay（scrcpy 源码
  `server.c: set_tcp_nodelay`）；本侧不设会造成 Nagle 延迟（小包迟滞
  ~40ms 合成延迟，随 ACK 节奏抖动）。影响低于 A/C，但一行可修。

**E. H264Parser 纯 Python 逐字节扫描（多设备卡的第一主因，后端 CPU）**

- 位置：`backend/app/scrcpy/h264_parser.py:63-139`。
  `_find_start_code` 逐字节 Python 循环扫描；每次提取 NALU 后
  `self._buffer = self._buffer[next_start:]` 整段复制。
- **本地 benchmark（2026-09-18，模拟 4Mbps 运动画面流 11.8MB/3600 NALU）**：
  - 现状实现：**4.6 MB/s**
  - bytes.find + 收缩缓冲对照实现：**885 MB/s（190.9 倍）**
- 换算：一条 4Mbps 流（0.5MB/s）解析占 ~**11% 单核 CPU**；3 台设备 ≈ 33%。
  后端是单进程 asyncio + GIL，所有流的解析、WS 发送、perf 采样共享同一
  事件循环——三路流即可逼近单核满载，表现为「多设备时每台都卡」。
- 修复成本最低、收益最大（见 2.1 实施项 1）。

**F. perf 采样每设备每轮 5 个 adb 子进程，含 2 次重复 dumpsys（多设备卡第二主因）**

- 位置：`backend/app/infrastructure/performance/sampler.py:93-110`
  （`_collect_once` 串行调用 cpu/mem/fps/activity）+ `:209`（
  `_get_fps_and_jank` **内部再次调用** `_get_current_activity`——dumpsys
  activity activities 每轮执行 2 次，共 5 个 shell 进程/轮/设备）。
- 日志实锤（2026-09-18 06:46:38.719 与 .768 两次相邻
  `get_current_activity_failed`，间隔 49ms）。
- 成本：Windows 上 5 次 `create_subprocess_exec` + adb server 转发 +
  设备端 `dumpsys gfxinfo`/`dumpsys activity`（rk3568 上数百 ms 级 CPU）。
  3 台设备 = **15 子进程/s** + 设备端 system_server 持续被 dumpsys 拖占，
  与编码器/SurfaceFlinger 争抢设备 CPU。
- 旁证：失联设备 .33 仍被无休止轮询，每 ~1s 4 条失败命令刷屏
  （`adb_command_failed ... not found`），浪费进程与日志。

**G. Wi-Fi 带宽共享（多设备卡第三主因，链路层）**

- 多台设备的 4Mbps 视频流 + 控制 + adb 命令粪享同一无线信道
  （PC 与设备均为无线时更甚，半双工）。单设备 4Mbps 无压力，
  3 台 ≈ 12Mbps 上行 + 下行，接近 2.4G/拥挤 5G 信道可用带宽时
  开始排队丢包 → 帧延迟抖动。
- 缓解：自适应码率已有（`bitrate_advisor.py`），但仅凭客户端 fps 上报，
  对静止画面（fps≈0）不上报（`VideoPlayer.vue` 注释），需观察拥塞路由。
  详见 2.4 实验项。

**H. 浏览器多标签页解码争抢（单看一台仍卡的放大器）**

- 每台设备一个标签页；Chromium 同 site 多 tab 共享渲染进程，
  **后台标签页的 WebCodecs 解码与 drawImage 仍在运行**（output 回调
  不受 rAF 节流）。用户「单看其中一台」时，其余 tab 持续消耗
  CPU/GPU → 前台 tab 的解码渲染被拖慢。
- 缓解：Page Visibility API——`visibilitychange` 后台化时挂起解码
  （decoder 保留但暂停 submit 或切换低费率轮询），回到前台恢复。
  属前端可实施的降载项。

**I. 日志无条件采集与拉取（隐性资源消耗，随设备数线性放大）**

- 后端 `debug_service.py:101`：`create_session()` **无条件**启动
  `_collect_logcat` 后台任务（每会话一个 `adb logcat` 子进程 + 逐行解析 +
  `BatchLogWriter` 落库）；`restore_sessions()`（:174）服务重启后同样恢复
  采集。前端 `DeviceDetail.vue:94` 打开设备详情页即 `createSession`，
  `LogcatView.vue` onMounted 无条件 `connectWebSocket()` + `fetchLogs()`。
- 即使用户从不打开日志标签、从不开启录制，每台设备都常驻一个 logcat
  子进程在解析与落库 —— 与根因 F 同族的「子进程 + 事件循环」消耗，
  多设备时叠加放大，日志噪音同时淹没后端日志。
- **已按需的部分**（无需改动）：订阅者推送（`subscribe` 默认 paused、
  `_notify_subscribers` paused 时跳过，前端 `isRecording` 默认 false 且
  connect 时带 `paused: true`）。**未按需的部分**：采集本身与前端挂载即
  拉取（见 2.5 实施项 5）。

### 1.4 影响面

- **P0 项（1、2、3）**：改动集中在后端解析器与前端流服务，不触碰设备端
  scrcpy 协议、不改变 WS 消息协议；对集成测试（tests/integration）无影响，
  但 `tests/scrcpy/test_encoder.py`（如覆盖 parser 路径）需同步。
- **P1 项（4、5）**：perf 采样行为变化影响调试面板性能图表（fps 采集频率
  降低后曲线更平滑，无功能缺失）；失联自动停采样影响「设备重连后自动恢复
  监控」的既有行为，恢复策略需明确（见 2.2）。
- **实施项 5（日志按需）**：行为变化仅影响日志标签页的数据流（暂停时不再
  有历史拉取与实时推送）；Shell/网络/性能标签不受影响（WS 断线重连逻辑
  需加 isRecording 门，见 2.5）。
- 均不涉及四层架构变更（解析器属 `app/scrcpy` 工具层，sampler 属基础设施层内部）。

## 二、方案设计

### 2.1 实施项 1（P0）：H264Parser 重写为 bytes.find + 收缩缓冲

- **文件**：`backend/app/scrcpy/h264_parser.py`
- **做法**：`feed()` 内用 `bytearray.find(b'\x00\x00\x01', start)`
  （C 级扫描）定位起始码；找到第二个起始码后 `del buf[:next_start]`
  收缩（缓冲通常 <64KB，del 头部成本可忽略）；4 字节起始码通过
  3 字节定位偏移回看兼容（0x00 00 00 01 中含 00 00 01 于偏移 1，
  归属前一 NALU 无损）。
- **基准**：benchmark 从 4.6 MB/s → ~885 MB/s；解析 CPU 从 ~11%/路
  → ~0.06%/路。
- **测试**：`tests/scrcpy/test_h264_parser.py` 保留全部既有用例（跨 chunk
  NALU、4/3 字节起始码混用、无起始码、reset），新增：
  - 大帧（>64KB）跨多 chunk；
  - 连续起始码边界（空 NALU）；
  - 与现状实现的**对拍**（同一随机流，两种实现产出逐字节一致——用
    随机种子构造 200 组随机 NALU 流断言输出相同，防解析语义回归）。

### 2.2 实施项 2（P0）：前端解码队列积压丢帧

- **文件**：`frontend/src/services/h264VideoStream.ts`
- **做法**：
  ```ts
  // handleBinaryFrame 内 decode 前：
  if (this.decoder.decodeQueueSize >= MAX_DECODE_QUEUE && !isKeyFrame) {
    this._droppedFrames++   // 纳入 stats 展示
    return                  // 丢 delta 帧，不丢 key 帧
  }
  ```
  `MAX_DECODE_QUEUE` 取 2（参考 scrcpy 官方：>2 时开始丢 delta）。
- **测试**：vitest 纯函数化阈值判定（`shouldDropFrame(queueSize, isKey)`）
  + 既有 fallback 测试全绿。
- 附：stats 面板增加「丢帧」计数，便于观察积压发生。

### 2.3 实施项 3（P1）：perf 采样治理

- **文件**：`backend/app/infrastructure/performance/sampler.py`、
  `backend/app/application/performance_service.py`
- **做法**：
  1. 消除重复：`_collect_once` 把 `_get_current_activity()` 结果传入
     `_get_fps_and_jank(package, ...)`，删除内部重查（5 → 4 进程/轮）；
  2. 4 个采集改 `asyncio.gather` 并发（一轮耗时 = max(单命令) 而非 sum，
     同时降低事件循环上的串行占窗）；
  3. dumpsys gfxinfo（最重）降频：每 5 轮采集一次、fps 沿用上次有效值
     （`PerformanceMetrics.fps` 语义不变）；
  4. **失联自动停采样**：连续 `MAX_FAILURES=5` 次采样失败 → 停止该设备
     监控任务并记 warning（设备恢复后需用户重启监控或 list_devices 时
     自动恢复——评审时定，倾向「手动重启」，简单可预期）；
  5. shell 命令需总超时兜底（防 dumpsys 挂起拖死采样循环）。
- **测试**：`tests/infrastructure/test_sampler.py` 补：重复调用消除
  （Mock adb 断言每轮 shell 调用次数 4 次）、失败 N 次自动停、
  降频行为。

### 2.4 实施项 4（P2，实验）：流畅度实验与调参

- **TCP_NODELAY**（一行）：`scrcpy.py` 两个 `open_connection` 后
  `writer.transport.get_extra_info('socket').setsockopt(IPPROTO_TCP,
  TCP_NODELAY, 1)`（Windows 与 Linux 均可用）。
- **Rockchip 降档实验**（.18 专项）：`config/base.yaml` 为该设备试
  `stream.fps: 60→30`、`bit_rate: 4M→2M`，观察 vpu 故障复现率是否下降
  （E009 提示 RK3288 降参无效，rk3568 未验证——按经验记录流程先实验后
  定论，不做默认项）。
- **Page Visibility 降载**：`VideoPlayer.vue` 监听 `visibilitychange`，
  隐藏时停 fps 上报 + 暂停 inputController 激活（解码保留，Chrome 对
  后台 tab 本会节流定时器；此项按实测收益决定是否落地）。

### 2.5 实施项 5（P1）：日志按需采集与展示

- **后端文件**：`backend/app/application/debug_service.py`
- **做法（惰性启动采集）**：
  1. `create_session()` 与 `restore_sessions()` 不再启动 `_collect_logcat`；
  2. 在 `set_subscriber_filter(paused=False)` 时：若该 session 尚无采集任务，
     启动采集（`asyncio.create_task`，登记进 `logcat_tasks`，任务内自行清理）；
  3. 停采时机：`set_subscriber_filter(paused=True)` 且该 session 已无任何
     paused=False 的订阅者 → cancel 采集任务（内存 buffer 保留，历史可查）；
     订阅者断开（unsubscribe）后同样判定停采；
  4. 采集任务需保证幂等（启动前查 `logcat_tasks` 防重复），停止后再次
     paused=False 可重启；
  5. 保留 500ms 停采宽限（`asyncio.sleep` 后复查），防录制开关抖动导致
     logcat 子进程频繁启停。
  - 注意：`close_session()` 已有 cancel 逻辑，任务字典入口在停止后需移除
    （否则 close 时二次 cancel 无害但记 warning）。
- **前端文件**：`frontend/src/components/debug/LogcatView.vue`、
  `frontend/src/stores/debug.ts`
- **做法（开启录制才连接拉取）**：
  1. `LogcatView` onMounted **不再**直接 `connectWebSocket()`/`fetchLogs()`；
     改为 watch `debugStore.isRecording`：false→true 时先 `connectWebSocket()`
     再 `fetchLogs()`（拿历史），随后订阅推送自动生效（connect 时已按
     isRecording 发 paused）；true→false 时断开 WS（或保持连接仅 paused=true，
     评审时定——倾向断开，彻底省资源）。
  2. 初始 isRecording=false：页面显示「日志录制已暂停，开启后开始接收」，
     不发起任何网络请求；
  3. `debug.ts` 的意外断线自动重连加门：`!isRecording.value` 时不重连
     （当前 close handler 无条件 2s 重连）；
  4. 开启录制后新日志按现有滚动行为滚动显示（确认 LogcatView 的自动滚动
     仅在新日志追加时触发，历史载入不整页跳动）。
- **测试**：
  - 后端：`tests/application/test_debug_service.py`（如存）补：create 后
    logcat_tasks 为空；paused=False 触发采集启动（assert task 创建）；
    全部订阅者 paused 后停采；close 幂等。
  - 前端：vitest 对 debug store 的 setRecording 行为与重连门（mock
    WebSocketService）；LogcatView 挂载不发请求（mock api/ws 断言零调用）。
- **预期收益**：每台未看日志的设备省 1 个常驻 adb logcat 子进程 + 解析 +
  落库 I/O；多设备（尤其 .33 类失联设备）不再空跑采集、不再刷日志噪音。

### 2.6 明确不做（本期）

- 不重写为 `send_frame_meta=true` 帧分界协议（改动大、收益被实施项 1 吸收）。
- 不做 WebTransport/WebCodecs 之外的传输层替换。
- 不做「未观看设备自动停流」的服务端架构改造（需会话/观看者模型，另立方案）。

## 四、测试与验证

### 4.1 自动化

- 解析器：既有用例 + 对拍（2.1）。
- 前端丢帧判定：vitest。
- sampler：调用次数/自动停/降频（2.3）。
- 日志按需：后端惰性启动/停采、前端挂载零请求与重连门（2.5）。
- 全量门禁：`PYTHONPATH=backend python -m pytest tests/ -v`（排除
  integration/e2e）+ ruff + mypy strict；前端 vitest + eslint + build。

### 4.2 实测对照（手动）

- **后端解析 CPU**：修复前后对同一活跃流观察后端进程 CPU（任务管理器或
  psutil 采样），预期从 ~11%/路降至 <1%。
- **端到端滞后测量**：设备端打开时钟/秒表应用，前端截图与设备屏显对比
  （截图模式与 H264 模式各测 3 次取中位数），预期截图模式
  <2.5s → 输入触发刷新后 <800ms；H264 正常设备 <300ms。
- **多设备对照**：2 台可用设备（.18/.22）同时开流，逐台目视帧率与操作
  响应；有量化能力时用 `getPerfMetrics` 或浏览器 FPS 计数器记录。
- **日志按需**：不开启录制时后端进程列表无该设备的 `adb logcat` 子进程
  （Windows `tasklist` / `wmic process` 观察），前端 Network 面板无
  `/logs` 请求；开启录制后日志正常滚动显示且历史可见。
- 验证时设备约束：仅 .22 与 .18 可操作（.33 禁用）。

## 五、风险评估

| 风险 | 影响 | 缓解 |
|------|------|------|
| 解析器重写引入解析语义回归（起始码边界） | H264 花屏/断流 | 随机流对拍测试（2.1）+ 全部门禁 + 实测 |
| 丢帧策略过于激进导致观感劣化 | 画面跳变 | 阈值仅作用于积压态（queue>2），静止场景不触发 |
| sampler 降频后调试面板 fps 曲线稀疏 | 轻微 | 每 5s 采样 + 前端平滑，语义不变 |
| 失联自动停采样后设备恢复不自动续采 | 监控断档 | 行为明确化（手动重启），日志提示 |
| 惰性采集启动竞态（多订阅者同时 paused=False） | logcat 任务重复启动 | 幂等启动（查任务字典）+ 停采宽限复查 |
| 停采后历史日志缺失（采集间隔内日志不落库） | 开启录制前无历史 | 语义即「按需」——开启时才从当前时刻起收，文案明示 |
