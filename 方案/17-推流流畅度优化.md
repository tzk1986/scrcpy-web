## 一、问题分析

### 1.1 现象（用户报告）

1. **操作后画面比实际屏幕滞后**：点击/滑动后，画面反馈明显晚于设备实际屏幕。
2. **连接多设备时单独看一台设备更卡**：同时连接多台设备推流时，即使只看其中一台，
   该台的流畅度也低于只连一台时的表现。
3. **日志无条件采集浪费资源**：打开设备详情页即在后端启动 logcat 采集 + 前端拉取
   历史日志，即使用户从不看日志（新增需求：不需要日志时不请求，开启日志时才拉取
   并滚动显示）。

### 1.2 现状链路走查

单设备视频链路：

```
设备屏幕 → scrcpy-server 硬编码(OMX/rk) → TCP(adb forward 隧道)
  → 后端 read_socket(64KB chunk) → _data_queue(maxsize=100)
  → ScrcpyEncoder.start yield → video.py: H264Parser.feed 逐 NALU 解析
  → websocket.send_bytes(每 NALU 一条) → 浏览器 H264VideoStream
  → annexBToAvcc+isKeyFrame 双重 extractNalus 扫描 → VideoDecoder.decode
  → output 回调 drawImage(canvas) → 用户眼睛
```

平行负载（每设备）：`PerformanceSampler` 1s 间隔串行执行 5 个 adb shell
子进程命令（见 1.3 根因 F）。

**协议备注**：启动参数显式 `raw_stream=true` + `send_frame_meta=false`
（`scrcpy.py:191-192`），设备端输出**无 12 字节包头的纯 Annex B 流**，
这就是后端必须扫描起始码解析 NALU 的原因——该包头（含 config/keyframe
标志 + PTS + 长度，scrcpy-server 默认开启）是自选放弃的免费帧边界信息，
见根因 E 与实施项 1b。

### 1.3 根因（按证据强度与影响排序）

**A. 截图模式固定 1.5s 轮询（滞后主因，截图模式下）**

- 位置：`frontend/src/services/videoStream.ts:49`（默认 refreshInterval=1500ms）
  + `backend/app/infrastructure/adb/cli.py:421-435`（`screencap -p` 单命令）。
- `screencap -p` 在 rk3568 上实测需数百 ms，加上 HTTP 往返与 createImageBitmap，
  用户操作后的画面反馈滞后 **1.5~2.5s**。截图模式是 .18（Rockchip）设备的
  当前主模式（H264 编码器故障，见根因 B），因此感知最直接。
- 改进空间：轮询间隔参数化/自适应；输入操作后立即触发一次截屏刷新（事件驱动
  截屏），操作反馈从 1.5s 降到 ~500ms。

**B. Rockchip 设备硬编码器故障导致 0.4fps（单设备大滞后，设备端）**

- 实测证据（后端日志 2026-09-18 会话 2）：06:46:39.6 第 5 帧后停帧，
  06:50:02 恢复至 frame 97、06:54:05 frame 197 —— **恢复后
  243 秒仅 100 帧 ≈ 0.4fps**。设备 OMX.rk.video_encoder.avc 先崩溃
  （14:44 session：`Observer died` + `Cleaning up`）后进入低性能卡顿态
  （vpu_api_legacy 周期性 rate-control 重配置、只吐 SPS/PPS 不出帧）。
- 与 docs/经验记录.md E009（RK3288）同族。**无软件根治**，靠
  「故障时回退截图 + 恢复后自动回切」（已实施于 2026-09-18，commit 508d0b8）
  兜底。后续可评估 30fps/2Mbps 降档是否降低故障率（实验项，见 2.4）。

**C. 前端无解码队列积压控制 + 每帧双重 JS 扫描（H264 模式滞后随时间单调增长）**

- 无积压控制：`frontend/src/services/h264VideoStream.ts:360-420`
  `handleBinaryFrame` 每帧无条件 `decoder.decode()`，WebCodecs 内部解码
  队列没有积压检测与丢帧策略。渲染/解码跟不上（CPU 抖动、后台 tab
  争抢、多设备同屏）时，队列积压 → 画面滞后随时间无界增长。
- **双重扫描（本轮评审新增）**：同一帧数据被 `annexBToAvcc()` 与
  `isKeyFrame()` **各跑一遍 `extractNalus`**（:392、:395），且内层
  `extractNalus` 从 naluStart+1 逐字节找下一起始码（O(n²) 双层循环）。
  4Mbps/30fps 流下每帧两遍 JS 字节扫描 ≈ 与后端 Python 逐字节扫描同量级
  的开销，方案初版遗漏了这一点。另有每消息 `TextDecoder.decode` JSON
  探测（:363，binaryType=arraybuffer 下 JSON 走 string 通道，探测多余）
  与逐帧 `console.log` 噪音。
- 与 scrcpy 官方桌面版的差异（调研 @ 19c1261）：官方**解码线程不丢帧**，
  靠渲染端「单槽帧缓冲」丢最旧留最新（frame_buffer 恒缓冲 1 帧，
  screen.c 事件合并）。Web 端输出回调直接 drawImage 天然等效单槽渲染，
  故我们丢的是**解码输入端**帧——丢 key 帧会让后续 delta 全部花屏直到
  下个 IDR（设备端 I 帧间隔 10s），所以必须「丢 delta 保 key」，与官方
  不保 key 的差异由此而来。
- `optimizeForLatency: true` 已设置（`h264VideoStream.ts:476-480`）✓。
- 另：后端每 NALU 一条 WS 消息（video.py:151），多 slice Access Unit 会被
  切碎为多条消息并由前端当作多个独立 chunk 提交——协议层帧聚合隐患，
  见实施项 1a 尾步骤。

**D. 后端 socket 无 TCP_NODELAY（评审后降级：几乎无收益）**

- 位置：`backend/app/infrastructure/stream/scrcpy.py:297-300、339-341`
  （`asyncio.open_connection`，默认不启用 TCP_NODELAY）与 `video.py`
  WS 发送侧。
- **评审修正（代码走查 + scrcpy 官方调研）**：① 这两个 socket 连接目标是
  **127.0.0.1 本地回环**，Nagle 只延迟「小于 MSS 的未确认小包」，回环上
  无网络往返延迟、几乎立即 ACK，Nagle 影响≈0；② scrcpy 官方桌面版**只对
  控制 socket** 设 nodelay（server.c:708-714 → net.c:272-285），视频
  socket 只收不发、设备侧还是 UNIX socket；③ Windows Proactor 事件循环下
  `transport.get_extra_info('socket')` 拿不到 socket（只暴露 `'pipe'`），
  初版方案的写法在 Windows 直接失效。
- 结论：视频路径 nodelay 没有可感知收益，**实施项 4 中降级为「可顺手做，
  不作为独立收益项」**；若做，仅 WS 服务端发送侧（浏览器可能位于局域网
  远端机器）且需按平台获取 socket。

**E. H264Parser 纯 Python 逐字节扫描（多设备卡的第一主因，后端 CPU）**

- 位置：`backend/app/scrcpy/h264_parser.py:63-139`。
  `_find_start_code` 逐字节 Python 循环扫描；每次提取 NALU 后
  `self._buffer = self._buffer[next_start:]` 整段复制。
- **本地 benchmark（2026-09-18，模拟 4Mbps 运动画面流 11.8MB/3600 NALU）**：
  - 现状实现：**4.6 MB/s**
  - bytes.find + 收缩缓冲对照实现：**885 MB/s（190.9 倍）**
- 换算：一条 4Mbps 流（0.5MB/s）解析占 ~**11% 单核 CPU**；3 台设备 ≈ 33%。
  后端是单进程 asyncio + GIL，所有流的解析、WS 发送、perf 采样共享同一
  事件循环——三路流即可逼近单核满载，表现为「多设备时每台都卡」。
- **根治方案存在（评审新增）**：scrcpy-server 的 `send_frame_meta` **默认
  开启**（Options.java:86），视频包自带 12 字节头（config/keyframe 标志
  bit62/61 + PTS + 4 字节长度，demuxer.c:14-17、Streamer.java:107-124）。
  本仓显式关掉了它改用 raw 流，才把「按长度字段 O(1) 切帧」退化成「全量
  扫起始码」。改回默认协议只需调整启动参数与后端读取逻辑，前端零改动
  （见 2.1 实施项 1b）。
- 修复成本低、收益最大有两种路径，见 2.1（1a 快赢 / 1b 根治）。

**F. perf 采样每设备每轮 5 个 adb 子进程，含 2 次重复 dumpsys（多设备卡第二主因）**

- 位置：`backend/app/infrastructure/performance/sampler.py:93-110`
  （`_collect_once` 串行调用 cpu/mem/fps/activity）+ `:209`（
  `_get_fps_and_jank` **内部再次调用** `_get_current_activity`——dumpsys
  activity activities 每轮执行 2 次，共 5 个 shell 进程/轮/设备）。
- 日志实锤（2026-09-18 06:46:38.719 与 .768 两次相邻
  `get_current_activity_failed`，间隔 49ms）。
- 成本：Windows 上 5 次 `create_subprocess_exec` + adb server 转发 +
  设备端 `dumpsys gfxinfo`/`dumpsys activity`（rk3568 上数百 ms 级 CPU）。
  3 台设备 = **15 子进程/s** + 设备端 system_server 持续被 dumpsys 拖占，
  与编码器/SurfaceFlinger 争抢设备 CPU。
- 旁证：失联设备 .33 仍被无休止轮询，每 ~1s 4 条失败命令刷屏
  （`adb_command_failed ... not found`），浪费进程与日志。

**G. Wi-Fi 带宽共享（多设备卡第三主因，链路层）**

- 多台设备的 4Mbps 视频流 + 控制 + adb 命令共享同一无线信道
  （PC 与设备均为无线时更甚，半双工）。单设备 4Mbps 无压力，
  3 台 ≈ 12Mbps 上行 + 下行，接近 2.4G/拥挤 5G 信道可用带宽时
  开始排队丢包 → 帧延迟抖动。
- 缓解：自适应码率已有（`bitrate_advisor.py`），但仅凭客户端 fps 上报，
  对静止画面（fps≈0）不上报（`VideoPlayer.vue` 注释），需观察拥塞路由。
  详见 2.4 实验项。

**H. 浏览器多标签页解码争抢（单看一台仍卡的放大器）**

- 每台设备一个标签页；Chromium 同 site 多 tab 共享渲染进程，
  **后台标签页的 WebCodecs 解码与 drawImage 仍在运行**（output 回调
  不受 rAF 节流）。用户「单看其中一台」时，其余 tab 持续消耗
  CPU/GPU → 前台 tab 的解码渲染被拖慢。
- 缓解：Page Visibility API——`visibilitychange` 后台化时挂起解码
  （decoder 保留但暂停 submit 或切换低费率轮询），回到前台恢复。
  属前端可实施的降载项。

**I. 日志无条件采集与拉取（隐性资源消耗，随设备数线性放大）**

- 后端 `debug_service.py:101`：`create_session()` **无条件**启动
  `_collect_logcat` 后台任务（每会话一个 `adb logcat` 子进程 + 逐行解析 +
  `BatchLogWriter` 落库）；`restore_sessions()`（:174）服务重启后同样恢复
  采集。前端 `DeviceDetail.vue:94` 打开设备详情页即 `createSession`，
  `LogcatView.vue` onMounted 无条件 `connectWebSocket()` + `fetchLogs()`。
- 即使用户从不打开日志标签、从不开启录制，每台设备都常驻一个 logcat
  子进程在解析与落库 —— 与根因 F 同族的「子进程 + 事件循环」消耗，
  多设备时叠加放大，日志噪音同时淹没后端日志。
- **已按需的部分**（无需改动）：订阅者推送（`subscribe` 默认 paused、
  `_notify_subscribers` paused 时跳过，前端 `isRecording` 默认 false 且
  connect 时带 `paused: true`）。**未按需的部分**：采集本身与前端挂载即
  拉取（见 2.5 实施项 5）。

### 1.4 影响面

- **实施项 1a/2（P0）**：改动集中在后端解析器与前端流服务，不触碰设备端
  scrcpy 协议、不改变 WS 消息协议；对集成测试（tests/integration）无影响，
  但 `tests/scrcpy/test_encoder.py`（如覆盖 parser 路径）需同步。
- **实施项 1b（P1，评审新增）**：改动后端 `ScrcpyEncoder.start`（恢复
  协议握手读取）与 `video.py`（长度切帧替代起始码扫描）；**前端与 WS 消息
  协议完全不变**（仍收 Annex B NALU bytes）。风险点在设备端兼容性，需
  真机冒烟（.22/.18）验证后转正。
- **P1 项（3、5）**：perf 采样行为变化影响调试面板性能图表（fps 采集频率
  降低后曲线更平滑，无功能缺失）；失联自动停采样影响「设备重连后自动恢复
  监控」的既有行为，恢复策略需明确（见 2.3）。
- **实施项 5（日志按需）**：行为变化仅影响日志标签页的数据流（暂停时不再
  有历史拉取与实时推送）；Shell/网络/性能标签不受影响（WS 断线重连逻辑
  需加 isRecording 门，见 2.5）。
- 均不涉及四层架构变更（解析器属 `app/scrcpy` 工具层，sampler 属基础设施层内部）。

## 二、方案设计

### 2.1 实施项 1（P0）：后端解析根治（1a 快赢 + 1b 协议化）

#### 1a（P0，立即实施）：H264Parser 重写为 bytes.find + 收缩缓冲

- **文件**：`backend/app/scrcpy/h264_parser.py`
- **做法**：`feed()` 内用 `bytearray.find(b'\x00\x00\x01', start)`
  （C 级扫描）定位起始码；每提取一个 NALU 后 `del buf[:next_start]`
  收缩（出帧后缓冲通常 <1KB，del 头部成本可忽略）。
- **4 字节起始码的修正规则（评审修正，初版表述有语义错误）**：不能
  「仅搜 3 字节码并把偏移 1 的命中归属前一 NALU」——那样会把 4 字节码
  切碎（前一 NALU 尾多 2 个 0、后一 NALU 起始码残缺）。正确做法：命中
  3 字节码位置 i 后**回看一字节**，`i>=1 and buf[i-1]==0x00` 时把起始
  位置修正为 `i-1`（吸收 4 字节码），下一轮从修正位置 +4（或 +3）继续
  扫描；提取右边界 = 下一修正后起始位置。对拍测试兜语义回归。
- **基准**：benchmark 从 4.6 MB/s → ~885 MB/s（对照实现已本地验证）；
  4Mbps/路解析 CPU 从 ~11% → <0.1%。
- **测试**：`tests/scrcpy/test_h264_parser.py` 保留全部既有用例（跨 chunk
  NALU、4/3 字节起始码混用、无起始码、reset），新增：
  - 大帧（>64KB）跨多 chunk；
  - 连续起始码边界（空 NALU）；
  - **4/3 字节码紧邻混用**（专测回看修正：`00 00 00 01` 后紧跟
    `00 00 01`，断言两 NALU 边界字节零漂移）；
  - 与现状实现的**对拍**（同一随机流，两种实现产出逐字节一致——用
    随机种子构造 200 组随机 NALU 流断言输出相同，防解析语义回归）。

#### 1a 尾步骤（P1，需真机验证）：后端按帧聚合发送

- **文件**：`backend/app/interfaces/ws/video.py`
- **动机**：现状每 NALU 一条 WS 消息（video.py:151），30fps × 多 NALU/帧
  = 数百消息/s/路；多 slice Access Unit 还会被切碎为多条消息，前端把
  每个消息当独立 chunk 提交（协议层帧聚合隐患）。
- **做法**：`parser.feed()` 产出 NALU 后按启发式聚成 Access Unit 再
  `send_bytes`（消息数降 ~5-10 倍；前端 `annexBToAvcc` 天然支持多 NALU
  消息，**无需改动**）：SEI(6)/SPS(7)/PPS(8) 挂到后继 VCL；IDR(5) 与
  非 IDR slice(1) 为新帧起点；AUD(9) 显式分界。
- **假设与验证**：假设设备编码器每 AU 单 slice（rk3568 MediaCodec 常态）。
  真机 .22/.18 各验证 30s 帧序正确（前端 frameCount 增长与画面无撕裂），
  验证失败（多 slice 帧出现）则回退逐 NALU 发送，等 1b 落地后由包头
  size 精确聚帧。
- **测试**：纯函数化聚合逻辑（`aggregate_aus(nalus) -> list[bytes]`），
  `tests/scrcpy/test_au_aggregator.py` 覆盖 SPS/PPS/SEI 挂靠、连续 slice
  聚合、AUD 分界。

#### 1b（P1，评审新增·根治）：改回 scrcpy-server 默认 12 字节头协议

- **依据**：`send_frame_meta` 官方默认开启（12B 头 = config/keyframe 标志
  + PTS + 4B size）；本仓显式 `raw_stream=true` 关掉了它。改回默认后
  「扫起始码」退场，按 size 字段 O(1) 切帧，直接消除根因 E 的全部解析
  CPU，还白得 config/keyframe 标记（前端丢帧判定与恢复探测不再需要自扫
  NALU 类型，虽协议不变前端可暂不利用）。
- **文件**：`backend/app/infrastructure/stream/scrcpy.py` +
  `backend/app/interfaces/ws/video.py`
- **做法**：
  1. 启动参数去掉 `raw_stream=true`、`send_frame_meta=false`（改回默认
     协议，或显式 `send_frame_meta=true`）；
  2. `ScrcpyEncoder.start` 恢复协议握手读取：1B dummy + 64B 设备名 +
     4B codec + 4B w + 4B h（scrcpy v2.4，头部注释已记载协议流；分辨率
     从此不再依赖 `adb shell wm size` 子进程）；
  3. 视频数据读循环改为 12B 头 + size 载荷切包，产出完整 packet（跨
     chunk 缓冲）；config 包（flags bit62）提取 SPS/PPS 走既有
     `_send_config`，非 config 包按 keyframe 标志（bit61）标记后交给
     帧聚合发送（AU 边界由包头 size 精确定义，替代 1a 尾步骤的启发式）。
- **前端影响**：**零改动**——后端仍按 Annex B 字节发 NALU，config 仍走
  既有 JSON 消息。
- **验证（转正条件）**：真机 .22（正常编码器）与 .18（Rockchip 故障型）
  各冒烟 10 分钟：画面正常、config 重复下发（码率重启场景）正常、编码器
  崩溃/恢复（.18 场景）行为与 raw 流一致；通过后转正为标准实现，
  1a 的 H264Parser 保留为兜底回退路径（配置开关）。
- **顺带收益**：包边界丢帧（替换现有 64KB chunk 超时丢块的半帧损坏问题）、
  PTS 可用于前端 chunk timestamp（当前恒 0）、恢复探测可用 media 标志
  替代帧扫描。

### 2.2 实施项 2（P0）：前端解码路径治理

- **文件**：`frontend/src/services/h264VideoStream.ts`
- **做法**：
  1. **单遍扫描**（评审新增）：`handleBinaryFrame` 合并 `annexBToAvcc`
     与 `isKeyFrame` 的双重 `extractNalus` 为一次调用，产出
     `{ nalus, hasIdr }` 供转换与 key 判定共用；`extractNalus` 内层
     起始码查找改为单指针推进（消除 O(n²) 双层循环的重复扫描段）。
  2. **删除每消息无谓开销**：TextDecoder JSON 探测（binaryType=
     arraybuffer + Chromium 专属约束下 JSON 走 string 通道，探测是
     纯浪费）；逐帧 `console.log` 收敛为仅前 5 帧 + 异常路径。
  3. **积压丢帧**：
     ```ts
     // handleBinaryFrame 内 decode 前：
     if (this.decoder.decodeQueueSize >= MAX_DECODE_QUEUE && !isKeyFrame) {
       this._droppedFrames++   // 纳入 stats 展示
       return                  // 丢 delta 帧，不丢 key 帧
     }
     ```
     `MAX_DECODE_QUEUE` 取 2。**保 key 的理由**（与官方实现差异，见根因
     C）：Web 端丢的是解码输入帧，丢 key 会导致后续 delta 全花屏直至
     下一个 IDR（设备端 I 帧间隔 10s）；官方桌面端丢的是已解码帧，
     前后帧都合法，所以无需保 key。scrcpy-server 无 IDR 请求控制消息
     （master 调研确认），丢帧策略必须保守。
  4. **严重积压恢复（可选增强）**：若积压跨越一个 IDR 仍 > 阈值（即
     `hasIdr && queueSize >= MAX`），调用 `decoder.reset()` 清空队列并
     以当前 key 帧重新解码——对应 ws-scrcpy「I 帧到达时清空 framesList
     跳新帧」的做法，比逐帧丢更干净。
- **测试**：vitest 纯函数化阈值判定（`shouldDropFrame(queueSize, isKey)`）
  + 单遍扫描行为（mock Uint8Array 断言 extractNalus 调用次数为 1）
  + 既有 fallback 测试全绿。
- 附：stats 面板增加「丢帧」计数，便于观察积压发生。

### 2.3 实施项 3（P1）：perf 采样治理

- **文件**：`backend/app/infrastructure/performance/sampler.py`、
  `backend/app/application/performance_service.py`
- **做法**：
  1. 消除重复：`_collect_once` 把 `_get_current_activity()` 结果传入
     `_get_fps_and_jank(package, ...)`，删除内部重查（5 → 4 进程/轮）；
  2. 4 个采集改 `asyncio.gather` 并发（一轮耗时 = max(单命令) 而非 sum，
     同时降低事件循环上的串行占窗）；
  3. dumpsys gfxinfo（最重）降频：每 5 轮采集一次、fps 沿用上次有效值
     （`PerformanceMetrics.fps` 语义不变）；
  4. **失联自动停采样**：连续 `MAX_FAILURES=5` 次采样失败 → 停止该设备
     监控任务并记 warning（设备恢复后需用户重启监控或 list_devices 时
     自动恢复——评审时定，倾向「手动重启」，简单可预期）；
  5. shell 命令需总超时兜底（防 dumpsys 挂起拖死采样循环）。
- **测试**：`tests/infrastructure/test_sampler.py` 补：重复调用消除
  （Mock adb 断言每轮 shell 调用次数 4 次）、失败 N 次自动停、
  降频行为。

### 2.4 实施项 4（P2，实验）：流畅度实验与调参

- **TCP_NODELAY（降级为顺手项，评审修正）**：仅当 WS 服务端发送侧服务
  于局域网远端浏览器时略有余量；且 Windows Proactor 下需按平台取
  socket（`get_extra_info('socket')` 为 None 时回退 `'pipe'`）。视频/
  控制 socket 是 loopback、官方也只对控制 socket 设置（见根因 D），
  **不做为独立收益项**。
- **Rockchip 降档实验**（.18 专项）：`config/base.yaml` 为该设备试
  `stream.fps: 60→30`、`bit_rate: 4M→2M`、`max_fps=30`（ws-scrcpy 对
  低端设备即取 480×480@24fps/512kbps/i-frame 5s 的低档策略，我们的
  max_size=0 坐标约束限制分辨率降档，仅试帧率/码率），观察 vpu 故障
  复现率是否下降（E009 提示 RK3288 降参无效，rk3568 未验证——按经验
  记录流程先实验后定论，不做默认项）。
- **解码硬件加速降级实验**（评审新增）：ya-webadb 对硬解错误自动降级
  `hardwareAcceleration: 'prefer-software'` 并重放保存的关键帧序列。
  .18 花屏/解码错误时可试 `prefer-software` 能否规避 Chromium 硬解与
  Rockchip 码流的兼容问题（Chrome 专属，成本一个配置项）。
- **Page Visibility 降载**：`VideoPlayer.vue` 监听 `visibilitychange`，
  隐藏时停 fps 上报 + 暂停 inputController 激活（解码保留，Chrome 对
  后台 tab 本会节流定时器；此项按实测收益决定是否落地）。
- **确认 repeat-previous-frame 行为**：scrcpy-server SurfaceEncoder 设
  `repeat-previous-frame-delay-us=100ms`（官方源码），静止画面或按 10fps
  重复出帧；与本仓「静止画面 fps≈0」的实测注释（VideoPlayer.vue）相左，
  需真机确认一次，避免自适应码率对静止画面误判（重复出帧时静止画面
  fps 上报 ~10 不触发上报 gate，决策器不会误降档；真正静止 0fps 也不
  上报——两者都安全，确认只为记录事实）。

### 2.5 实施项 5（P1）：日志按需采集与展示

- **后端文件**：`backend/app/application/debug_service.py`
- **做法（惰性启动采集）**：
  1. `create_session()` 与 `restore_sessions()` 不再启动 `_collect_logcat`；
  2. 在 `set_subscriber_filter(paused=False)` 时：若该 session 尚无采集任务，
     启动采集（`asyncio.create_task`，登记进 `logcat_tasks`，任务内自行清理）；
  3. 停采时机：`set_subscriber_filter(paused=True)` 且该 session 已无任何
     paused=False 的订阅者 → cancel 采集任务（内存 buffer 保留，历史可查）；
     订阅者断开（unsubscribe）后同样判定停采；
  4. 采集任务需保证幂等（启动前查 `logcat_tasks` 防重复），停止后再次
     paused=False 可重启；
  5. 保留 500ms 停采宽限（`asyncio.sleep` 后复查），防录制开关抖动导致
     logcat 子进程频繁启停。
  - 注意：`close_session()` 已有 cancel 逻辑，任务字典入口在停止后需移除
    （否则 close 时二次 cancel 无害但记 warning）。
- **前端文件**：`frontend/src/components/debug/LogcatView.vue`、
  `frontend/src/stores/debug.ts`
- **做法（开启录制才连接拉取）**：
  1. `LogcatView` onMounted **不再**直接 `connectWebSocket()`/`fetchLogs()`；
     改为 watch `debugStore.isRecording`：false→true 时先 `connectWebSocket()`
     再 `fetchLogs()`（拿历史），随后订阅推送自动生效（connect 时已按
     isRecording 发 paused）；true→false 时断开 WS（或保持连接仅 paused=true，
     评审时定——倾向断开，彻底省资源）。
  2. 初始 isRecording=false：页面显示「日志录制已暂停，开启后开始接收」，
     不发起任何网络请求；
  3. `debug.ts` 的意外断线自动重连加门：`!isRecording.value` 时不重连
     （当前 close handler 无条件 2s 重连）；
  4. 开启录制后新日志按现有滚动行为滚动显示（确认 LogcatView 的自动滚动
     仅在新日志追加时触发，历史载入不整页跳动）。
- **测试**：
  - 后端：`tests/application/test_debug_service.py`（如存）补：create 后
    logcat_tasks 为空；paused=False 触发采集启动（assert task 创建）；
    全部订阅者 paused 后停采；close 幂等。
  - 前端：vitest 对 debug store 的 setRecording 行为与重连门（mock
    WebSocketService）；LogcatView 挂载不发请求（mock api/ws 断言零调用）。
- **预期收益**：每台未看日志的设备省 1 个常驻 adb logcat 子进程 + 解析 +
  落库 I/O；多设备（尤其 .33 类失联设备）不再空跑采集、不再刷日志噪音。
