## 二、后端四层结构与依赖方向

### 2.0 依赖规则

```
interfaces/  ──►  application/  ──►  domain/
                                        ▲
                     infrastructure/ ───┘（实现 domain 定义的 Protocol）
```

- **domain 层不依赖任何框架**：`ports.py` / `device.py` / `session.py` 只有 dataclass 与 `typing.Protocol`。
- **application 层只依赖 Protocol**，不 import 具体实现类（例外见 2.5 关于 `scrcpy/` 的说明）。
- **infrastructure 层实现 Protocol**：`AdbCliDriver` 实现 `AdbDriver`、`ScrcpyEncoder` 实现 `VideoEncoder`、
  `SqliteDebugRepository` 实现 `DebugRepository`。
- **interfaces 层只做协议转换**：解析 HTTP/WS 消息、调用应用服务、序列化回包。
- 依赖注入全部集中在 `backend/app/deps.py`（组合根），通过 FastAPI `Depends()` 注入。

### 2.1 领域层 `backend/app/domain/`

| 文件 | 内容 |
|------|------|
| `device.py` | `DeviceInfo` 数据类：`id` / `model` / `os_version` / `resolution` / `battery` / `status`（`online`\|`offline`\|`busy`）等，另有 `is_online` / `is_busy` 属性 |
| `session.py` | `DebugSession` 数据类：日志内存环形缓冲 `log_buffer`、`shell_history`、断线续传游标 `seq_next`、`touch()` |
| `ports.py` | 全部 Protocol 端口与跨层 DTO |

`ports.py` 定义的 Protocol（`@runtime_checkable`）：

- `AdbDriver` — 设备通信全部入口：`list_devices` / `get_device_info` / `shell` / `shell_stream` / `stream_logcat` / `push` / `pull` / `install` / `screenshot` / `connect_tcp` / `disconnect_tcp` / `create_shell`。
- `ShellSession` — 交互式 PTY shell：`start` / `execute` / `send_input` / `get_output` / `stop`。
- `VideoEncoder` — `start(device_id, opts) -> AsyncIterator[bytes]` / `stop`。
- `DebugRepository` — 会话、日志、shell 历史的持久化与清理。
- `DeviceRepository` — 设备信息持久化。

DTO：`LogEntry`（ts/level/pid/tid/tag/message/raw）、`LogFilter`、`EncoderOpts`（`max_size` / `bit_rate` / `codec` / `fps`）。

### 2.2 应用层 `backend/app/application/`

| 模块 | 类 | 职责 |
|------|----|------|
| `device_service.py` | `DeviceService` | 设备发现/详情/APK 安装/截图；持有后台设备状态刷新任务与连接/断开回调 |
| `stream_service.py` | `StreamService` | 视频流用例编排：每设备一个编码器实例、帧分发、自适应码率重启、`start_stream` / `stop_stream` / `get_encoder` / `report_client_fps` |
| `debug_service.py` | `DebugService` | 调试会话生命周期、logcat 惰性采集（`_collect_logcat`）、WS 订阅者过滤分发、shell 执行与历史（同一会话命令经 `_session_locks` 串行化）、定期清理 |
| `app_service.py` | `AppService` | 应用列表/详情/启动/停止/卸载/清数据/内存占用（解析 `dumpsys` 等） |
| `session_service.py` | `SessionService` | 协作会话（owner/participants/active_controller），当前为纯内存实现 |
| `performance_service.py` | `PerformanceService` | 性能采样任务管理 + 内存环形缓冲 + `stream_metrics` 异步生成器 |
| `bitrate_advisor.py` | `BitrateAdvisor` / `AdvisorConfig` / `parse_bit_rate` | 自适应码率纯逻辑决策器（无 IO、无时钟，时间由调用方注入） |

### 2.3 基础设施层 `backend/app/infrastructure/`

| 子目录/文件 | 实现 | 说明 |
|------|------|------|
| `adb/cli.py` | `AdbCliDriver` | 基于 `adb` 子进程实现 `AdbDriver`；`stream_logcat()` 启动 `adb shell logcat -v threadtime -T "$(date "+%m-%d %H:%M:%S.%N")"`，以设备端当前时刻为下界（零重放） |
| `adb/shell.py` | `InteractiveShell` | `adb shell -tt` 持久化 PTY 会话，后台读取器路由 `_exec_queue` / `_output_queue` |
| `adb/winpty.py` | ConPTY 适配器 | Windows 无真实控制台时把 pywinpty 适配成 `asyncio.subprocess.Process` 形状 |
| `adb/reachability.py` | `probe_tcp()` | `adb connect/disconnect` 前的纯 TCP 可达性预检，失败抛 `DeviceUnreachableError` |
| `persistence/sqlite.py` | `SqliteDebugRepository` / `SqliteDeviceRepository` / `init_db()` | aiosqlite 异步访问，WAL + busy_timeout，按 db_path 共享连接池 |
| `persistence/batch_writer.py` | `BatchLogWriter` | 日志先入内存，满 `log_batch_size`（默认 100）条或 0.1s 一次 `save_logs_bulk` 单事务落库 |
| `stream/scrcpy.py` | `ScrcpyEncoder` | 实现 `VideoEncoder`：推 JAR、建端口转发、启动 server、双 socket（视频+控制）、12 字节包头切包、`send_input()` |
| `performance/sampler.py` | `PerformanceSampler` | ADB 采集 CPU/内存/帧率/前台 Activity，产出 `PerformanceMetrics` |
| `network/sampler.py` | `NetworkSampler` | `/proc/net/dev`、`/proc/net/tcp` 等采集流量与连接表 |

### 2.4 接口层 `backend/app/interfaces/`

HTTP 路由（六个模块，均在 `main.py` 中用 `include_router` 注册）：

| 模块 | 前缀 | 主要端点 |
|------|------|----------|
| `http/devices.py` | `/api/devices` | 列表、详情、安装 APK、批量安装、截图、`connect` / `{id}/disconnect`、SSE `events` |
| `http/debug.py` | `/api/debug` | `sessions` 创建/查询/关闭、`sessions/{id}/logs` 查询与导出（CSV 等）、`sessions/{id}/shell` 执行 |
| `http/sessions.py` | `/api/sessions` | 协作会话创建/加入/离开/转移控制权 |
| `http/apps.py` | `/api/apps` | 应用列表/详情/launch/stop/uninstall/clear-data/memory |
| `http/network.py` | `/api/network` | `{device_id}/stats`、`{device_id}/connections` |
| `http/performance.py` | `/api/perf` | `{device_id}/metrics`、`start`、`stop` |

WebSocket 端点（因 FastAPI 限制，路径在 `main.py` 内联注册，处理逻辑在 `interfaces/ws/`）：

| 端点 | 处理函数 | 用途 |
|------|----------|------|
| `/ws/video/{device_id}` | `ws/video.py: video_stream()` | 视频帧下发（二进制）+ 输入事件上行（JSON） |
| `/ws/debug/{session_id}` | `ws/debug.py: debug_stream()` | 日志推送、shell 流式输出、PTY 输入透传 |
| `/ws/perf/{device_id}` | `ws/performance.py: stream_metrics()` | 每秒推送一次性能指标 JSON |

`ws/socket_opts.py: enable_tcp_nodelay()` 是接口层的 best-effort 工具：为 WS 连接设置 `TCP_NODELAY`，失败静默忽略。

### 2.5 协议实现包 `backend/app/scrcpy/`

这是**四层之外的共享协议原语包**（不在严格分层图内），被接口层与基础设施层共同引用：

| 文件 | 内容 |
|------|------|
| `constants.py` | NALU 类型（`NALU_TYPE_SLICE=1` / `IDR=5` / `SEI=6` / `SPS=7` / `PPS=8` / `AUD=9`）、Android keycode、`SCRCPY_SERVER_VERSION="4.1"`、`SCRCPY_SERVER_REMOTE_PATH="/data/local/tmp/scrcpy-server.jar"`、`SCRCPY_SERVER_CLASS="com.genymobile.scrcpy.Server"`、`VIDEO_STREAM_FRAME_SIZE=65536` |
| `h264_parser.py` | `H264Parser.feed()` 按起始码切分 NALU，回看修正 3/4 字节码混用 |
| `stream_protocol.py` | scrcpy v4.1 流协议：握手（1B dummy + 64B 设备名 + 4B codec id）、`SC_PACKET_HEADER_SIZE=12`、`SC_PACKET_FLAG_SESSION=1<<63`、`SC_PACKET_FLAG_CONFIG=1<<62`、`SC_PACKET_FLAG_KEY_FRAME=1<<61`、`SC_CODEC_ID_H264=0x68323634`；`read_packets()` 异步切包迭代器产出 `SessionEvent` / `MediaEvent` |
| `au_aggregator.py` | `aggregate_aus()` 启发式聚帧（raw_stream 兜底路径使用） |
| `control_sender.py` | `ControlSender`：二进制控制消息（触摸 32B、按键 13B、文本 5+len、滚动 21B），`asyncio.Lock` 串行化写入 |
| `server_manager.py` | `ServerManager`：`push_server()` 每次启动都推送 JAR（server 退出时会自删） |
| `scrcpy-server.jar` | scrcpy v4.1 服务端（推送到设备后由 `app_process` 启动） |

> 现状说明：`interfaces/ws/video.py` 与 `infrastructure/stream/scrcpy.py` 都直接 `from app.scrcpy import ...`。
> 这是既成的技术取舍（协议原语无状态、无 IO、便于单测），不代表新增业务代码可以照此跨层引用。

### 2.6 横切关注点与组合根

| 文件 | 作用 |
|------|------|
| `backend/app/core/config.py` | 重新导出项目根 `config/settings.py` 的 Pydantic Settings 单例 |
| `backend/app/core/logging.py` | structlog 配置，`get_logger(__name__)` 结构化日志 |
| `backend/app/core/exceptions.py` | `OpenScrcpyException` 体系与统一异常处理器 |
| `backend/app/core/config_watch.py` | 配置热重载：`ConfigWatcher`（零依赖 mtime 轮询 `config/base.yaml` + `config/{APP_ENV}.yaml`）+ `reload_config()`（监听循环与 `POST /api/system/config/reload` 共用） |
| `backend/app/deps.py` | 组合根：`@lru_cache()` 单例（`get_adb_driver` / `get_device_repository` / `get_debug_repository` / `get_device_service` / `get_debug_service` / `get_performance_service` / `get_app_service`），`get_stream_service` / `get_session_service` 每次新建 |

| `backend/app/main.py` | `create_app()` 应用工厂：CORS、三级异常处理器、七个 HTTP 路由、三个 WS 端点、`/health` |
| `run_server.py` | Windows 上先设置 `WindowsProactorEventLoopPolicy` 再 `uvicorn.run`（asyncio 子进程必需） |

## 四、关键数据流

### 4.1 数据流一：H.264 视频帧（设备 → 浏览器画布）

```
[设备] 屏幕内容
  │  MediaCodec 硬编码（video_codec=h264, max_fps=30, video_bit_rate=4Mbps）
  ▼
[设备] scrcpy-server.jar（app_process 启动，tunnel_forward=true, control=true）
  │  v4.1 流协议：session 包（宽高）/ config 包（SPS/PPS）/ 媒体包
  ▼
[主机] adb forward tcp:27183+hash(device_id)%100 → localabstract:scrcpy
  │  TCP 127.0.0.1:27xxx
  ▼
[后端 infrastructure/stream/scrcpy.py] ScrcpyEncoder
  │  后台任务 read_socket() 调用 scrcpy/stream_protocol.py: read_packets()
  │    ├─ 握手：1B dummy + 64B 设备名 + 4B codec id（校验 0x68323634）
  │    ├─ 12B 头 bit63 → SessionEvent(width, height, client_resized)
  │    │     → _handle_session_event() 更新分辨率 / 创建或更新 ControlSender
  │    └─ 其余 → 12B 头 + 载荷 → MediaEvent(is_config, is_key, pts, payload)
  │  config 包必入队（宁可阻塞不丢）；媒体包入 _data_queue(maxsize=100)，
  │  队列满则超时丢整包（包边界对齐，不产生半帧损坏）
  ▼
[后端 application/stream_service.py] StreamService.start_stream(device_id)
  │  帧循环：asyncio.wait({取帧, restart_event}) —— 自适应码率重启时以新码率重建编码器
  ▼
[后端 interfaces/ws/video.py] video_stream()
  │  H264Parser.feed(chunk) → NALU 列表
  │    ├─ SPS(7)/PPS(8)：拦截，两者齐备后 _send_config()
  │    │     → ws.send_json({type:"config", codec:"avc1.XXYYZZ", width, height, description: hex(SPS+PPS)})
  │    └─ 其余 NALU：
  │         packet_mode（默认，12B 包头协议）→ 包内 NALU 合并为单 AU → ws.send_bytes(au)
  │         兜底（stream.raw_stream_fallback=true）→ aggregate_aus() 启发式聚帧后逐 AU 发送
  ▼
[网络] WebSocket /ws/video/{device_id} 二进制消息（启用 TCP_NODELAY）
  ▼
[前端 services/websocket.ts] WebSocketService.onmessage（binaryType=arraybuffer）
  ▼
[前端 services/h264VideoStream.ts] H264VideoStream
  │  config 消息：hexToUint8Array → extractNalus → buildAvccDescription（avcC box）
  │               → canvas.width/height = 设备分辨率 → initDecoder() → VideoDecoder.configure()
  │  二进制帧：extractNalus → hasKeyFrame → shouldDropFrame(decodeQueueSize, isKey)
  │            → nalusToAvcc → new EncodedVideoChunk({type, timestamp:0, data})
  │            → decoder.decode(chunk)
  ▼
[前端] VideoDecoder output 回调：ctx.drawImage(frame, 0, 0, canvas.width, canvas.height) → frame.close()
  ▼
[浏览器] <canvas class="video-canvas">（CSS object-fit: contain 自适应容器，画布缓冲区 == 设备分辨率）
```

要点：

- `ScrcpyEncoder.start()` 强制 `max_size=0`（不缩放），保证视频帧尺寸 == 设备物理分辨率，
  这样画布坐标直接等于设备坐标，输入映射不会因缩放错位。
- 每次自适应码率重启会让 `StreamService` 的 epoch +1；WS 层检测到 epoch 变化即重建 `H264Parser`、
  清空 SPS/PPS/config 缓存，等待新 config。
- PTS 未透传给解码器（`EncodedVideoChunk.timestamp = 0`），仅用 `is_key` 标记 key/delta。

### 4.2 数据流二：控制指令（画布事件 → 设备）

```
[浏览器] 用户在 canvas 上 mousedown / touchstart
  ▼
[前端 components/stream/VideoPlayer.vue] onMouseDown / onTouchStart
  ▼
[前端 services/inputController.ts] InputController
  │  mapToScreen(clientX, clientY, canvas)：拉平 letterbox → 归一化 → 乘 canvas 像素尺寸
  │  手势识别：< 500ms 且位移 < 20px 视为点击；位移 >= 20px 视为滑动；长按 500ms 触发长按
  ▼
[前端] ws.send({action:"touch", x, y}) —— JSON 文本消息（同一条 /ws/video/{device_id} 连接上行）
       滑动：{action:"swipe", x1,y1,x2,y2,duration}
       按键：{action:"key", keycode}   文本：{action:"text", text}
       另每 2s 上报 {op:"stats", fps}（自适应码率反馈，静止 fps<1 时不上报）
  ▼
[后端 interfaces/ws/video.py] handle_input() 任务（与推流任务并发）
  │  op == "stats" → StreamService.report_client_fps() → BitrateAdvisor.decide()
  │  action 分支 → _handle_input() → StreamService.get_encoder(device_id)
  ▼
[后端 infrastructure/stream/scrcpy.py] ScrcpyEncoder.send_input(data)
  ▼
[后端 scrcpy/control_sender.py] ControlSender（二进制控制协议）
  │  touch → struct.pack(">B", TYPE_INJECT_TOUCH_EVENT) + ">BqiiHHHii" = 32 字节
  │  key   → TYPE_INJECT_KEYCODE + 13 字节
  │  text  → TYPE_INJECT_TEXT + 5 + len(utf8)
  │  swipe → ACTION_DOWN + 最多 100 个 ACTION_MOVE（步长 5px）+ ACTION_UP
  ▼
[网络] 控制 socket（与视频 socket 同端口 127.0.0.1:27xxx 的第二条连接）
  ▼
[设备] scrcpy-server 控制通道（control=true）→ Android InputManager.injectInputEvent()
       端到端延迟 < 5ms（对比 adb shell input 的 50-200ms）
```

降级路径：控制 socket 不可用（`_control_sender is None` 或分辨率未知）或发送异常时，
`ScrcpyEncoder._fallback_adb_input()` 改用 `adb shell input tap/swipe/keyevent/text`。

自适应码率的信令是双向的：

- 客户端 → 服务端：`{op:"stats", fps}` → `StreamService.report_client_fps()` → `BitrateAdvisor` 决定新档位
  → 写入 `_pending_bitrate` 并置位 `restart_event`。
- 服务端 → 客户端：`video.py` 的输入循环发现 pending 后发
  `{"type":"restarting","bit_rate":<bps>}`；前端 `H264VideoStream` 据此设 15s 宽限期，暂停回退 watchdog 与 fps 上报。

```
[前端] 用户在 LogcatView 点「开启录制」（默认不采集、不拉取）

  ▼
```

相关生命周期细节：

- **停采**：所有订阅者暂停/断开后 `_schedule_logcat_stop()` 延迟 `LOGCOLLECT_STOP_GRACE = 0.5s` 复查，
  仍无非暂停订阅者才取消采集任务（防开关抖动频繁启停子进程）。
- **断线续传**：前端重连时 `subscribe` 带 `from_seq`，服务端 `get_logs_since()` 补发缺口并回报 `missing`（已被环形缓冲淘汰的最旧条数），

  `restore_max_sessions`（默认 20）恢复会话对象，`seq_next` 从 `repo.next_seq()` 续接；logcat 不随恢复启动。
- **清理**：`start_cleanup_task()` 每 `cleanup_interval_hours` 执行 `run_cleanup()`（按保留期删除日志 / shell 历史 + 超库体积裁剪最旧日志）。仓储 `vacuum()` 已有实现与单测但尚未接入清理链路（指标数据清理方案 18 首次引入，见 `方案/18`）。

## 五、关键技术决策

### 5.1 为什么用 WebCodecs 而不是 MSE / 转码

- 项目约束只支持 Chrome，可直接使用 `VideoDecoder`，无需 polyfill。
- 低延迟路径：`optimizeForLatency: true` 逐帧 `decode()`，输出回调直接 `drawImage` 到 canvas
  （等价于 scrcpy 官方桌面端的「单槽帧缓冲」渲染语义），不做播放缓冲排队。
- 免去 MSE 的容器封装（fMP4 分段、jitter buffer）与 ffmpeg.wasm 的 CPU 开销。

### 5.2 传输通道：WebSocket 现状与 WebTransport 占位

- **现实链路只有 WebSocket 一条**：`/ws/video/{device_id}` 同时承载二进制视频帧与 JSON 输入/统计消息，
  并启用 `TCP_NODELAY`。上层直接使用 FastAPI WebSocket 对象，未包抽象层。
- **WebTransport 只剩前端占位符**：`WebTransportService.connect()` 在浏览器不支持时返回 false，
  当前没有任何调用方接入视频管道。后端原有的 `WebTransportTransport` 占位实现与
  `domain/ports.py` 的 `Transport` 协议已随死代码清理删除（全仓零引用、零覆盖）；
  将来真要上 HTTP/3 时再按需引入抽象（YAGNI）。

### 5.3 12 字节包头协议与 raw_stream 兜底

- 默认（`stream.raw_stream_fallback = false`）使用 scrcpy v4.1 原生包头：**包边界即帧边界**，
  config/keyframe/PTS 随包携带，后端无需靠启发式猜帧，`video.py` 直接把一包合并成一个 AU 下发。
- 兜底（置 true）回退 `raw_stream=true`（裸 Annex B），由 `H264Parser` + `aggregate_aus()` 启发式聚帧
  （SEI/SPS/PPS 挂靠后继 VCL，IDR/非 IDR slice 开新 AU，AUD 显式分界）。
- 两条路径由 `StreamService.use_packet_protocol()` 单点判定，WS 层据此选择聚合策略。

### 5.4 自适应码率：只能「按档重启」

- scrcpy 协议没有运行中改码率的控制消息，因此 `StreamService.start_stream()` 在检测到待生效码率时
  **停止并用新码率重建整个编码器**（每次切换 1-3s 黑屏）。
- `BitrateAdvisor`（纯逻辑）用迟滞与冷却把重启压到很少发生：档位来自 `stream.bitrate_tiers`（默认 `8M,4M,2M,1M`），
  客户端 fps 上报是输入，`start_bps` 为升档上限。
- 重启的配套动作：帧循环与 `restart_event` 赛跑（静止画面也能立即切换）→ epoch +1 →
  WS 层重置解析器并重新下发 config → 前端收到 `restarting` 后进入 15s 宽限期。

### 5.5 解码积压与回退/回切

- 解码队列积压时 `shouldDropFrame()` **只丢 delta 帧、key 帧永不丢**（丢 key 会导致后续 delta 全部花屏直到下个 IDR，
  设备端 I 帧间隔约 10s）；积压跨越一个 IDR 仍超阈值则重建解码器。
- 设备端编码器故障（典型如 Rockchip 硬编码器编码数秒后停流但 TCP 不断开）靠前端 watchdog 兜底：
  `evaluateH264Fallback()` 四类信号——`error` / `stalled`（出过帧后 3s 无新帧）/ `no-stream`（8s 无帧）/ `timeout`（15s 硬兜底）。
- 回退后 `H264VideoStream.suspend()` 保留 WS 消息处理器只计数不解码（探针），
  `evaluateH264Recovery()` 以 3 个 2000ms 窗口、每窗 ≥ 4 帧判定码流恢复，才 `resume()` 回切，
  回切后设 30s 冷却防「恢复几秒又卡死」的来回横跳。

### 5.6 依赖倒置与组合根

`deps.py` 是唯一的装配点，`@lru_cache()` 管理单例。
应用层构造参数类型一律是 Protocol（如 `DeviceService(adb: AdbDriver, repo: DeviceRepository)`），
因此测试可以注入假实现（例如 `StreamService` 的 `encoder_factory` 注入点）。

### 5.7 Windows 环境约定

- `run_server.py` / `main.py` 在 win32 上强制 `WindowsProactorEventLoopPolicy`——asyncio 子进程的前提。
- Git Bash 下执行 ADB shell 命令设置 `MSYS_NO_PATHCONV=1`，避免 `/data/local/tmp/...` 被转换成 Windows 路径。
- 交互式 shell 在 Windows 走 ConPTY（`infrastructure/adb/winpty.py`），不可用时降级管道。
