## E001 scrcpy v2.4 协议握手字段

**日期**：2026-09-09  
**标签**：`scrcpy` `协议` `握手`

### 症状

协议握手后分辨率解析为异常值：`26674x13876`。服务器继续发送 8 字节后连接关闭，无视频数据。

### 根因

错误的协议理解：以为握手只发 dummy byte + 设备名 + 分辨率（4 字节 = 2x uint16）。

**实际 scrcpy v2.4 协议握手顺序**：

| 顺序 | 长度 | 内容 | 格式 |
|------|------|------|------|
| 1 | 1 字节 | Dummy byte | 固定 `0x00` |
| 2 | 64 字节 | 设备名 | UTF-8，null 填充 |
| 3 | 4 字节 | Codec 名称 | ASCII 字符串（如 `"h264"`） |
| 4 | 4 字节 | 宽度 | uint32，大端序 |
| 5 | 4 字节 | 高度 | uint32，大端序 |

之前把 "h264" 的 ASCII 字节（`68 32 36 34`）按 uint16 解析成"分辨率"，得到 26674x13876。

### 正确实现

```python
# 1. Dummy byte
dummy = await reader.readexactly(1)

# 2. 设备名 (64 字节)
device_name = (await reader.readexactly(64)).decode("utf-8").rstrip("\x00")

# 3. Codec 名称 (4 字节 ASCII)
codec = (await reader.readexactly(4)).decode("ascii")  # "h264"

# 4. 宽度 (uint32 大端序)
width = struct.unpack(">I", await reader.readexactly(4))[0]

# 5. 高度 (uint32 大端序)
height = struct.unpack(">I", await reader.readexactly(4))[0]
```

### 经验

- 协议字段顺序不能猜测，必须对照 server 源码（`server/src/main/java/com/genymobile/scrcpy/Streamer.java`）
- 解析出异常数值（如分辨率 26674x13876）时，先检查原始字节是否是 ASCII 字符串

### 参考

- `docs/视频流修复完成.md`
- scrcpy v2.4 源码：`server/src/main/java/com/genymobile/scrcpy/Streamer.java`

## E002 scrcpy-server JAR 自动删除机制

**日期**：2026-09-09  
**标签**：`scrcpy` `server` `JAR`

### 症状

scrcpy-server 启动后立即崩溃，`adb shell` 输出 `Aborted`，进程退出码 134（SIGABRT）。

### 根因

scrcpy-server 在退出时（无论正常还是异常）会**自动删除** `/data/local/tmp/scrcpy-server.jar`。

因此每次启动前必须重新推送 JAR，不能假设上次推送的文件还在。

### 解决方案

```python
# 每次启动 server 前必须推送 JAR
async def start_server(self, device_id: str):
    # 1. 先推送 JAR（必须！）
    await self._push_jar(device_id)
    
    # 2. 再启动 server
    await self._run_server(device_id)
```

### 经验

- 设备上的临时文件可能被对方程序自动清理，不能假设"上次推送过就一直在"
- 推送失败时（如 Windows Git Bash 路径转换错误）会静默导致后续崩溃，必须检查推送结果

### 关联

## E003 scrcpy 编码器选择策略

**日期**：2026-09-09  
**标签**：`scrcpy` `编码器` `设备兼容`

### 症状

Server 启动报错：`Video encoder 'OMX.google.h264.encoder' for h264 not found`。

### 根因

不同 Android 设备支持的硬件编码器不同：
- RK3288 设备：`OMX.rk.video_encoder.avc`
- 通用 Google 软件编码器：`OMX.google.h264.encoder`

硬编码编码器名称会导致在不支持的设备上启动失败。

### 解决方案

**不指定 `video_encoder` 参数**，让 scrcpy-server 自动选择可用的编码器。

```python
cmd = [
    "adb", "-s", device_id, "shell",
    f"CLASSPATH={SCRCPY_SERVER_REMOTE_PATH}",
    "app_process", "/",
    SCRCPY_SERVER_CLASS,
    SCRCPY_SERVER_VERSION,
    "log_level=info",
    f"max_size={opts.max_size}",
    f"max_fps={opts.fps}",
    f"video_bit_rate={bit_rate_value}",
    "video_codec=h264",          # 必须指定编码格式
    # ❌ 不指定 video_encoder，让服务器自动选择
    "tunnel_forward=true",
    "send_frame_meta=false",
    "control=true",
    "audio=false",
    # ...
]
```

### 经验

- 硬件能力因设备而异，不要硬编码硬件相关参数
- `video_codec`（编码格式）可以固定为 `h264`（浏览器友好），但 `video_encoder`（具体编码器实现）让 server 自动选择
- Server 启动日志会打印可用编码器列表，调试时可查看

### 调试命令

```bash
adb shell dumpsys media.codec | grep -i encoder
```

## E004 Git Bash 路径自动转换

**日期**：2026-09-09  
**标签**：`Windows` `Git Bash` `ADB` `路径`

### 症状

`adb push local.jar /data/local/tmp/scrcpy-server.jar` 失败，错误：

```
failed to copy to 'C:/Program Files/Git/data/local/tmp/scrcpy-server.jar'
```

或 `adb shell ls /data/local/tmp/` 报错：

```
ls: Files/Git/data/local/tmp/scrcpy-server.jar: not found
```

### 根因

Git Bash（MSYS2）会**自动将 POSIX 风格路径转换为 Windows 路径**：
- `/data/local/tmp` → `C:/Program Files/Git/data/local/tmp`

这对 ADB 命令（目标路径是 Android 设备上的 POSIX 路径）是灾难性的。

### 解决方案

**方法 1**：设置环境变量禁用路径转换

```bash
MSYS_NO_PATHCONV=1 adb push local.jar /data/local/tmp/scrcpy-server.jar
```

**方法 2**：在 `asyncio.create_subprocess_exec` 中传递环境变量

```python
env = os.environ.copy()
env["MSYS_NO_PATHCONV"] = "1"
process = await asyncio.create_subprocess_exec(
    "adb", "-s", device_id, "push", local_path, remote_path,
    env=env,
)
```

**方法 3**：使用 `//` 开头（Git Bash 识别为绝对路径，不转换）

```bash
adb shell ls //data//local//tmp/
```

### 经验

- 在 Windows Git Bash 中执行 ADB 命令**必须**设置 `MSYS_NO_PATHCONV=1`
- 所有涉及 ADB 的 subprocess 调用都要传递这个环境变量
- `adb push/pull`、`adb shell`、`adb forward` 都受影响

## E005 scrcpy 双连接协议

**日期**：2026-09-09  
**标签**：`scrcpy` `协议` `连接`

### 症状

只建立视频连接时，server 行为异常或协议不同步。

### 根因

scrcpy v2.x 协议**强制要求建立两个连接**：
1. **视频 socket**：用于接收视频数据
2. **控制 socket**：用于发送控制事件（触摸、按键等）

即使不用控制功能，也必须建立控制连接，否则协议状态不正确。

### 正确实现

```python
# 1. 建立视频连接（先）
video_reader, video_writer = await asyncio.open_connection("127.0.0.1", port)

# 2. 建立控制连接（后）
_, control_writer = await asyncio.open_connection("127.0.0.1", port)

# 两个连接都要保持打开
```

### 经验

- 协议连接顺序很重要：视频连接先建立，控制连接后建立
- "即使不用也要建立"是常见的协议设计模式（如 HTTP/2 的 SETTINGS 帧）
- 停止时必须关闭两个连接，否则会泄漏资源

## E006 scid 格式（十六进制非十进制）

**日期**：2026-09-09  
**标签**：`scrcpy` `scid` `格式`

### 症状

scrcpy v4.x server 无法识别 socket 连接，连接被拒绝。

### 根因

scid（Session ID）是 **31 位随机数，格式化为 8 位十六进制零填充**，不是十进制。

scrcpy 源码 `app/src/server.c`：
```c
snprintf(scid_string, sizeof(scid_string), "%08x", scid);  // %08x = 十六进制
```

错误实现：`f"scrcpy_{scid}"`（scid 是十进制）  
正确实现：`f"scrcpy_{scid:08x}"`（scid 格式化为 8 位十六进制）

### 注意

**scrcpy v2.x 使用固定 socket 名称 `"scrcpy"`**，不含 scid。只有 v4.x 才需要 scid。

### 经验

- 格式化的进制（十进制 vs 十六进制）必须对照源码确认
- 版本差异可能导致 socket 命名规则不同

没有阅读 scrcpy-server 源码，仅凭猜测和文档（可能不准确）实现协议。

- **禁止盲改试错**（违反 DEVELOPMENT.md 约束 7）

## E008 Windows asyncio 子进程必须用 ProactorEventLoop

**日期**：2026-09-09  
**标签**：`Windows` `asyncio` `子进程`

### 症状

Windows 上 `asyncio.create_subprocess_exec` 报错：
```
NotImplementedError: subprocesses are not supported on Windows with SelectorEventLoop
```

### 根因

Windows 默认的 `SelectorEventLoop` **不支持子进程**。必须使用 `ProactorEventLoop`。

### 解决方案

在程序入口处（`run_server.py`）设置事件循环策略：

```python
import sys
import asyncio

if sys.platform == "win32":
    asyncio.set_event_loop_policy(asyncio.WindowsProactorEventLoopPolicy())
```

### 经验

- Windows 上任何涉及 `asyncio.create_subprocess_exec` 的程序都必须配置 ProactorEventLoop
- 必须在**主线程**、**程序入口**处设置，不能在子线程或异步函数中设置
- FastAPI/Uvicorn 会在启动时创建 loop，所以要在 `uvicorn.run()` 之前设置

## E009 Rockchip 硬件编码器崩溃导致视频流中断

**日期**：2026-09-10
**标签**：`scrcpy` `编码器` `Rockchip` `兼容性`

### 症状

浏览器显示"正在连接..."，始终无法进入"直播中"状态。后端日志显示 scrcpy-server 正常启动并完成协议握手，但只发送了约 21 帧（~150KB）后数据流停止。WebSocket 连接保持打开但不再有数据传输。

### 诊断过程

1. **排除前端问题**：Vite 代理正确转发 WebSocket（JSON config + 二进制帧均通过）
2. **排除后端问题**：直连后端 8765 端口行为一致（初始帧后停止）
3. **编码器诊断日志**：在 `read_socket` 和 yield 循环添加计数，确认数据在 TCP 层就停止了
4. **设备日志**：`adb logcat` 发现关键线索：
   ```
   OMXNodeInstance: !!! Observer died. Quickly, do something, ... anything...
   scrcpy: Cleaning up
   ```
5. **根因确认**：Rockchip RK3288 的 OMX 编码器组件 (OMX.rk.video_encoder.avc) 在编码几秒后崩溃
6. **多种参数测试**：降低分辨率（800x448）、帧率（15fps）、码率（2Mbps）均无效

### 根因

设备硬件编码器 OMX.rk.video_encoder.avc 存在兼容性问题：
- 编码器能成功初始化（setupVideoEncoder succeeded）
- 能产出少量帧（SPS/PPS + IDR + 几帧 P-frame）
- 几秒后 OMX 组件崩溃（Observer died），不再产出帧
- 这是 Android 7.1.2 + Rockchip RK3288 的已知问题

参考：[scrcpy GitHub #2964](https://github.com/Genymobile/scrcpy/issues/2964)

### 解决方案

**前端自动回退**：VideoPlayer.vue 实现 10 秒超时检测
- 启动 H264 模式
- 10 秒内无帧 → 自动切换到截图模式 (~1 FPS)
- 截图模式使用 `adb screencap -p` API（~0.8 秒/帧，已验证可用）

```typescript
// H264 超时回退
const h264FallbackTimer = window.setTimeout(() => {
  if (h264Stream.stats.frameCount === 0) {
    h264Stream.stop()
    startScreenshotMode()  // 切换到截图模式
  }
}, 10000)
```

### 经验

- **编码器崩溃不会报错到客户端**：TCP socket 保持打开，但数据停止流动。需要通过超时检测来发现
- **设备日志是关键**：`adb logcat | grep OMX` 能发现编码器层面的问题
- **硬件兼容性问题无软件解法**：降低参数无效，只能回退到截图模式
- **分层诊断**：前端 → 代理 → 后端 → TCP → 设备，逐层排除

### 诊断命令

```bash
# 检查设备可用编码器
adb shell cat /system/etc/media_codecs.xml | grep -i encoder

# 实时监控编码器日志
adb logcat | grep -E 'OMX|MediaCodec|scrcpy|encoder'

# 检查编码器是否崩溃
adb logcat | grep "Observer died"
```

## E010 坐标映射必须基于视频实际尺寸而非设备物理分辨率

**日期**：2026-09-11
**标签**：`坐标映射` `输入控制` `视频流`

### 症状

截图模式下鼠标点击定位不准确，点击位置与实际触发位置有偏差。

### 诊断过程

1. **分析 InputController.mapToScreen() 逻辑**：
   - 使用 `canvas.width/canvas.height` 计算视频纵横比
   - 使用 `this.deviceWidth/deviceHeight`（设备物理分辨率）映射到设备坐标

2. **发现问题**：
   - 截图模式下，`canvas.width/height` 被 `renderBlob` 更新为截图实际尺寸（如 1080x608）
   - 但 `deviceWidth/deviceHeight` 来自 API 的设备物理分辨率（如 1080x1920）
   - 如果设备横屏，截图是 1920x1080，但 deviceWidth=1080, deviceHeight=1920
   - 导致坐标映射错误

### 根因

坐标映射应基于**当前显示的视频/截图实际尺寸**，而不是设备物理分辨率。

参考 scrcpy 源码（`app/src/input_manager.c` + `screen.h`）：
```c
// scrcpy 使用 frame_size（视频帧尺寸）而非设备物理分辨率
*x = *x * screen->frame_size.width / screen->window_size.width;
*y = *y * screen->frame_size.height / screen->window_size.height;
```

### 解决方案

使用 `canvas.width/height`（视频/截图实际像素尺寸）进行坐标映射：

```typescript
mapToScreen(clientX: number, clientY: number, canvas: HTMLCanvasElement) {
    const rect = canvas.getBoundingClientRect()
    const canvasPixelWidth = canvas.width   // 视频/截图实际宽度
    const canvasPixelHeight = canvas.height // 视频/截图实际高度

    // 计算视频显示区域（处理 letterboxing）
    const videoAspect = canvasPixelWidth / canvasPixelHeight
    const containerAspect = rect.width / rect.height

    // ... 计算 displayWidth, displayHeight, offsetX, offsetY ...

    // 计算点击在视频区域内的相对位置（0-1）
    const relX = (clientX - rect.left - offsetX) / displayWidth
    const relY = (clientY - rect.top - offsetY) / displayHeight

    // 映射到设备坐标（基于视频实际尺寸）
    return {
        x: Math.round(relX * canvasPixelWidth),
        y: Math.round(relY * canvasPixelHeight),
    }
}
```

### 经验

- **坐标映射必须基于显示内容的实际尺寸**，而非设备的物理属性
- 设备可能横屏/竖屏，截图尺寸会随之变化
- 参考官方实现（如 scrcpy）的坐标转换逻辑
- 添加边界检查（clamp）防止坐标超出范围

### 参考

- scrcpy 源码：`app/src/input_manager.c`、`app/src/screen.h`
- GitHub 搜索结果确认 scrcpy 使用 `frame_size` 而非设备分辨率

## 通用经验提炼

### 1. 协议实现铁律

- **不猜测**：协议字段顺序、长度、进制必须对照源码
- **参考多源**：官方源码 + 已验证客户端实现
- **解析出异常值时**：先检查是否是 ASCII 字符串、是否读错了偏移

### 2. Windows 开发坑

| 坑 | 解决 |
|---|---|
| Git Bash 路径转换 | `MSYS_NO_PATHCONV=1` |
| asyncio 子进程 | `WindowsProactorEventLoopPolicy()` |
| Unicode 输出 | `PYTHONIOENCODING=utf-8` 或避免特殊字符 |

### 3. 资源生命周期

- 对方程序可能自动清理临时文件（如 scrcpy-server 删除 JAR）
- 多连接协议必须全部正确关闭
- 子进程必须在 finally 中 terminate + 检查 returncode

### 4. 调研方法论

症状 → 假设 → **查源码验证假设** → 修复

不是：症状 → 猜测 → 改代码试试 → 再猜 → 再改

### 5. 调试技巧

- 抓原始字节，看十六进制（`data.hex()`）
- 尝试不同解码方式（ASCII、UTF-8、uint16、uint32）
- 对照源码逐字节核对
- 用最小复现脚本隔离问题

## E011 WebCodecs AVCC description 构建必须包含 NAL 头

**日期**：2026-09-11  
**标签**：`WebCodecs` `AVCC` `H264` `SPS/PPS`

### 症状

WebCodecs VideoDecoder 报错：`An EncodedVideoChunk was marked as type key but wasn't a key frame`，所有帧解码失败，触发 15 秒超时回退到截图模式。

### 根因

AVCC (avcC box) 格式中 SPS/PPS 数据的正确内容：
- **包含 NAL 头**（如 `0x67 xx xx ...`），只去掉起始码（`00 00 00 01` 或 `00 00 01`）
- 参考 ISO 14496-15 AVC Sample Entry 规范

错误实现：
```typescript
// ❌ 去掉了 NAL 头（0x67），只保留 RBSP
const sps = stripStartCodeAndNalHeader(spsWithStartCode)
```

正确实现：
```typescript
// ✅ 只去起始码，保留 NAL 头
const sps = stripStartCode(spsWithStartCode)  // 保留 0x67 xx xx ...
```

### SPS 字段索引

SPS 数据（保留 NAL 头后）：
```
sps[0] = NAL header (0x67 for SPS)
sps[1] = profile_idc
sps[2] = constraint_set flags (compatibility)
sps[3] = level_idc
```

错误用法 `sps[0]/sps[1]/sps[2]` → 正确用法 `sps[1]/sps[2]/sps[3]`

### AVCC totalSize 计算

```
// ❌ 缺少 numOfPPS 字段（1 字节）
totalSize = 6 + 2 + sps.length + 2 + pps.length  // = 36（RangeError）

// ✅ 正确
totalSize = 7 + 2 + sps.length + 2 + pps.length  // = 37
```

avcC box 结构（7 字节头部）：
```
configurationVersion (1) + profile (1) + compatibility (1) + level (1) +
lengthSizeMinusOne (1) + numOfSPS (1, 高3位=0x1F | 低5位=1) +
SPS_length (2) + SPS_data + numOfPPS (1) +
PPS_length (2) + PPS_data
```

### 经验

- AVCC/avcC 是 ISO 14496-15 定义的格式，必须**严格**按规范实现
- WebCodecs 的 `description` 字段是 ArrayBuffer（avcC 二进制），不是字符串
- 错误的数据格式不一定报错，可能导致解码器状态异常（如"非关键帧被标记为关键帧"）

### 参考

- ISO 14496-15: AVC file format
- WebCodecs VideoDecoder codec string 规范

## E012 WebSocket 消息处理器必须在 connect() 前注册

**日期**：2026-09-11  
**标签**：`WebSocket` `时序` `竞态条件`

### 症状

H264 视频流始终不显示，前端 console 无任何 `[H264] Config received` 日志，但有大量 `Frame dropped: decoder not ready, state: undefined decoder exists: false`。

### 根因

消息处理器的注册时序错误：
```typescript
// ❌ 错误：先 connect() 再注册 handler
ws.connect()              // 服务端立即发送 config 消息
h264Stream.start()        // 此时注册 handler → config 消息已被丢弃
```

WebSocket 连接建立后，服务端立即发送 config JSON 消息。如果此时 `onMessage` 回调还未注册，消息会被丢弃（`WebSocketService` 的 `onMessage` 为 null 时直接忽略）。

### 正确实现

```typescript
// ✅ 正确：先注册 handler，再 connect
h264Stream.start()   // 注册 setMessageHandler
ws.connect()         // 连接后 config 消息能正确到达 handler
```

### 经验

- WebSocket 消息可能在连接建立后立即到达，处理器必须提前注册
- 对于"请求-响应"模式（如 config），时序问题尤为关键
- 建议：API 设计上先调用 `start()`（注册 handler），后调用 `connect()`（建立连接）

## E013 scrcpy max_size 缩放导致坐标映射错位

**日期**：2026-09-11  
**标签**：`scrcpy` `坐标映射` `max_size` `输入控制`

### 症状

H264 模式下后端日志显示 `sending_touch` 正常触发，但设备无响应或响应位置错误。点击位置整体偏移。

### 根因

`max_size=1080` 导致 scrcpy-server 将视频缩小：
- 设备物理分辨率：1280x720（横屏）
- max_size=1080 缩放后视频：1080x607
- 前端 canvas 尺寸：1080x607（基于视频帧）
- InputController 映射坐标：0-1080（基于 canvas 尺寸）
- scrcpy-server 期望坐标：0-1280（设备物理分辨率）

坐标范围不一致：前端发送 (540, 300)，server 当作 (540, 300) 处理，但实际设备坐标范围是 0-1280 x 0-720，导致点击位置偏移。

### 解决方案

**后端**：强制 `max_size=0`（禁用缩放），保证视频帧尺寸 == 设备物理分辨率

```python
# backend/app/infrastructure/stream/scrcpy.py
opts = EncoderOpts(
    max_size=0,       # 禁用缩放
    bit_rate=opts.bit_rate,
    codec=opts.codec,
    fps=opts.fps,
)
```

**前端**：收到 config 消息后立即设置 canvas 尺寸为设备分辨率

```typescript
// frontend/src/services/h264VideoStream.ts
if (width > 0 && height > 0) {
    this.canvas.width = width
    this.canvas.height = height
    this.canvas.style.aspectRatio = `${width} / ${height}`
}
```

### 经验

- **视频缩放会影响坐标映射**：scrcpy-server 接收的坐标是设备物理坐标，不是视频帧坐标
- `max_size=0` 表示不缩放，视频帧尺寸 == 设备物理分辨率
- 坐标映射的一致性：前端 canvas 尺寸 == 视频帧尺寸 == 设备物理分辨率
- 后端 config 消息必须携带设备分辨率（`width/height`），前端据此初始化 canvas

### 关联

- [E010 坐标映射必须基于视频实际尺寸](#e010-坐标映射必须基于视频实际尺寸而非设备物理分辨率)

### 症状

视频流无法显示，涉及前端（WebCodecs）、后端（WebSocket/scrcpy）、设备（编码器）多层，难以定位问题所在层。

### 调试流程

1. **分层诊断**：前端 → 代理 → 后端 → TCP → 设备，逐层排除
2. **日志关键点**：
   - 前端：`[H264] Config received` / `[H264] Decoder state` / `[H264] Decode failed`

   - 检查原始字节（hex dump）确认 SPS/PPS 结构
   - 验证 AVCC description 大小是否符合公式
   - 确认 codec string 格式（`avc1.XXYYZZ`）

```
SPS 索引错误
    ↓

    ↓
```

## E016 /proc/net/tcp 地址格式解析

**日期**：2026-09-11  
**标签**：`网络` `Android` `proc`

### 背景

实现网络监控功能时，需要解析 `/proc/net/tcp` 文件获取 TCP 连接信息。

### 症状

直接读取 `/proc/net/tcp` 中的地址字段（如 `0100007F:0050`），无法直接使用。

### 根因

`/proc/net/tcp` 中的 IP 地址和端口号以十六进制编码，且 IP 地址是**小端序**（little-endian）。

格式：`hex_ip:hex_port`
- `0100007F` → 小端序解析为 `127.0.0.1`（不是 `7F000001`）
- `0050` → 十六进制端口 80

### 解决方案

```python
import struct

def parse_address(addr: str) -> tuple[str, int]:
    """解析 /proc/net 中的地址格式。"""
    parts = addr.split(":")
    ip_hex = parts[0]
    port_hex = parts[1]

    # 解析端口（大端序）
    port = int(port_hex, 16)

    # 解析 IP（小端序）
    ip_int = int(ip_hex, 16)
    ip_bytes = struct.pack("<I", ip_int)  # 注意 <I 是小端序
    ip_addr = f"{ip_bytes[0]}.{ip_bytes[1]}.{ip_bytes[2]}.{ip_bytes[3]}"

    return ip_addr, port
```

### 经验

- Linux proc 文件系统中的网络地址使用小端序编码
- 解析时需要用 `struct.pack("<I", ...)` 处理字节序
- `/proc/net/tcp6` 格式不同，IPv6 地址解析更复杂

### 参考

- Linux kernel 文档：`Documentation/networking/proc_net_tcp.txt`

## E017 dumpsys gfxinfo 获取 FPS 的正确方式

**日期**：2026-09-11  
**标签**：`性能监控` `Android` `FPS`

### 背景

实现性能监控时，需要获取设备实时帧率（FPS）。

### 症状

使用 `dumpsys gfxinfo <package>` 获取帧数，返回值是累计帧数（如 46887），不是实时 FPS。

### 根因

`dumpsys gfxinfo` 输出的是应用**启动以来的累计统计**：
- `Total frames rendered: 46887` — 累计渲染帧数
- `Janky frames: 2995` — 累计卡顿帧数

### 解决方案

**两次采样差值法**：

```python
class PerformanceSampler:
    def __init__(self):
        self._prev_frames: int | None = None
        self._prev_ts: float | None = None

    async def _get_fps(self, now: float) -> float | None:
        # 获取累计帧数
        total_frames = await self._get_total_frames()

        # 首次采样无法计算 FPS
        if self._prev_frames is None:
            self._prev_frames = total_frames
            self._prev_ts = now
            return None

        # 计算实时 FPS
        elapsed = now - self._prev_ts
        frame_delta = total_frames - self._prev_frames
        fps = frame_delta / elapsed if elapsed > 0 else 0

        self._prev_frames = total_frames
        self._prev_ts = now
        return fps
```

### 经验

- Android 没有直接提供"当前 FPS"的系统 API
- 实时 FPS 需要通过两次采样累计帧数的差值计算
- 首次采样返回 `null`（无前序数据），前端应显示 `-`
- 采样间隔建议 1-2 秒，间隔太短会导致 ADB 命令过于频繁

### 参考

- Android gfxinfo 文档：https://developer.android.com/topic/performance/graphics/debug-gfx
- `dumpsys gfxinfo` 命令参考
