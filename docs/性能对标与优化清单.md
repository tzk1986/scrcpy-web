## 一、对标评估：网页方案档已达第一梯队（端到端延迟实测钉死）

参照系：

- 原生 scrcpy 官方标称 **35–70ms**（USB 最佳路径：设备硬编 ~15-25ms + 传输 + 桌面原生解码渲染）
- 最接近的同类网页方案 ws-scrcpy（Node 代理 + 浏览器解码，比本方案还多一跳 Node 代理）**无公开基准**
- 网页架构必然比原生多「浏览器解码 + canvas 渲染 + WS 一跳」，行业合理预期在 **100–150ms 档**

现状判定：

- **已问鼎的项**（见 §二）
- **评估空白（已收口，见 §4.2）**：README 目标「视频 <150ms」实测**中位数 76ms**（65–83ms 5 样本）——「第一梯队」由实测数据钉死
- **架构级事项**：WS over TCP 有队头阻塞（WebRTC/UDP 是理论更低延迟路径，但引入复杂度大，属 Phase 2+ 议题）；截图模式反馈 1.5-2.5s 未达方案 17 目标的 <800ms

### 4.2 端到端延迟实测（P1-4）

- 方法：设备端毫秒时钟页（`http://127.0.0.1:8000/clock.html`，经 `adb reverse` + ACR Browser 部署）+ 网页投屏同框拍照法
- 拍照瞬间两侧为同一物理时刻：设备屏读数 ≈ 当前时刻 T，投屏画面读数 ≈ T − latency
- 布局：设备读数 "秒.毫秒"（如 `07.157`，60s 循环），投屏画面为同一读数页面
- 结果（2026-09-30，.18 设备 1366×768 横屏，局域网 adb 连接，4Mbps / 30fps，Chrome WebCodecs，5 张同框照片）：

| 样本 | 设备屏读数 | 投屏画面读数 | 延迟 |
|------|-----------|-------------|------|
| 1 | 37.135 | 37.070 | 65ms |
| 2 | 42.294 | 42.212 | 82ms |
| 3 | 39.710 | 39.644 | 66ms |
| 4 | 38.372 | 38.296 | 76ms |
| 5 | 41.148 | 41.065 | 83ms |

- **中位数 76ms**（均值 74.4ms，范围 65–83ms）
- 对照：原生 scrcpy 35–70ms；网页架构行业预期 100–150ms；README 目标 **<150ms**

- 测量精度说明：30fps 帧量化（±33ms 采样偏置）+ LCD 响应时间，绝对精度 ±20–30ms 级；延迟定义 = 同一画面内容在设备屏与投屏屏上的呈现时刻差
- 环境要点（复现用）：
  - `adb reverse tcp:8000 tcp:8000`（PC 与设备不同网段，用反向转发打通）

### 4.6 JAR 流复用收口（P1-7，2026-09-30，方案 28）

- 背景：E022 负载时段 JAR 推送 10.1s 致首帧抖动 4.3s→14.1s + no-stream 误回退闪变。根因链：scrcpy-server 退出自删主 JAR（E002）→ 每次连接无条件重推（push 常态 0.06–1s、负载态尖峰 10.1s）
- Phase 0 spike（.18，`tests/manual/spike_stream_reuse.py`）钉死三组事实：A 组 server 进程宽限复用（D2）判死——tunnel socket accept-once、客户端全断开即退进程；B 组 bak 链路 cp 0.094 / ls 0.109 / mv 0.110s（~0.1s 恒定 vs push 抖动）；C 组启动基线首帧中位 3766ms / p95 3891ms（stress 3860 / 3969 无显著劣化）
- 实施（TDD RED→GREEN，6 用例）：`backend/app/scrcpy/server_manager.py` `push_server` bak 化（10afca0）——ls -l 校验 bak 大小 → `cp` 恢复（bak 常驻不消耗）；无 bak/不符/恢复失败回退 push（D3）+ push 成功后 cp 刷新 bak（失败不阻塞）
  - **mv→cp 修正（0cad4ea）**：真机首轮复测暴露 mv 消耗性恢复缺陷——bak 移走后主 JAR 再被自删 → 10 轮 = 5 push + 5 restore；cp（0.094s ≈ mv）使 bak 常驻
- Phase 2 真机复测（.18）：
  - 连/断 N=10：首帧中位 **3829ms** / p95 **3906ms**（≤4s、无尖峰；与基线持平——常态 push 本就 ~0.06–1s 且与 JVM 冷启动串行，D1 摘除的 0.3–0.8s 被启动方差掩盖）；日志 **1 push + 9 restore**、bak 常驻（733706 B）
  - bak 失效回退：rm bak → 单轮 4141ms → push 重建 bak ✓（D3）
  - 码率重启（D4）：`tests/manual/spike_bitrate_restart.py` 低 fps stats 诱导降档 → restarting → 重启后 config+首帧，日志确认重启走 bak 恢复而非 push ✓
- 门禁：后端 pytest 794 passed / ruff / mypy strict 全绿；前端零改动；e2e video-stream 2 passed（32.6s）
- 判定：**P1-7 收口**——D1 价值如实重述为「10s 级 push 尖峰结构性摘除 + bak 路径与设备负载解耦」（E022 当日高负载偶发态，尖峰今日不复现），常态首帧不受损（与基线持平）；前端 no-stream 宽限（D5）按 spike 校准不实施（p95 3906ms 远小于 8s 阈值，误回退闪变由 D1 结构性闭合）。E022 慢 push 根因未查明——D1 绕开而非治愈

### 4.7 截图模式设备端编码链路换挡收口（P1-6 设备端，2026-09-30，方案 29）

- 背景：§4.5 收口后反馈中位 1116ms 仍距 <800ms 目标有差距，瓶颈单点 = 设备端 screencap PNG 编码中位 ~950–1000ms（已超目标本身），PNG 链路物理不可达
- Phase 0 spike（`tests/manual/spike_screenshot_raw.py`，三机 .18/.25/.33）一测定生死：
  - raw 裸传判死（4.2MB/帧，.25 全链 2625ms）；**raw|gzip -1 判活**：.18 照片级 594–750ms 中位 641 vs PNG 1171/1219/1281 ≈ 2×；典型画面 328–360ms；.25（rk3288/A7.1）两链路打平 ~985/1000（旧机物理上限）
  - 帧头双态钉死：A11=16B（w/h/fmt/colorspace）、A7.1=12B（w/h/fmt），前端按 `len - w*h*4` 反推；fmt=1 三台一致；通道顺序与 PNG 逐像素 SAME；gzip 往返精确；toybox gzip 三台可用
  - 契约经用户确认：`?format=raw` opt-in，默认 PNG 不变（D1）
- 实施（TDD RED→GREEN，后端 4 提交 2/前端 2 提交）：
  - 后端：`cli.py` `screenshot_raw_gzip`（`exec-out sh -c "screencap | gzip -1"`）+ `ports.py` Protocol 抽象 + `device_service` 薄透传 + 端点 `format=raw`（gzip 字节 + `Content-Encoding: gzip` + `X-Frame-Format: raw-rgba` 原样透传，浏览器网络层原生透明解压、后端零 CPU）；AdbError 单请求内回退 PNG + `X-Frame-Format: png`（D2/D4）
  - 前端：`api.ts` `screenshotRaw`（读 x-frame-format 头）；`videoStream.ts` 首帧走 raw、帧头校验（12/16B 双态 + fmt==1 + 尺寸越界档）`putImageData` 直渲染；校验失败丢弃该帧 + `_rawUnsupported` 会话记忆（不再试 raw）；后端回退 png 同步置记忆（D3/D4）
- Phase 3 真机收口（2026-09-30，端点级 = HTTP 全链含设备编码/传输）：
  - `.18` 照片级（本机 Spotlight 摄影图 cover 1366×768 全屏，熵 7.52）：raw **中位 673.5ms**（N=7：614.9/661.8/671.5/673.5/675.2/688.2/711.6）vs png 中位 1263.5ms（1223.3–1371.7）→ **约 1.9×，<800ms 达成 ✓**；解压帧头 16B/fmt=1 校验通过
  - `.18` 典型画面（主屏）：raw 中位 544.3 vs png 927.5 → 相对方案 27 基线 1116ms **约 2× 下降**
  - `.25`（A7.1）不进不退：raw 中位 873.0 vs png 1016.7（略优）；12B 头真机链路验证通过（解压 header=12/fmt=1）
  - e2e `screenshot-fallback` .18/.25 各 1 passed（真实浏览器出帧）；后端日志证实页面请求全为 `format=raw` 且无降级——dev 路径（vite 代理）`Content-Encoding` 透传无损
- 门禁：后端 pytest 800 passed + 1 skipped / ruff 清零 / mypy strict 63 文件；前端 vitest 411 passed / vue-tsc / eslint / coverage services 80% 达标
- 判定：**P1-6 收口、<800ms 目标达成**（照片级中位 673.5ms ≈ spike 预估 ~700ms 吻合）
- 备注（验证范围如实）：
  - 「无 gzip 设备」回退链路的真机注入不可行（三台设备系统目录只读且均带 toybox gzip，无法卸除）——该路径由三层单测锁定：cli rc=127+`sh: gzip: not found` → AdbError → 后端回退（`test_screenshot_raw_falls_back_to_png`）→ 前端 `format==='png'` 降级记忆
  - 构建版（_internal 静态托管）与 dev 的唯一差异 = vite 代理跳数（更严苛已验），直连后端只会更简单；构建版回归随下次方案 15 发版打包流程执行
  - .25 旧机 gzip 字节 > PNG 的极端内容（如启动器）仅 wire 增大、耗时不退（CPU 省于 PNG 编码）
