## 一、对标评估：网页方案档已达第一梯队（端到端延迟实测钉死）

参照系：

- 原生 scrcpy 官方标称 **35–70ms**（USB 最佳路径：设备硬编 ~15-25ms + 传输 + 桌面原生解码渲染）
- 最接近的同类网页方案 ws-scrcpy（Node 代理 + 浏览器解码，比本方案还多一跳 Node 代理）**无公开基准**
- 网页架构必然比原生多「浏览器解码 + canvas 渲染 + WS 一跳」，行业合理预期在 **100–150ms 档**

现状判定：

- **已问鼎的项**（见 §二）
- **评估空白（已收口，见 §4.2）**：README 目标「视频 <150ms」实测**中位数 76ms**（65–83ms 5 样本）——「第一梯队」由实测数据钉死
- **架构级事项**：WS over TCP 有队头阻塞（WebRTC/UDP 是理论更低延迟路径，但引入复杂度大，属 Phase 2+ 议题）；截图模式反馈 1.5-2.5s 未达方案 17 目标的 <800ms

## 四、验收基线（本次验证）

### 4.1 Task 泄漏 spike（P0-1）

- 脚本：`tests/manual/spike_task_leak.py`（同进程直连真设备流，不经 WS 层 → 隔离自适应降档唤醒路径）
- 复测：`python -u tests/manual/spike_task_leak.py 192.168.8.18:5555 --seconds 120`
- 结果（2026-09-30，.18 设备 1360×768 横屏，毫秒时钟页满速 30fps，120s）：

| 指标 | 实测 |
|------|------|
| 泄漏速率 | **30.0 任务/s** |
| 实测帧率 | 30.0 fps |
| 比值 | **1.00 任务/帧**（每帧精确泄漏 1 个） |
| 120s 累积 pending `Event.wait` | 3479（线性无上限） |
| stop_stream + aclose 后残留 | 3478（finally 不回收历史泄漏） |
| `gc.collect()` 后残留 | 0（循环引用可回收） |
| GC 回收副作用 | 每个任务一条 `Task was destroyed but it is pending!` 警告（数千行日志风暴） |

- 判定：**P0-1 确认成立**。会话期间线性增长（1 小时会话 ≈ 10.8 万 pending Task）；降档 `set()` 时全部同时唤醒（CPU 风暴）；GC 回收时日志被警告淹埋。

#### 4.1b 修复收口（2026-09-30）

- 修复：帧分支胜出即取消 loser（`event_task.cancel()`，+1 行）——取消传播至 `Event.wait` 的 future，即从 `Event._waiters` 摘除；`finally` 兜底与降档/卡死路径语义不变
- 回归测试：`tests/application/test_stream_task_leak.py`（修复前 5 帧残留 5 个 pending Task → 修复后 0）
- 真机复测（.18 / 毫秒时钟页满速 / 120s / 与基线同条件）：

| 指标 | 修复前（§4.1） | 修复后复测 |
|------|--------------|-----------|
| 实测帧率 | 30.0 fps | 30.0 fps |
| 泄漏速率 | 30.0 任务/s | **0.0 任务/s** |
| 比值 | 1.00 任务/帧 | **0.00 任务/帧** |
| 运行中 Event.wait（120s 采样） | 线性增长 → 3479 | **恒 1**（当轮活跃任务） |
| stop + aclose 后残留 | 3478 | **0** |
| `gc.collect()` 后残留 | 0（伴随数千行销毁警告） | 0（无警告） |

- 补充：静止屏低帧率复测（2.3 fps / 120s / 299 帧，全部为 6s 空闲保活）同样零泄漏——保活路径一并覆盖
- 判定：**P0-1 已修复收口**——3489 帧零泄漏、残留归零；门禁全绿（ruff / mypy strict / pytest 772 passed），自适应降档、卡死恢复、关键帧请求全路径无回归

### 4.2 端到端延迟实测（P1-4）

- 方法：设备端毫秒时钟页（`http://127.0.0.1:8000/clock.html`，经 `adb reverse` + ACR Browser 部署）+ 网页投屏同框拍照法
- 拍照瞬间两侧为同一物理时刻：设备屏读数 ≈ 当前时刻 T，投屏画面读数 ≈ T − latency
- 布局：设备读数 "秒.毫秒"（如 `07.157`，60s 循环），投屏画面为同一读数页面
- 结果（2026-09-30，.18 设备 1366×768 横屏，局域网 adb 连接，4Mbps / 30fps，Chrome WebCodecs，5 张同框照片）：

| 样本 | 设备屏读数 | 投屏画面读数 | 延迟 |
|------|-----------|-------------|------|
| 1 | 37.135 | 37.070 | 65ms |
| 2 | 42.294 | 42.212 | 82ms |
| 3 | 39.710 | 39.644 | 66ms |
| 4 | 38.372 | 38.296 | 76ms |
| 5 | 41.148 | 41.065 | 83ms |

- **中位数 76ms**（均值 74.4ms，范围 65–83ms）
- 对照：原生 scrcpy 35–70ms；网页架构行业预期 100–150ms；README 目标 **<150ms**
- **判定：大幅优于 README 目标，接近原生 scrcpy 区间上沿——「第一梯队」由实测钉死**
- 测量精度说明：30fps 帧量化（±33ms 采样偏置）+ LCD 响应时间，绝对精度 ±20–30ms 级；延迟定义 = 同一画面内容在设备屏与投屏屏上的呈现时刻差
- 环境要点（复现用）：
  - `adb reverse tcp:8000 tcp:8000`（PC 与设备不同网段，用反向转发打通）
  - PC 侧 `python -m http.server 8000 --directory .scratch`
  - 设备侧 ACR Browser：`am start -a android.intent.action.VIEW -d http://127.0.0.1:8000/clock.html -n acr.browser.barebones/acr.browser.lightning.activity.MainActivity`
  - 设备保活：`svc power stayon true` + `settings put system screen_off_timeout 2147483647`
  - 坑：AOSP 浏览器（.25）与 htmlviewer 对 file:// 禁止 JS；ACR + HTTP 正常

### 4.3 队列反压恢复实测（P0-2/P0-3，2026-09-30）

- 修复（`backend/app/infrastructure/stream/scrcpy.py`）：队列满 put 超时（模块常量 `_QUEUE_FULL_PUT_TIMEOUT = 1.0`）后不再「只丢新包」：
  - 清空积压（`_drop_backlog()`，丢旧保新、时延归零）
  - 断链 P 帧不入队（`_awaiting_keyframe` 等待态）；节流 1s 经控制 socket 发 RESET_VIDEO（`_request_idr_throttled()`，服务端 0.1-0.4s 重出 IDR 并重发 SESSION/CONFIG）
  - 关键帧自身触发超时时清积压后直投（解码即恢复，无需 RESET）
  - config 包（SPS/PPS）超时清积压腾位但**不丢**（解码前提）；read_socket 收尾哨兵改「清积压 + put_nowait(None)」，消除队列满时的无限阻塞
- 回归测试：`tests/scrcpy/test_scrcpy_encoder.py` 新增 7 例（清积压+丢到关键帧+节流请求 / config 超时保全 / 收尾哨兵直投 / 关键帧直投无 RESET / 节流器三元组），TDD RED 7/7 → GREEN；实现中修正「关键帧正常路径须复位等待态」缺陷（测试捕获）
- 真机 spike（.18 / 1360×768 横屏毫秒时钟页 / 慢消费者停滞 10s，`tests/manual/spike_backpressure.py`）：

| 指标 | 实测 | 判定 |
|------|------|------|
| 停滞期间溢出循环数 | 2 次/10s（读循环存活——每轮 RESET 响应携带 SESSION/CONFIG 均安全通过） | P0-3 消除 |
| RESET→新 IDR（awaiting=True 窗口） | 平均 289ms / 最大 375ms | 与方案 19「0.1-0.4s」吻合 |
| 队列峰值 → 停滞末值 | 100 → 27（溢出即清空） | 无旧积压回放 |
| 恢复后首帧延时 | 0ms（积压即刻吐出） | 时延归零 |
| 恢复后首个关键帧 | **第 2 帧** | 花屏窗口 ~10s → **~0** |
| 门禁 | pytest 779 passed / ruff 清零 / mypy strict 63 文件 | 全绿 |

- 判定：**P0-2/P0-3 已修复收口**——花屏窗口从 ~10s（等下个自然 IDR）缩至 ~0（RESET 0.3s 级催新 IDR + 关键帧直投），读循环与收尾不再有满队列阻塞点
- 备注：全量测试两次间一次 `test_find_available_port_detects_wildcard_listener` 偶发失败（方案 23 测试：端口压力下临时端口分到 65535 时 occupied+1 溢出），单跑与复跑全绿，与本修复无关
